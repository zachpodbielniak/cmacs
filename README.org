* Overview

CMacs is a fork of GNU Emacs 31.x that deeply integrates the
GLib/GObject ecosystem.  The goal: make Emacs a first-class GLib
application where everything — window management, shell, scripting,
introspection — is controllable from C via GObject Introspection,
without requiring elisp.

CMacs embeds three companion projects as git submodules under =deps/=:

- [[https://gitlab.com/zachpodbielniak/crispy][Crispy]] — C scripting engine (compile-and-run C with GLib/GObject)
- [[https://gitlab.com/zachpodbielniak/bacon][Bacon]] — GLib-native shell (pipelines, modules, job control)
- [[https://gitlab.com/zachpodbielniak/gowl][Gowl]] — Wayland compositor (tiling WM built on wlroots + GLib)

Each module is optional and detected at configure time via
=--with-cmacs-*= flags.

* Modules

** GLib Core (=--with-cmacs-glib=)

GLib event loop integration with the Emacs main loop.

- =cmacs-glib-iteration= / =cmacs-glib-pending-p= — pump the GMainContext
- =cmacs-glib-timeout-add= / =cmacs-glib-idle-add= / =cmacs-glib-source-remove= — schedule callbacks
- =cmacs-gobject-wrap= / =cmacs-gobject-unwrap= — bridge GObjects to elisp

** GObject Introspection (=--with-cmacs-gi=)

Call any GI-annotated library from elisp or cmacsgi:

- =gi-require= — load a typelib (e.g. =Gtk=, =Gio=, =Gowl=)
- =gi-call= / =gi-method= — invoke functions and methods by name
- =gi-enum= — resolve enum values
- =gi-list-functions= / =gi-function-info= — introspect namespaces

** Crispy (=--with-cmacs-crispy=)

Embed the Crispy C scripting engine:

- =crispy-eval= / =crispy-eval-string= — evaluate C expressions
- =crispy-compile= / =crispy-run= — compile and execute C source files
- =crispy-repl-eval= / =crispy-repl-reset= — interactive C REPL
- =crispy-cache-status= — check the build cache

** Bacon Shell (=--with-cmacs-bacon=)

Embed the Bacon shell as a GLib-native terminal:

- =bacon-start= / =bacon-stop= / =bacon-running-p= — lifecycle
- =bacon-eval= — execute shell commands
- =bacon-eval-c= — compile and run C code via crispy (from shell)
- =bacon-source= / =bacon-alias= / =bacon-environment= / =bacon-complete= — shell internals
- =bacon-ipc-start= / =bacon-ipc-stop= — socketpair IPC for cmacsgi builtin

The bacon shell's =cmacsgi= builtin can call back into CMacs (eval elisp,
open files, invoke GI functions, control gowl) over the IPC channel.

** Gowl Wayland Compositor (=--with-cmacs-gowl=)

Embed a full tiling Wayland compositor inside CMacs.  49 elisp commands
and 15 JSON dispatch methods expose complete window manager control:

*** Lifecycle
- =gowl-start= / =gowl-stop= / =gowl-running-p=
- =emacs --gowl= starts the compositor; inside an existing Wayland session
  it comes up nested, i.e. an *embedded session*.  =emacsclient --gowl=
  (and =M-x cmacs-gowl-attach=) brings that session up in an Emacs that is
  already running, falling back to =emacs --gowl= when no server answers.
  The installed launchers /Emacs Gowl/ and /Emacs Gowl (Client)/ do both
  for you.

*** GObject Accessors (for GI runtime control)
- =gowl-compositor= — the live =GowlCompositor= GObject
- =gowl-config-object= — the live =GowlConfig= GObject
- =gowl-module-manager= — the =GowlModuleManager= GObject

*** Client Management

*** Monitor & Tags

- =gowl-view-tags= / =gowl-set-tags= / =gowl-toggle-tag-view=

*** Layout

*** cmacsgi / D-Bus Access

All gowl features are also exposed over the bacon IPC channel and
D-Bus (=org.cmacs.Editor1=), so external processes and bacon scripts
can control the compositor without elisp:

#+begin_example
cmacsgi GowlListClients '{}'
cmacsgi GowlSpawn '{"command": "foot"}'
cmacsgi GowlAddKeybind '{"key": "Mod4+Return", "action": 1, "arg": "foot"}'
cmacsgi GowlSetMfact '{"mfact": 0.55}'
cmacsgi GowlViewTags '{"tagmask": 3}'
#+end_example

Or via D-Bus:

#+begin_example
gdbus call --session --dest org.cmacs.Editor.Pid$(pidof emacs) \
  --object-path /org/cmacs/Editor \
  --method org.cmacs.Editor1.GowlListClients
#+end_example

** Org-Ex Interactive Widgets (=--with-cmacs-org-ex=)

Embed interactive widgets---GTK controls, web views, buffer windows,
and code evaluation results---directly inside Org mode buffers.

- Activate with =#+ORGEX: t= file keyword or =M-x cmacs-org-ex-mode=
- Widget types: =slider= (GTK), =web= (WebKit), =buffer= (file embed), =elisp= / =crispy= / =bacon= (code evaluation)
- Reactive binding: =:bind= links widgets to =#+PROPERTY:= lines
- Pub/sub channels: =:publish= / =:subscribe= for widget-to-widget messaging
- Export: HTML (live widgets), text (fallback descriptions)
- State persistence: ephemeral widget state saved to =.org-ex-state= sidecar
- Tablet ink: =#+BEGIN_INK= canvas blocks + per-line marginalia
  + region overlay ink (=cmacs-ink-mode=,
  =C-c i c= / =C-c i a= / =C-c i r=).  Pen, eraser, and pressure
  read directly from =GdkDeviceTool= / =GDK_AXIS_PRESSURE= --
  works out of the box with Wacom under Wayland.  *Requires
  =--with-rsvg=* (librsvg2): rendered canvases are inline
  =(image :type svg)= overlays.  Region overlay ink (=C-c i r=)
  goes a step further: it paints transparent stroke layers /on
  top of live buffer text/ via a post-glyph Cairo hook into
  pgtk's redisplay-finish path -- underlying text remains live
  and editable, strokes scroll with it.  Annotations persist
  inline in the file for org buffers (folded =* cmacs-ink
  :noexport:= section) and as a pretty-printed
  =<source>.cmacs-ink= sidecar for everything else --- both
  formats are git-diff-friendly (one stroke per line).

Architecture: =liborgex-1.0.so= shared library (GObject-native, GI-introspectable)
with a thin DEFUN bridge (20 primitives) and Elisp layer.

#+begin_example
#+BEGIN_WIDGET slider
:min 0
:max 100
:value 50
:bind temperature
#+END_WIDGET
#+end_example

** MCP Server (=--with-cmacs-mcp=)

Embed an MCP (Model Context Protocol) server in Emacs for AI-native
runtime control.  Uses =mcp-glib= (bundled from =deps/mcp-glib=) to
expose Emacs internals as MCP tools, resources, and prompts.

- Tools: =eval=, =buffers=, =windows=, =input=, =processes=, =debugging=, =GI=, =gowl=
- Resources: =buffer://=, =file://=, =variable://= URIs for live Emacs state
- Prompts: prebuilt prompt templates for common editor interactions
- Transport: =cmacs-mcp= shim binary connects via Unix socket for stdio transport
- Dependencies: =json-glib-1.0=, =libsoup-3.0=, =libdex-1=

** LibreClaw Chat/Matrix Integration (=--with-cmacs-libreclaw=)

Embed [[https://gitlab.com/zachpodbielniak/libreclaw][libreclaw]]
(=liblc-1.0=) — a GObject-native AI agent gateway — as a cmacs
subsystem.  Each "room" surfaces as an org-mode buffer,
ellama-style: a single read-only history section followed by an
editable =* Compose= region where =C-c C-c= sends and =RET= stays
free for multi-line drafting (source blocks, tables, links,
attachments).

*One-command entry point:*

#+begin_example
M-x cmacs-libreclaw-open
#+end_example

=cmacs-libreclaw-open= detects your current project (via
=project-current= / =vc-root-dir= / =.git=), opens a dedicated
chat buffer for that project root, auto-starts libreclaw, and
auto-generates a default config on first run.  *Each project gets
its own persistent buffer* with its own AI session — open one in
=~/Documents/notes=, a separate one in
=~/source/projects/cmacs=, and libreclaw keeps the two
conversations fully separated across Emacs restarts.

- *Cmacs channel* (recommended default): native in-process
  =LcCmacsChannel= that lets the Emacs host drive multi-room chat
  with no credentials, no sockets, and no sub-processes.  Per-project
  buffer history is persisted at
  =~/.libreclaw/cmacs-sessions/<sha>.org= and the libreclaw session
  manager keeps the AI's rolling context under the key
  =cmacs:<project-root>:<user>=.
- Other channels: Matrix (libsoup3), Email (libetpan IMAP/SMTP),
  Webhook (HTTP receiver).  Local stdin/stdout channel is also
  available but is only useful for the standalone =libreclaw= CLI.
- Shared podomation: libreclaw's =LcPodomation= attaches to cmacs's
  existing =PodEngine= via =lc_podomation_new_with_engine()= (new in
  libreclaw 0.18.0) so there's one engine for the whole process
- Embed mode: =lc_app_new_embedded= attaches all event sources to
  cmacs's GMainContext without owning a GMainLoop, so Emacs's
  pselect-based loop drives everything
- YAML config: specify via =cmacs-libreclaw-config-file=; secrets
  (Matrix tokens, email passwords) flow through =auth-source=
- Hatch wizard: =M-x cmacs-libreclaw-hatch= scaffolds a new
  workspace from inside an org buffer in REPL-style (type answer,
  press =C-c C-c=, next question appears), driving libreclaw's
  =lc_hatch_*= library API step-by-step
- GI: libreclaw ships =Lc-1.0.gir= / =typelib= by default as of 0.18.0,
  so =(gi-require "Lc" "1.0")= works for scripting access
- Podomation bridge module (=cmacs_libreclaw=) emits =on_cm_lc_*=
  events and supports a =send_message= handler action, so DSL rules
  can react to chat traffic alongside normal Emacs events
- Dependencies: =libsoup-3.0=, =json-glib-1.0=, =libcmark=, =sqlite3=,
  =libetpan=, =libpq=, =yaml-0.1=

** AI Coding Agent (=--with-cmacs-ai=)

Wrap [[https://gitlab.com/zachpodbielniak/ai-glib][ai-glib]] —
the multi-provider GObject-based AI library — as a first-class
coding-agent surface.  Independent of libreclaw: where libreclaw
orchestrates conversations across channels, =cmacs-ai= is raw,
low-latency, single-conversation model invocation tuned for code
editing.

- Nine providers via one DEFUN: =claude=, =openai=, =gemini=,
  =grok=, =ollama=, =claude-code=, =opencode=, =claude-tmux=,
  =grok-build=
- Streaming chat buffers in =cmacs-ai-chat-mode= (derived from
  org-mode) with the same read-only history + =* Compose= sentinel
  pattern as libreclaw
- *Agentic harness* in =cmacs-ai-harness-mode= (=M-x cmacs-ai-harness=,
  =-with-provider=, =-with-provider-in-directory=): ai-glib's transcript
  layer rendered natively, so tool calls arrive grouped and summarised by
  the library rather than as a wall of JSON.  Slash commands and =@path=
  mentions complete from the same files =claude= and =opencode= already
  read on disk.  =C-c C-c= sends, =C-c C-k= cancels or clears, =C-c C-g=
  writes the prompt in a dedicated buffer, =C-c C-e= / =C-c E= export
  the session as org / markdown.  Distinct from a chat buffer: the
  transcript is a *rendered view* the library owns, not an Org document —
  which is why exporting to org exists here at all.  See
  [[file:doc_org/cmacs/cmacs-ai-harness.org][the manual]].
- Region commands: =cmacs-ai-rewrite-region=,
  =cmacs-ai-explain-region=, =cmacs-ai-doc-region=,
  =cmacs-ai-test-region=, =cmacs-ai-suggest-commit-message=
- Inline FIM ghost-text completion (=cmacs-ai-completion-mode=,
  CLI provider by default for cost control)
- Voice loop: =M-x cmacs-ai-voice-chat= chains whisper-in / ai /
  piper-out for full hold-to-talk coding
- Project-aware agent: =M-x cmacs-ai-agent-open= auto-attaches
  =CLAUDE.md= / =AGENTS.md= as the system prompt
- Tool use via ai-glib's built-in =AiToolExecutor= (bash, read,
  write, edit, glob, grep, web_fetch); custom Elisp tools via
  =cmacs-ai-tools-register=
- MCP bridge: every chat buffer auto-wires cmacs's own MCP tool
  surface (buffer / file / project / eval / apropos / describe by
  default) as additional ai-glib tool callbacks, so the model can
  drive cmacs natively -- edits land in buffers (undoable),
  searches use cmacs project boundaries, introspection uses
  Emacs's own =apropos= / =describe-function=.  Symmetric to the
  outbound =ai_*= MCP tools that let external agents drive cmacs.
- =#+BEGIN_SRC ai= org-babel backend
- GObject Introspection: =AiGlib-1.0.typelib= auto-prepended to
  GIRepository's search path so =(gi-require "AiGlib" "1.0")= and
  the bacon =cmacsgi= builtin Just Work
- MCP tools: =ai_prompt=, =ai_list_providers=, =ai_open_chat= for
  outer agents to drive the in-editor AI
- Canonical artifact: =libai-glib-1.0.a= is built once from
  =deps/ai-glib= and shared with libreclaw via an =AI_GLIB_DIR=
  override (no duplicate copy linked)
- Dependencies: =libsoup-3.0=, =json-glib-1.0= (yaml-glib is
  vendored inside ai-glib; not embedded in its static archive)

** Print to cmacs (=--with-cmacs-print=)

OneNote-style "Print to cmacs" virtual printer.  Print from any
application (Firefox, Evince, LibreOffice, …); the job arrives in
cmacs as an annotatable multi-page org document with each PDF page
rendered as an inline image.  Annotation rides on the existing
=cmacs-ink-region= overlay system and the user's Doom annotation
plugins (=pdf-tools=, =org-noter=, =org-remark=, =org-roam=).

*Two install modes (pick one), then a drainer (always):*

#+begin_example
# System mode — writes to /usr/lib/cups/backend/, prompts sudo
make install-cmacs-printer

# Per-user mode — no sudo, no /usr writes, works on immutable
# systems (Silverblue / Atomic / NixOS / Bazzite / Bluefin / …).
# Uses ippeveprinter + a systemd user service; cups-browsed
# auto-creates a CUPS queue named "cmacs" via mDNS discovery.
make install-cmacs-printer-user

# Editor-independent drainer (per-user systemd path+service,
# no sudo).  Required: this is what picks up the print job from the
# spool dir and rasterises it, with no interactive cmacs needed.
make install-cmacs-print-watcher
#+end_example

The system-mode installer auto-detects immutable =/usr= (via
=/run/ostree-booted= or a non-writable =/usr=) and redirects you to
the per-user mode with a one-line message, so running the wrong one
does not break anything.

*Usage:*

- Print from any application — pick =cmacs= as the printer.
- Or programmatically: =M-x cmacs-print-import-pdf-interactive=.
- Or from the shell:
  =gdbus call --session --dest=org.cmacs.Editor1
  --object-path=/org/cmacs/Editor
  --method=org.cmacs.Editor1.Eval
  '(cmacs-print-import-pdf "/tmp/foo.pdf")'=

*Output:* flat layout under =~/Documents/notes/03_resources/cmacs-print/=:

#+begin_example
20260502-142300-receipt/
  index.org                      # generated org with inline page images
  source.pdf                     # full copy of the original PDF
  page-001.png                   # one PNG per page
  page-002.png
inbox/                           # legacy cmacs-down fallback
#+end_example

(One self-contained directory per print job — copy/move it anywhere
and the org links keep working.)

*Configuration* (defcustoms in =cmacs-print.el=):

- =cmacs-print-output-formats= — list of =org=, =pdf=, or both
  (default both — keeps the PDF available for =org-noter=).  Set
  to ='(org)= for org-only, ='(pdf)= to skip rasterisation entirely.
- =cmacs-print-target-dir= — output directory.
- =cmacs-print-dpi= — rasterisation density (default =150=).
- =cmacs-print-max-pages= — guard against runaway PDFs.
- =cmacs-print-auto-open= — open the doc on import.

*Annotation:* with =cmacs-ink-mode= active, mark a region around any
=* Page N= heading and press =C-c i r= to draw transparent overlay
strokes on top of the rendered page image (anchored to buffer
markers, persisted inline as =#+BEGIN_INK_REGION= blocks).
=org-remark= keeps text-anchored highlights and notes; =org-noter=
pairs the org doc with the sibling =.pdf= for side-by-side reading.

*Dependencies:* =poppler-utils= (Fedora/Debian/Arch) for =pdftocairo=
and =pdfinfo=, =glib2= / =libglib2.0-bin= for =gdbus=, =cups= for
the print spooler.  =install-deps= picks them up.

** Step by Step

*** 1. Clone with Submodules

#+begin_src bash
git clone --recursive git@git-ssh.podbielniak.com:zachpodbielniak/cmacs.git
cd cmacs
#+end_src

If you already cloned without =--recursive=:

#+begin_src bash
git submodule update --init --recursive
#+end_src

*** 2. Install Dependencies

The =install-deps= script auto-detects your platform and handles
everything:

#+begin_src bash
# Install all dependencies (system packages + build deps from source)
./install-deps

# System packages only
./install-deps --system

# Build crispy/bacon/gowl from deps/ only
./install-deps --from-source

# List what would be installed (dry run)
./install-deps --list

# Set up /usr/local/lib64 in ldconfig (Linux, needed after from-source)
sudo ./install-deps --ldconfig
#+end_src

Supported platforms: Fedora/RHEL, Ubuntu/Debian, Arch Linux, macOS
(Homebrew), FreeBSD.

On Fedora Silverblue or other immutable systems, install inside a
distrobox:

#+begin_src bash
distrobox enter dev
./install-deps
#+end_src

** Android APK (containerized, Doom Emacs embedded)

CMacs ships a containerized Android APK build pipeline.  The host
needs only =podman= (or =docker=); the JDK, Android SDK, NDK, and
build-tools live inside the container image.

The APK is *stock GNU Emacs* — none of the cmacs C subsystems
(gowl, bacon, libreclaw, podomation, mcp, org-ex) cross-compile to
the Android NDK.  What the APK *does* embed is the host user's Doom
Emacs configuration: =~/.config/emacs= (Doom core) and
=~/.config/doom= (private layer) are bundled as Android assets and
seeded into the app's =$HOME= on first launch.

There are two ways to build:

- =just android-repack= (recommended) — downloads upstream Po Lu's
  prebuilt APK from SourceForge, injects our Doom bundle, resigns,
  done.  Works on devices where from-source builds crash (notably
  Samsung Fold 5 / Android 16, which trips a libhwui mutex bug
  we couldn't isolate).
- =just android-build= — cross-compile Emacs from source.  Slower,
  works on most devices, lets you hack on Emacs C internals.

#+begin_src bash
# One-time: build the Fedora + JDK 21 + Android SDK 36 + NDK r28
# container image (~4 GB, ~10 min the first time).
just android-image

# Recommended: repack upstream's prebuilt APK with our Doom bundle.
# ~30 s, output in build/android-out/.
just android-repack

# Alternative: build Emacs from source.
just android-build

# Install onto a connected device:
just android-deviceinstall
#+end_src

Override the bundled config locations or target ABI via env vars:

#+begin_src bash
# Embed a different Doom checkout
CMACS_DOOM_CORE=/path/to/.config/emacs \
CMACS_DOOM_PRIVATE=/path/to/.config/doom \
just android-build

# 64-bit x86 emulator instead of aarch64 phone:
CMACS_ANDROID_ABI=x86_64 just android-build
#+end_src

On-device first launch: =M-x doom-sync= once (network required) to
install Doom's packages into the seeded =~/.config/emacs/.local/=.
The shim at =lisp/site-start.el= handles the seeding; subsequent
launches skip it and never overwrite on-device edits.  Native
compilation is disabled (no =libgccjit= for the NDK), so Doom runs
on byte-code.

See =Containerfile.android=, =build-aux/android-build.sh=, and the
=[android]= recipe group in the =Justfile= for the full pipeline.

** IPC Design

The bacon shell's =cmacsgi= builtin communicates with CMacs over a
socketpair using length-prefixed JSON messages:

1. Child (bacon) sends: =4-byte big-endian length + JSON payload=
2. Parent (CMacs) reads non-blocking into a =GByteArray= accumulator
3. Complete messages are parsed and queued in a =GQueue=
4. Dispatch happens via GLib idle callbacks (one request per iteration)
5. Response is written back as length-prefixed JSON

This design prevents IPC deadlocks — the parent never blocks on reads,
and dispatch interleaves with the GLib event loop.

The same methods are also available over D-Bus (=org.cmacs.Editor1=)
for external process access.

** Static Linking

When building with bundled dependencies (the default), crispy, bacon,
and gowl are statically linked into the emacs binary using
=--whole-archive=.  This avoids runtime library path issues and makes
the binary self-contained.

* Key Differences from GNU Emacs

- GLib =GMainContext= integrated into the Emacs event loop
- GObject ↔ elisp bridge (wrap/unwrap arbitrary GObjects)
- GObject Introspection: call any GI library from elisp or C
- Embedded C scripting via Crispy
- Embedded GLib-native shell via Bacon
- Embedded Wayland compositor via Gowl
- D-Bus service (=org.cmacs.Editor1=) for external control
- All features accessible from C/GI without elisp knowledge

* Source Layout

- =cmacs/glib/= — GLib core, GObject bridge, GClosure, D-Bus service, eval dispatch
- =cmacs/gi/= — GObject Introspection bridge
- =cmacs/crispy/= — Crispy integration
- =cmacs/bacon/= — Bacon shell, IPC, bacon modules (GI transport, etc.)
- =cmacs/gowl/= — Gowl compositor integration
- =deps/crispy/= — Crispy submodule
- =deps/bacon/= — Bacon submodule
- =deps/gowl/= — Gowl submodule
- =install-deps= — multi-platform dependency installer
