* Definitions

An agent is a markdown file with YAML frontmatter: metadata above, the system
prompt below.

#+begin_example
---
name: researcher
description: Deep research across notes and the web; produces a cited brief.
model: claude/claude-sonnet-4-6
fallback-model: ollama/gpt-oss:20b
tools: [memory, web_search, project_read_file]
isolation: none
worker: inproc
budget-usd: 0.50
max-turns: 40
emits: [brief]
---
You are a research analyst working inside the user's own editor...
#+end_example

Not org, even though everything else here is. Agent definitions would otherwise
be indexed as part of the notes corpus and retrieved as knowledge, so a question
about research methodology would surface the researcher's own prompt. Not a
=defcustom= either: the body is prose, and prose in a customization string is
miserable to edit and diffs badly.

Markdown with frontmatter is also the interop surface — =worker: claude-code=
hands the file to an external CLI more or less verbatim, and the same format
already sits in =~/.claude/agents=.

A file with *no* frontmatter still parses, taking its name from the filename.
That is what makes an existing =~/.claude/agents= directory importable rather
than something to convert.

Unrecognised keys are kept, not dropped. Whoever added one is presumably using
it.

** Search path

=cmacs-brigade-agent-path=, earliest to latest, later wins by name:

1. shipped, under =data-directory=
2. =~/.config/cmacs/brigade/agents/=
3. =~/.claude/agents/= — imported read-only
4. =<project>/.cmacs/agents/= — consulted per project, always wins

=M-x cmacs-brigade-agent-reload= rescans. A definition that fails to parse is
reported and skipped rather than aborting the scan: one malformed file should
not cost you every other agent in the directory.

** From Lisp

=cmacs-brigade-register-agent= populates the same registry, so an agent defined
in your init is referenced from a plan exactly like a file-defined one.

* Shipped agents

| Agent     | For                                                    |
|-----------+--------------------------------------------------------|
| researcher | Notes + web research producing a cited brief          |
| librarian  | Answers strictly from your own notes. Read-only       |
| critic     | Argues against a plan or a piece of work              |

* Workers

A worker decides /how/ an agent runs.

| Worker        | Runs as                                    |
|---------------+--------------------------------------------|
| =claude-code=   | a =claude --print= subprocess (the default) |
| =opencode=      | an =opencode run= subprocess               |
| =shell=         | a shell script                             |
| =inproc=        | in the editor's own process                |

Agents run *out of process* by default, and this is not a performance choice.
A =--gowl= cmacs instance /is/ the user's Wayland session: an agent that blocks
or errors inside the editor takes the desktop and every application in it.

Register your own with =cmacs-brigade-register-worker=. A worker that cannot
push its state — a detached process is reparented to init, so no =SIGCHLD= ever
arrives — supplies =:poll= instead and gets swept.

* Isolation

| Backend    | What it does                                             |
|------------+----------------------------------------------------------|
| =none=       | runs in place; safety comes from the allowlist alone     |
| =worktree=   | a git worktree, outside the repository                   |
| =podman=     | a container with no network                              |

Worktrees go *outside* the repo being worked on. One under the repo is walked by
every other agent's =rg= and =find=, which turns every search into duplicate
hits across sibling checkouts and quietly degrades everything.

Teardown forces removal, because an agent's worktree is dirty by definition —
that is what it is for — and =git worktree remove= refuses a dirty checkout.
Every teardown tolerates being called twice and being called after a prepare
that failed halfway: it runs from an unwind path, which is exactly when the
state is least predictable.

=none= is not a default anywhere, and should not be one in an agent you write.
It is only as strong as the allowlist.

* Budgets

Ceilings, not guidance. An agent that reaches one stops.

Both levels are enforced: an agent's own budget catches one runaway, and the
brigade's shared budget catches fifty well-behaved agents that add up to too
much. Neither subsumes the other.

Cost is carried in integer micro-dollars because it is summed across thousands
of turns, and floating point drift in the one figure a limit acts on would be
the worst possible place for it. A model with no price is reported as
*unpriced*, never as free — the two are indistinguishable once summed.


** Budgets and what zero means

A budget of =0.00= means /no ceiling/, not a zero-dollar cap. That follows ai-glib's =AiBudget=, where every limit is tested only when it is greater than zero — so a zero token, turn or wall-clock limit is likewise unlimited. =cmacs-brigade-default-budget-usd= is =0.00=, so an agent that does not name a budget is uncapped.

Be aware that nothing enforces the number yet on the worker paths cmacs ships. =cmacs-brigade-run= spawns =claude-code=, =opencode= or a shell as a subprocess, and a subprocess spends what it spends; the =AiBudget= ceiling lives in ai-glib's in-process agent runtime, which the Elisp runner does not drive. The value is carried on the definition and reported, but it does not stop a run, and the =over-budget= state is currently unreachable.

* Tool access

Each agent gets a freshly minted random token and a 0600 =.mcp.json= under
=XDG_RUNTIME_DIR=, naming =emacs --mcp-relay= with the agent's expanded
allowlist. See [[file:extending.org][Extending the brigade]] for how the allowlist is evaluated.

The token is never derived from the agent's name or id. Agents quote their own
context into prompts and logs constantly, so a secret derived from something
they know about themselves is a secret by construction only.

* When they are loaded

The definitions on `cmacs-brigade-agent-path' are read once when the brigade loads, so a stock plan naming =researcher= works with no setup. After editing or adding a definition, press =A= in the dashboard or run =M-x cmacs-brigade-agent-reload=.

A malformed definition is reported and skipped rather than aborting the load, so one bad file cannot stop cmacs from starting or hide the other agents.

* Workers

A worker decides /how/ an agent runs. Five ship, and all five are registered through the public =cmacs-brigade-register-worker=, so one you register yourself is reached by exactly the same path.

| Worker | What it does | Continues a conversation? |
|--------+--------------+---------------------------|
| =inproc= | runs the tool loop inside cmacs against the provider's HTTP API (the default) | yes, by keeping the session |
| =claude-code= | drives the =claude= CLI in =--print= mode | yes, via =--resume= |
| =opencode= | drives the =opencode= CLI | yes, via =--session= |
| =codex= | drives OpenAI's =codex= CLI as =codex exec --json= | yes, via =codex exec resume= |
| =shell= | pipes the prompt to bash; mostly for testing | no |

*** Codex

The =codex= worker differs from the other two CLIs in three ways worth
knowing.

=cmacs-brigade-codex-program= names the binary (default =codex=), and
=CODEX_PATH= overrides it, matching what ai-glib does for the same
provider.

It runs under a real *sandbox* rather than a skipped prompt.
=cmacs-brigade-codex-sandbox= (default =workspace-write=) is passed as
=--sandbox=, and codex enforces it: a run that tries to write outside
the workspace fails rather than asking. claude's
=--dangerously-skip-permissions= removes a prompt; this is a boundary.

Its tools arrive through a *=CODEX_HOME= overlay*, not a config flag.
Codex reads MCP servers from =CODEX_HOME/config.toml= and has no
=--mcp-config=, so the worker builds a directory holding just that file
— the user's own config first, our =[mcp_servers.cmacs-brigade]= table
appended — and symlinks every other entry of the real Codex home into
it, =auth.json= above all. Writing into =~/.codex/config.toml= was not
an option: it is the user's, agents run concurrently, and a crash would
leave a server declared there for every later codex run. The overlay
lives in =cmacs-brigade-runtime-dir=, not the shared temp directory,
because codex refuses to create its PATH helpers under one.

It reports as *JSONL*, not one object. =codex exec --json= streams an
event per line, so the worker reads =thread.started= for the session id,
the last =agent_message= item for the reply and =turn.completed= for
usage. Codex reports no cost, so the budget sees tokens and zero dollars
rather than a figure invented from a price list.

The last column is the worker's =:supports-session= flag, and it is what
=agent_send= checks. Sending to a =shell= task is refused rather than re-running
bash with the follow-up as though it were a first prompt: that produces a
process which has never seen the first message, and presenting it as a
continuation would be a lie the caller cannot detect. See [[file:mailbox.org][Mailboxes]].

*You rarely name a worker.* It is resolved in this order: an explicit =worker:= in the definition, then the worker implied by the model's provider (=claude-code/=, =opencode/= and =codex-cli/= pick their own CLI), then =cmacs-brigade-worker=. An HTTP provider — including one of your own from =cmacs-ai-openai-compatible-endpoints=, as =my-vllm/qwen3= — implies nothing and stays on =inproc=, which is what gives it the full tool loop. Running a CLI provider through the in-process loop would silently drop every tool — the CLI clients ignore the tools argument and take them over MCP — so the provider gets to decide.

=inproc= is the default because it is the one that honours =:MODEL:= and the tool allowlist directly: the executor is built from the allowlist, so the agent cannot name a tool that was not installed.

** Running a local model through a CLI worker

=claude-code= and =claude-tmux= accept a model spelled =ollama/NAME= and run it through Ollama as the transport instead of Anthropic: the command becomes =ollama launch claude --model NAME --= followed by the usual claude arguments, and claude's own =--model= is omitted because Ollama supplies it. So a model of

: model: claude-code/ollama/qwen3.5:9b

gets you the claude-code harness driving a model that never leaves the machine. The first component picks the cmacs provider; everything after it is the model string that provider receives, which is why the =ollama/= ai-glib looks for survives intact.

Both worker paths build that command, and they have to agree: =inproc= gets it from ai-glib (=ai-claude-launch.c=), and the subprocess worker builds the same argv itself, since it spawns the CLI directly and never goes through ai-glib. Verify either with =ai -p claude-code -m ollama/NAME --dry-run "hi"=.

Two things this is *not*. =ollama/qwen3.5:9b= with no CLI prefix is the plain Ollama provider talking HTTP to the server — no CLI involved, and it resolves to the =inproc= worker. And =opencode/ollama/NAME= is opencode's own =vendor/model= spelling, passed through untouched; opencode has no launcher indirection.

The claude CLI must still be installed. =OLLAMA_PATH= overrides the launcher binary, and =cmacs-brigade-ollama-program= is the =defcustom= behind it.

The loop runs on a worker thread with its *own* =GMainContext=, reporting back through the dispatch callback registry, so the editor is not blocked — which matters more than usual under =--gowl=, where the editor is the compositor.

The private context is load-bearing, not an optimisation. Without one the loop binds to the process-global default context — the one Emacs itself iterates from =xg_select= — and so does the provider's libsoup I/O. The main thread then wins the race to own that context, dispatches the HTTP completions and runs the model's tool calls itself, while the worker sits in =g_main_context_wait_internal= waiting for a context it will never get. A =bash= tool running a build blocked the whole editor for twenty minutes that way.

An Elisp tool cannot run on that worker at all — Emacs's allocator is not thread-safe, so =build_string= and every =Lisp_Object= have to happen on the main thread. The call is marshalled there and waited for, bounded by =cmacs-ai-tool-call-timeout= (120s) so a wedged main thread costs one tool call rather than the worker.

*** Where the tools run

An =inproc= agent's built-in tools — =bash=, =read=, =write=, =edit=, =glob=, =grep=, =ls= — resolve relative paths against the task's directory and run commands there. That is the task's =:CWD:= property, which =agent_spawn= records from wherever the spawn came from, and which =worktree= and =podman= isolation set to the sandbox they prepared.

Without it they use whatever directory Emacs is in, which is wherever you last visited a file — so an agent told to work in one tree read, wrote and built in another.

#+begin_src elisp
;; the same knob, for a one-shot call
(cmacs-ai-call "what is in this project?"
               :builtin-tools t
               :directory "~/src/project")
#+end_src

The CLI workers get their tools over MCP instead, through a scoped =.mcp.json= — see [[file:mcp.org][MCP]].

** Registering your own

#+begin_src elisp
(cmacs-brigade-register-worker
 :name 'my-runner
 :description "Run the agent on the build box."
 :start (lambda (task-id agent prompt cwd env endpoint)
          ;; return a plist describing the run; it is merged into the
          ;; runtime entry and handed back to :cancel
          (list :ssh-job (my/dispatch-remote agent prompt)))
 :cancel (lambda (task-id run)
           (my/kill-remote (plist-get run :ssh-job))))
#+end_src

Call `cmacs-brigade--finish' with the task id, a final state and the output when the run ends. An unknown worker fails the task with a message naming the ones that are registered, rather than erroring somewhere further down.

* Writing one

#+begin_src elisp
M-x cmacs-brigade-new-agent        ; or N in the dashboard
#+end_src

Writes a commented skeleton into the first writable directory on =cmacs-brigade-agent-path= and opens it. Save, then =A= in the dashboard to load it.

The format is markdown with YAML frontmatter because that is the interop surface — =worker: claude-code= hands the same file to an external CLI verbatim — but it is not guessable, which is what the skeleton is for. =M-x cmacs-brigade-list-tools= (=T= in the dashboard) shows every tool and its group, for the =tools:= list.

* Choosing a model at spawn time

An agent's model is whatever its definition says, and a spawn can override it:

| Tool | What it does |
|------+--------------|
| =agent_providers= | providers this cmacs can reach, and whether each is HTTP or a CLI |
| =agent_models= | models a provider offers, already formatted as =provider/model= |

=agent_spawn= takes an optional =model=; omitted, the agent's own is used. The override is written as =:MODEL:= on the spawned task, so it is visible in the plan, editable, and survives a restart exactly like a hand-written one.

The same two lookups are on every surface:

#+begin_src sh
emacsctl brigade providers
emacsctl brigade models claude-code
emacsctl brigade spawn "survey deps/" researcher "" claude-code/opus
#+end_src

and on D-Bus as =Providers=, =Models= and =Spawn='s fourth argument.

* The default agent

An unqualified spawn uses =general=, a neutral agent that ships with cmacs on =claude-code/sonnet=. =cmacs-brigade-subagent-default-agent= names it.

It is named rather than inferred on purpose. The fallback used to be whichever agent sorted first, so on a machine with =~/.claude/agents= every unqualified spawn silently inherited a code reviewer's system prompt — the spawn worked, the result was subtly wrong, and nothing said why.

* Where a spawned agent runs

The directory the spawn came from, recorded as =:CWD:= on the task when it is created.

Captured at spawn time rather than read at start time, because by the time a task starts the current buffer is whatever the main loop happens to be in — so a spawn from a chat in one project would run in whichever project the editor was last sitting in. A =worktree= or =podman= agent still gets the directory its sandbox decides.
