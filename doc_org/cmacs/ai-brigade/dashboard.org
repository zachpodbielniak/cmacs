* Getting a task without knowing the format

Writing a task by hand means knowing that a plan is an org file, where plans
live, which properties mean what, and that =:MODEL:= is spelled
=provider/model=. That is a lot to know before you can ask an agent to do
something. Four keys skip all of it, and every one of them ends in the same
transient so you get a look at the task before it exists.

** =n= — describe it

Opens a small window at the bottom of the frame. Write what you want done, in
as many lines as it takes, then =C-c C-c=. What you wrote goes to a model
(=claude-code/sonnet= by default, see =cmacs-brigade-compose-author-provider=
and =-author-model=), which proposes the whole spec — title, prompt, agent,
provider, model, tools, budget, working directory — and the transient opens
already filled in.

Nothing is created by that call. The model's proposal is a *draft*: names it
invented for agents, tools or providers are dropped before you ever see them,
and you still have to press =RET=.

Set =cmacs-brigade-compose-entry= to =minibuffer= for a one-line prompt
instead of the window.

*** What gets read out of what you said

Provider, model and agent are picked out of the request /before/ any model sees
it, and they win over whatever the draft proposes. These three are stated
rather than inferred, and matching them against the providers, model lists and
agent registry that actually exist is exact, instant, and cannot invent a name.
It also means they survive a drafting call that fails, times out, or is not
possible in this build.

| You said                                            | Read as                        |
|-----------------------------------------------------+--------------------------------|
| =use grok to survey my notes=                         | provider =grok=                  |
| =with claude-code sonnet, refactor the keybinds=      | provider =claude-code=, model =sonnet= |
| =have the researcher agent look at this=              | agent =researcher=               |
| =using grok-4.5 write a summary=                      | provider =grok=, model =grok-4.5=  |
| =summarise the gemini pricing page=                   | nothing — a mention is not a choice |

A name counts as chosen when something introduces it — a cue word (=use=,
=with=, =via=, =run=, =using=, …), a qualifier (=agent=, =model=, =provider=),
or both — or when a qualifier follows it. So all of these read:

#+begin_example
run pwd with sonnet                     model  sonnet
run pwd with the sonnet model           model  sonnet
run pwd on claude-code, model sonnet    claude-code / sonnet
use the researcher agent to look at X   agent  researcher
use agent researcher for this           agent  researcher
have researcher do this                 agent  researcher
#+end_example

A bare mention never counts. Without that rule any mention matched, and asking about a
vendor's pricing page silently routed the task to that vendor.

Whatever is read out is also *removed from the prompt*. "Run the command pwd
with Grok" is an instruction plus a routing decision, and only the first
belongs in the brief — passing the second on asks grok to do something about
grok, which it reasonably finds confusing:

| You said                                        | Prompt the agent gets            |
|-------------------------------------------------+----------------------------------|
| =i need you to run the command PWD with Grok=     | i need you to run the command PWD |
| =use grok to survey my notes=                     | survey my notes                  |
| =with claude-code sonnet, refactor the table=     | refactor the table               |
| =run the command pwd with grok and report back=   | run the command pwd and report back |
| =summarise the gemini pricing page=               | unchanged — nothing was read out |
| =with grok, summarise the grok pricing page=      | summarise the grok pricing page  |

The removal is driven by the same rule as the extraction, so it can only ever
take out what became a field. The last row is the case that shows it: the
first =grok= was a choice and the second is the subject, and only the choice
goes. The drafted path is cleaned too — the model is told to leave the routing
out of the brief, and regularly does not.

The two halves are deliberately not equally eager. Extraction may over-read —
=compare the sonnet model documentation= will set the model field, because
"the sonnet model" is exactly the shape of a choice — and that is visible in
the menu and one key to clear. The prompt is the half that must not be damaged,
so it only loses a phrase that was *introduced* as a choice; that sentence
reaches the agent exactly as written. A request that is nothing but routing
(=use grok, model grok-4.5=) keeps its text rather than being stripped to
nothing, which would leave the menu refusing to create anything with no hint
why.

*** Titles

The headline is a short label, never the instruction restated — a task list
where every row is the whole prompt is one you cannot scan. The choices are
stripped out of it (they are fields now), as is the polite opening:

| Request                                                    | Title                       |
|------------------------------------------------------------+-----------------------------|
| =use grok to survey my notes for the infinity fund=          | Survey my notes for the infinity fund |
| =have the general agent clean up the queue, then report=     | Clean up the queue          |
| =please can you go through the inbox and flag anything urgent= | Go through the inbox and flag anything urgent |

A title the model proposes is used only if it is genuinely shorter than the
prompt and not a prefix of it; otherwise one is derived. Models restate the
instruction as the title constantly.

*** When the draft comes back the wrong shape

It usually does, and that is handled rather than argued with. Asked to
*describe* a task, claude-code answered with an =agent_spawn=-shaped object —
=action=, =task= — and once put a slug (=survey_notes_for_infinity_fund=) under
=task= with the real brief under =objective=. So the parser accepts the aliases
models actually use and picks the most prose-like value for each field, and a
prompt that is a bare identifier, or shorter than the request it was meant to
expand, is refused in favour of what you typed.

The CLI author also runs in an empty scratch directory. Started inside a
project it picks up that project's =.mcp.json=, sees the brigade tools, and
answers a request to describe a task by spawning one — which it did, twice,
before this. An empty directory removes the temptation rather than arguing
with it.

*** Telling the conversation when it is done

=N= picks a conversation to notify when the task finishes. A chat that spawns
a subagent otherwise sits parked: =agent_spawn= returns an id immediately (a
blocking spawn holds a turn open for minutes), the work finishes, nothing says
so, and it waits for you to come back and type "is it done yet".

With a target set, the finished run delivers a turn into that conversation —

#+begin_example
[automatic] Subagent a17 (researcher) has finished with state `done'.
Call agent_result with id "a17" to collect what it produced, then carry
on with what you were doing.
#+end_example

— and the model picks it up and continues on its own. A spawn made *from* a
conversation records that conversation automatically, so =N= is only needed for
a task you started by hand. It defaults to none: a task you composed yourself
reports to nobody unless you say otherwise.

**** Which conversations can be told

Both of the editor's conversation surfaces, listed together in the picker:

- *cmacs-ai chat buffers* (=cmacs-ai-chat-mode=);
- *libreclaw rooms* (=cmacs-libreclaw-room-mode= and cmacs-channel rooms),
  which reach Matrix and the bridge as well, since delivery goes through the
  room's own send command rather than around it.

Neither is special-cased. Each is a =client= in the registry
(=cmacs-brigade-register-client=), so a surface of your own — another chat
front-end, a room in something not shipped here — becomes a notify target by
registering =:current=, =:targets=, =:live-p=, =:ready-p= and =:deliver=. See
[[file:extending.org][Extending the brigade]].

The two surfaces differ in one way, and it is worth knowing which you are in.
*Automatic* capture works for cmacs-ai chat because that chat layer runs its
tool loop in Elisp with the chat buffer current, so =agent_spawn= simply
notices where it is. A libreclaw agent runs its tool loop in C, with no room
buffer current, so a spawn *it* makes records no target — use =N=, or spawn
from the room buffer yourself. Delivery into a libreclaw room works either way;
it is only the noticing that does not.

It is a =:NOTIFY:= property on the task, so the target is visible in the plan,
survives a restart, and is editable like any other intent.

**** When it waits

Never mid-turn. A message inserted while a reply is streaming interleaves with
the model's own output, and one inserted while you have something half-typed in
the compose region would send your draft along with it. In both cases the
message queues and goes out when the conversation is idle
(=cmacs-brigade-loopback-retry-seconds=), or is dropped after
=cmacs-brigade-loopback-give-up-seconds= — a conversation abandoned mid-stream
for a quarter of an hour is not coming back to this. A closed chat is dropped
immediately. Each task notifies once.

Turn the whole thing off with =cmacs-brigade-loopback-enabled=, or change the
wording with =cmacs-brigade-loopback-message= — it takes the task id, the agent
name, the final state and the id again. It reports the state but not the
output: results can be long, and =agent_result= is a tool the model already
has.

**** Other clients

Delivery goes through the =client= registry, not through knowledge of chat
buffers, so anything conversational can be a target:

#+begin_src elisp
(cmacs-brigade-register-client
 :name 'matrix
 :targets (lambda () (mapcar (lambda (r) (cons (format "matrix:%s" r) r))
                             (my/joined-rooms)))
 :ready-p (lambda (_target) t)
 :deliver (lambda (target text)
            (my/matrix-send (string-remove-prefix "matrix:" target) text)))
#+end_src

A target id is =CLIENT:REST=; the prefix picks the client out of the registry
and the rest means whatever that client wants. The functions that go with it:

| Function                                | Returns                        |
|-----------------------------------------+--------------------------------|
| =cmacs-brigade-loopback-targets=          | every live target, as (ID . LABEL) |
| =cmacs-brigade-loopback-current-target=   | the target for the context you are in |
| =cmacs-brigade-loopback-deliver=          | sends TEXT, or queues it if busy |
| =cmacs-brigade-loopback-task-target=      | the target a task reports to   |

=cmacs-brigade-loopback-retry-seconds= (5) is how often a queued message
re-checks whether its target has gone idle. =:current= is the one worth
implementing if spawns should record your client automatically — it answers
"is this being called from inside you?", which is how the chat client works
without any plumbing between the two.

*** Commands and options

Every key has a command behind it, reachable with =M-x= from anywhere:

| Command                          | What it does                          |
|----------------------------------+---------------------------------------|
| =cmacs-brigade-compose=            | the transient, on whatever is composed |
| =cmacs-brigade-compose-quick=      | describe a task, draft it, then the menu |
| =cmacs-brigade-compose-voice=      | say it, draft it, then the menu       |
| =cmacs-brigade-compose-clone=      | copy an existing task into the menu   |
| =cmacs-brigade-compose-set=        | fill the menu in from your own code   |
| =cmacs-brigade-compose-read-model= | read a provider and one of its models |

| Option                                  | Default            |
|-----------------------------------------+--------------------|
| =cmacs-brigade-compose-default-agent=     | =general=            |
| =cmacs-brigade-compose-default-model=     | =claude-code/sonnet= |
| =cmacs-brigade-compose-author-provider=   | =claude-code=        |
| =cmacs-brigade-compose-author-model=      | =sonnet=             |
| =cmacs-brigade-compose-author-timeout=    | 120 seconds        |
| =cmacs-brigade-compose-entry=             | =window=             |
| =cmacs-brigade-compose-entry-height=      | 8 lines            |
| =cmacs-brigade-compose-plan-file=         | =compose.org= in the plan directory |
| =cmacs-brigade-compose-start-immediately= | nil                |

=cmacs-brigade-compose-set= is the way in for your own code: hand it a plist
with any of =:title=, =:prompt=, =:agent=, =:provider=, =:model=, =:tools=,
=:budget=, =:cwd=, =:notify= and =:plan=, and the menu opens on it.

With =cmacs-brigade-compose-start-immediately= on, =RET= means go rather than
leaving the task as a draft.

** =V= — say it

The same thing, spoken. Records until =cmacs-brigade-voice-stop=, transcribes
with whisper, drafts, and shows you the result. Also on =v n=.

It is deliberately never created straight off a transcript. Whisper is good,
but the failure mode is an agent spending real money on a misheard
instruction, and a wrong word is cheap to fix on screen.

** =C= — clone

Copies everything the task under point *said* — agent, model, tools, budget,
working directory, and the prompt itself — and none of what it *did*. The copy
gets its own id and starts as a draft, and the transient opens on it so you can
change the one thing you wanted different. That is the reason to clone rather
than re-run.

A task with per-task overrides runs under a derived agent
(=researcher@b12c7a46=); the clone carries the base name =researcher=, so the
overrides stay in the transient where you can edit them rather than frozen into
a definition belonging to the original.

** =x= — compose

The transient itself, empty. Every field shows what it is set to, and an unset
field means "whatever the agent definition says" rather than a hidden default.

#+begin_example
Compose a brigade task
 drafted from your request
 into ~/.local/state/cmacs/brigade/brigade/compose.org

 Task                      Who runs it
 p prompt   Survey the...  a agent     researcher
 T title    Survey gaps    m model     claude-code/sonnet
                           t tools     memory_search, web_search

 Where and how much        Draft
 d directory  ~/src/foo/   ! re-draft from a description
 b budget     0.50         v re-draft from your voice
 f plan file  compose.org  r reset

 Create
 RET create it   S create and start it   e create and open in the plan
#+end_example

=e= opens the brigade's settings, =q= leaves the menu and discards what was
composed, and =M-x cmacs-brigade-compose= reaches it from anywhere.

*** What it opens on

An empty menu is not much use if the first two things you do are always pick
the same agent and the same model, so it starts on them:

| Option                                | Default              |
|---------------------------------------+----------------------|
| =cmacs-brigade-compose-default-agent=   | =general=              |
| =cmacs-brigade-compose-default-model=   | =claude-code/sonnet=   |

Both are only ever fallbacks. An agent or provider named in your request,
proposed by the draft, or carried by a clone wins over them — say "use grok"
and you get grok, not the default. The model default is applied only when
*neither* a provider nor a model is already set, so naming half of one does not
silently acquire the other half from here.

Set either to nil to leave that field empty, which hands the decision back to
the agent definition. A default naming an agent that is not loaded is ignored
rather than written into a plan that would fail at start.

Note =cmacs-brigade-compose-default-model= is distinct from
=cmacs-brigade-default-model=: the latter is what an agent /definition/ falls
back to when its frontmatter names no model, this one is what the /menu/ starts
on.

** What gets written

An ordinary org headline in an ordinary plan file
(=cmacs-brigade-compose-plan-file=, =compose.org= under the plan directory by
default), adopted exactly as if you had typed it. A composed task is editable,
refilable, greppable and in git like every other one — there is no second
representation.

* It is a projection

The dashboard holds no state of its own, and its keys call exactly the functions
the org hooks call. There are two writers — org and the runtime — and three
readers. A third thing that thought it knew the answer would be a third thing to
keep in sync.

* Rendering

A full redraw on =special-mode= rather than =tabulated-list-mode=: the view is a
tree with per-row progress, which tabulated-list does badly, and
=cmacs-transcode= had already worked out how to redraw without losing the cursor.

Refresh is *event-driven with a coalescing idle timer*, never a poll. Eight
streaming agents deliver progress at tens of hertz each; redrawing per event
melts the display. A two-second heartbeat refreshes elapsed times, and nothing
redraws at all while the buffer is not visible.

* Every backend

The dashboard is text, so it works identically in a terminal, under PGTK, and
under =emacs --lrg=.

Status glyphs fall back to ASCII where Unicode cannot be displayed
(=cmacs-brigade-dashboard-unicode=, =auto= by default).

Columns are anchored with =:align-to= display properties, not laid out by
padding with spaces. That distinction is the difference between a table and a
nearly-a-table: a space is exactly one column wide, and a glyph is not
necessarily anything of the sort. =▶=, =✔= and =✖= are East-Asian-Ambiguous —
=string-width= reports one column, and a graphical frame lays them out as two
from the font's own advance. Padded rows therefore came out a column short for
exactly the states you notice, since a fresh task shows the narrow =·= and
everything else shows a wide glyph. Padding could not fix it, because the width
it would pad by is the width that is wrong.

Rows are padded /as well as/ anchored: the padding is what makes the buffer's
plain text line up when it is copied out or read by something that ignores
display properties, and the anchor is what makes the display line up when the
two disagree. Where they do, the anchor absorbs the difference.

The trap under =--lrg= is menus: =display-graphic-p= returns =t= there, so the
obvious guard passes, but lrgterm draws no menu bar. Use
=cmacs-libregnum-popup-menu=, which falls through to the native menu on PGTK.
An ERT test greps the brigade sources for =x-popup-menu=, =image-map= and
=menu-bar-*= to keep it that way.

* Panels

Sections come from =cmacs-brigade-register-panel=, so a configuration can add
its own:

#+begin_src elisp
(cmacs-brigade-register-panel
 :name 'calls :title "Recent calls" :order 20
 :render (lambda () (list "  +15551234567  2m ago")))
#+end_src

A panel that signals is caught and reported in place rather than taking the
dashboard down — the dashboard is how you would notice the panel is broken.

* How it takes the screen

By default the dashboard fills the frame, and gives your layout back when you quit with =q=. It is a wide table plus panels; in half a frame the columns wrap and it stops being glanceable.

#+begin_src elisp
(setq cmacs-brigade-dashboard-display 'full-frame)   ; default
;; or 'same-window  -- reuse the selected window, leave the rest alone
;; or 'other-window -- Emacs's default splitting behaviour
#+end_src

None of the three ever creates a window. =display-buffer-alist= still applies if you want to place it somewhere specific.

|-----+--------------|

| =K= | cancel it |
| =o= | read its transaction log — every message, reply and tool call, not just the last answer |
| =i= | send it another message; it continues the same conversation, running or long finished |
| =I= | list what is queued for it, and optionally drop one |
| =X= | close the conversation and release the session it is holding |
| =RET= | jump to its headline in the plan |

| =p= | open an existing plan |
| =a= | set the agent |
| =m= | set the provider and model |
| =b= | set the spend ceiling |
| =t= | set the tool allowlist |

| =T= | list the tools an agent can be given |

=a=, =m=, =b= and =t= write the org headline and re-adopt it. They do not poke the runtime: org owns intent, and a dashboard that could set a model the plan file did not know about would be a second source of truth.

** Setting a provider and model

=m= asks for a provider first, then a model from that provider. The two are one string on the wire (=claude/claude-sonnet-4-6=), but choosing a model without first narrowing to a provider means reading one list of everything.

The model list is completion, not a fixed set — a provider ships new model names between cmacs releases, and a closed list would make the newest model the one thing the UI cannot express. Leave the model empty to use the provider's default.

Because the runtime record carries only an agent /name/, a task that overrides the model gets a derived agent registered under =<agent>@<id>=. The dashboard shows the base name, so this is invisible unless you go looking; =cmacs-brigade-agent-base-name= is what does the unwrapping.

** Under Doom and Evil

Every key above is a single keypress in a read-only buffer, which is exactly what Evil's state maps and minor modes like =evil-snipe= would otherwise swallow — =s=, =c=, =a=, =b=, =t= and =p= are all Evil commands in normal state.

The dashboard installs its map as an Evil /intercept/ map through =cmacs-evil-setup-mode-map=, which puts it above both the state maps and minor-mode maps, and adds the mode to =evil-snipe-disabled-modes=. Keys the dashboard does not bind are untouched, so the Doom leader, =C-w= and =ESC= keep working. In vanilla Emacs it is an ordinary =special-mode= map and none of this applies.
