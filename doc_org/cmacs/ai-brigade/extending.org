* Why this document is the important one

The brigade's shipped features are a demonstration. The product is the
registration API: it should be trivial to hand the AI something of yours,
and doing so should light it up everywhere at once.

The acceptance test for the whole design is [[*Worked example: "Call For Me"][the worked example]] at the
bottom — a telephony feature cmacs deliberately does *not* implement,
built entirely from a user's own config. If anything in it required
patching cmacs, the fabric would have failed.

* One registration, three surfaces

=cmacs-brigade-deftool= registers a plain Elisp function. It immediately
becomes callable by in-process HTTP agents (as a tool on their executor),
by CLI agents such as =claude-code= and =opencode= (as an MCP tool through
the =emacs --mcp-relay= bridge, scoped by that agent's capability token),
and by external MCP clients on cmacs's own MCP server.

#+begin_src elisp
(cmacs-brigade-deftool weather-now
  "Current conditions for a place, as a short sentence."
  ((place string  "City or 'lat,lon'")
   (units string  "metric or imperial" :optional t :default "metric"))
  :group 'weather
  (my/fetch-weather place units))
#+end_src

Parameter specs are =(NAME TYPE DOC &rest KEYWORDS)=. =TYPE= is one of
=string=, =integer=, =number=, =boolean=. Keywords: =:optional=, =:default=,
=:enum=.

Tool-level keywords:

| Keyword        | Meaning                                                       |
|----------------+---------------------------------------------------------------|
| =:group=         | Allowlist vocabulary — an agent can ask for the whole group   |
| =:destructive=   | Excluded from read-only agents unless named explicitly        |
| =:confirm=       | =nil= / =ask= / =always= — gated before dispatch, via the approval handler |
| =:async=         | Body receives a =done= callback instead of returning           |
| =:timeout=       | Seconds before an async tool is failed and reaped              |

** Async tools

A phone call or a long build cannot block. With =:async t= the body is
handed a =done= function and its return value is ignored:

#+begin_src elisp
(cmacs-brigade-deftool build-and-test
  "Run the full build and test suite; returns the summary."
  ((target string "make target"))
  :async t :timeout 1800
  (my/start-build target (lambda (summary) (funcall done summary))))
#+end_src

The Lisp closure is held in cmacs's GC-rooted callback registry for the
duration, so it survives collection across the round trip.

** Programmatic registration

=cmacs-brigade-deftool= is a thin macro over =cmacs-brigade-register-tool=,
which takes a plist. Use it directly to register in a loop, from a config
file, or from crispy C.

* The registries

Every variation point is public. Shipped features consume exactly these.

| Function                                    | Extends                        |
|---------------------------------------------+--------------------------------|
| =cmacs-brigade-register-tool=                 | the tool bus                   |
| =cmacs-brigade-register-agent=                | agent registry (Lisp-side)     |
| =cmacs-brigade-register-worker=               | how an agent executes          |
| =cmacs-brigade-register-isolation=            | sandbox backends               |
| =cmacs-brigade-register-memory-source=        | what gets indexed              |
| =cmacs-brigade-register-deliverable=          | output types                   |
| =cmacs-brigade-register-panel=                | dashboard sections             |
| =cmacs-brigade-register-context-provider=     | auto-injected prompt context   |
| =cmacs-brigade-register-approval-handler=     | how confirmations are asked    |
| =cmacs-brigade-register-notifier=             | how you are told something happened |
| =cmacs-brigade-register-client=               | a conversation a finished agent can wake |

A worker also declares =:supports-session=, which says whether it can continue an
existing conversation rather than only starting a fresh one — an in-process
session handle, or a CLI that takes a session id. Without it, =agent_send= to a
task run by that worker is refused rather than re-running it with the follow-up
as though it were a first prompt.

** Observing runs

| Hook | Fires |
|------+-------|
| =cmacs-brigade-run-finished-functions= | =(TASK-ID STATE OUTPUT)= when a turn completes. Unchanged: every observer that predates conversations is wired here |
| =cmacs-brigade-turn-finished-functions= | =(TASK-ID TURN OUTPUT)= once per turn, with the turn number |
| =cmacs-brigade-mailbox-delivered-functions= | =(TASK-ID MESSAGE)= when a queued message is handed to a turn |
| =cmacs-brigade-after-tool-call-functions= | every tool call, with =:task= naming the run that made it when there is one |

Both of the first two fire for every completed turn. They differ in what they
tell you: =run-finished= gives the task's state, =turn-finished= gives the turn
number. Take the second when you care about the shape of a conversation, the
first when you care about outcomes.

Writing a tool that asks a model for structured data? =cmacs-brigade-parse-json-object=
locates the JSON object in a reply and returns it as an alist. Models wrap JSON
in prose and code fences however firmly they are asked not to, and a reply that
is 95% the right answer should not be thrown away over the other 5%.

** Memory sources

Worth calling out. A source supplies =enumerate= (return a list of item
identifiers) and =read-chunk= (return text for one), so you can index a
Postgres table, a code tree, a Zotero library or an IMAP folder into the
same vector index — and every agent's =memory_search= covers it with no
further work.

** Workers

A worker decides /how/ an agent runs: in-process, as a =claude-code=
subprocess, as a detached job, on another machine. Registering one is how
you add an execution model the brigade does not ship.

** Notifiers

A notifier is a way of getting your attention. The brigade ships six —
echo area, speech, sound, desktop notification, a shell script, and a
thermal-printed receipt — and registering a seventh is one form:

#+begin_src elisp
(cmacs-brigade-register-notifier
 :name 'pushover
 :available (lambda () (getenv "PUSHOVER_TOKEN"))
 :notify (lambda (ev)
           (my/pushover-send (plist-get ev :text)
                             :priority (if (plist-get ev :urgent) 1 0))))

(setf (alist-get 'needs-input cmacs-brigade-notify-routes)
      '(speak pushover))
#+end_src

Which notifiers fire for which events is =cmacs-brigade-notify-routes=,
so a registered notifier is inert until you route something to it. See
[[file:notifications.org][Notifications and voice]] — including the part that matters most, which
is not the notification but the summary you get when you come back.

* Subagents

Five tools let a model hand work to another model:

| Tool | What it does |
|------+--------------|
| =agent_spawn= | queue work for another agent; returns a task id immediately |
| =agent_status= | what state that task is in, with turns, tokens and cost |
| =agent_result= | collect what it produced |
| =agent_cancel= | stop it |
| =agent_list= | the agents available to spawn, and every known task |

They are asynchronous on purpose. =agent_spawn= does not wait: a blocking spawn holds a turn open for minutes, and every provider has a tool-call timeout shorter than the work is likely to take. The parent polls and collects.

Spawning is deliberately *not* named =brigade_spawn=. The allowlist refuses every =brigade_= and =ai_= name outright, so an agent cannot reach back into the orchestrator and start work outside its budget accounting; these five are the sanctioned way through that wall. They go through the same queue, concurrency cap and state machine as a task you started by hand, and a spawned task appears in =subagents.org= like any other.

=cmacs-brigade-subagent-max-depth= (2) bounds nesting: a subagent that can spawn can spawn something that spawns, and a runaway tree is expensive in a way that is not noticed until the bill.

** On every surface

One registration reaches all of them:

| Surface | How |
|---------+-----|
| in-process HTTP agents | tools on the agent's executor |
| CLI agents | over the =emacs --mcp-relay= bridge, scoped by the agent's token |
| external MCP clients | cmacs's MCP server |
| a =cmacs-ai= chat buffer | see below |
| D-Bus | =org.cmacs.Editor1.Brigade= — =Spawn=, =Status=, =Result=, =Cancel=, =List=, =Agents= |
| =emacsctl= | =emacsctl brigade spawn/status/result/cancel/list/agents= |

D-Bus and emacsctl exist because they reach a running cmacs from /outside/ it — a shell script, a systemd unit, a cron job, another machine over the emacsctl ssh tunnel — with no MCP client and no agent involved:

#+begin_src sh
emacsctl brigade spawn "survey what changed in deps/ this week" researcher
emacsctl brigade list
emacsctl brigade result <id>
#+end_src

Both route through the same tool the model calls, so a script and an agent drive the same queue, concurrency cap and state machine. Confirmation is bypassed on the D-Bus path: it exists so an /agent/ cannot start paid work unattended, and a D-Bus caller is the session owner, who already has =org.cmacs.Editor1.Eval= on the same bus. It could not work anyway — RPC evals bind =inhibit-interaction=, so a prompt inside a dispatch signals rather than asking.

** In a chat buffer

A =cmacs-ai= chat gets the =agent= and =memory= groups, so you can spawn from a conversation by hand. =cmacs-brigade-chat-tools= changes which groups, or nil for none.

That happens through =cmacs-ai-chat-executor-functions=, a hook cmacs-ai offers rather than cmacs-ai knowing about the brigade — the brigade requires cmacs-ai, and the reverse would be a cycle. Your own subsystem can add tools to every chat the same way.

** With a CLI provider

ai-glib's CLI clients ignore the tools argument entirely (=(void)tools= in the claude-code and claude-tmux clients), so tools registered on an executor do not exist as far as those models are concerned. A chat buffer on =claude-code= or =claude-tmux= is therefore given a scoped MCP config instead, which is how those agents take tools — the same mechanism the brigade uses for CLI workers. The credential is revoked when the buffer is killed.

=opencode= has no MCP config property, so a chat on it says so rather than looking tool-enabled and having none.

* Confirmation, and why it cannot prompt

Nothing asks for confirmation by default: =cmacs-brigade-auto-approve= is =t=.

=*= likewise grants everything an agent could call — =eval=, =shell=, =bash=, =execute_command=, =send_keys=, =crispy_eval=, =bacon_eval= and the C-patching tools included. Both defaults are deliberate: it is your editor and your agents, and the prompt that used to stand in front of these was unanswerable anyway on the surface that reaches them.

To put the dangerous end back behind a deliberate naming, so an agent granted =*= cannot reach it and a definition has to list each one:

#+begin_src elisp
(setq cmacs-brigade-restrict-privileged-tools t)
#+end_src

One thing stays on: =cmacs-brigade-block-recursive-tools= (t) still refuses =ai_*= and =brigade_*=. That is a different mechanism from the privileged set — those names re-enter the orchestrator, so an agent that can call them starts work outside its own budget accounting and, through =ai_call=, can recurse into itself without bound. The =agent_*= tools are the sanctioned way to hand work to another agent and are unaffected. Set it to nil to lift that too.

It is the default because the prompt was mostly unanswerable. A tool call arriving from a chat, or any other GLib callback, runs inside a dispatch where Lisp cannot prompt: a minibuffer there enters a recursive edit /underneath/ the dispatch — =read_char= calls =wait_reading_process_output=, which calls =xg_select=, which dispatches the same =GMainContext= again — and the editor wedges, with =C-g= dead because the dispatch guard cleared =waiting_for_input=. cmacs therefore binds =inhibit-interaction= for the duration, a prompt signals instead of hanging, and a =:confirm= tool is declined. Left asking, every gated tool silently failed on the surface that most used it.

To be asked about specific tools, name the rest:

#+begin_src elisp
(setq cmacs-brigade-auto-approve
      '("agent_status" "agent_result" "agent_list"))
#+end_src

understanding that outside an interactive command, being asked means being declined.

Worth knowing what =t= now covers that a prompt used to: an agent granted =project_write_file= writes files without asking, and =agent_spawn= starts runs that spend money — bounded by the agent's budget and =cmacs-brigade-subagent-max-depth=, not by you.

* Hooks and events

Abnormal hooks fire on every lifecycle edge:

- =cmacs-brigade-before-agent-start-functions=
- =cmacs-brigade-after-agent-finish-functions=
- =cmacs-brigade-before-tool-call-functions= — *may veto*, which is how you
  implement your own policy layer without touching the C gate

The same edges are published as podomation events, so a pod can react
with no Elisp at all: =on_brigade_task_state=, =on_brigade_task_done=,
=on_brigade_needs_input=, =on_brigade_budget_exceeded=,
=on_brigade_tool_called=, =on_brigade_tool_denied=,
=on_brigade_memory_indexed=, =on_brigade_deliverable_ready=,
=on_genmail_triaged=.

* Worked example: "Call For Me"

Genspark ships a feature that places real phone calls. cmacs deliberately
does not — telephony is a separate concern with a hard real-time latency
budget. Here it is anyway, entirely in userspace.

#+begin_src elisp
;;; ~/.config/cmacs/init.el

;; 1. Expose the capability.  One form: HTTP agents, CLI agents over MCP,
;;    and external MCP clients all gain `call_for_me'.
(cmacs-brigade-deftool call-for-me
  "Place a phone call, speak a script, return a transcript."
  ((number string "Destination in E.164 form, e.g. +15551234567")
   (script string "What to say"))
  :group 'telephony :destructive t :confirm 'ask :async t :timeout 600
  (my/asterisk-call number script
                    (lambda (wav)
                      (funcall done (cmacs-whisper-transcribe-file wav)))))

;; 2. An agent that uses it, defined from Lisp rather than a file.
(cmacs-brigade-register-agent
 :name    "caller"
 :model   "claude/claude-sonnet-4-6"
 :tools   '(call-for-me memory_search)
 :isolation 'none
 :budget-usd 0.25
 :prompt  "You place phone calls on the user's behalf.  Confirm the
number and what you intend to say before dialling.")

;; 3. Index call transcripts into the same memory the notes live in.
(cmacs-brigade-register-memory-source
 :name 'calls :kind 'text
 :enumerate  (lambda () (directory-files "~/calls" t "\\.txt\\'"))
 :read-chunk #'my/call-transcript-chunks)

;; 4. Show recent calls on the dashboard.
(cmacs-brigade-register-client
 :name 'matrix
 :targets (lambda () (mapcar (lambda (r) (cons (format "matrix:%s" r) r))
                             (my/joined-rooms)))
 :ready-p (lambda (_target) t)
 :deliver (lambda (target text)
            (my/matrix-send (string-remove-prefix "matrix:" target) text)))

(cmacs-brigade-register-panel
 :name 'calls :title "Recent calls" :render #'my/calls-panel)
#+end_src

You wrote a SIP bridge and four registration forms. You got a tool every
agent can call on every transport, an agent definition, transcripts in the
vector index alongside your notes, a dashboard panel, budget accounting,
confirmation prompts, allowlist scoping, and podomation events — none of
which you implemented.

* Allowlists and the relay

An agent's =tools:= list may name individual tools, groups, or =*=.  Before a
CLI agent is spawned, that list is *expanded* by
=cmacs-brigade-allowlist-expand=: group names resolve to the concrete tools in
them, while =*= and any unrecognised name pass through untouched.

The expansion happens in cmacs, not in the relay, and the reason is worth
knowing if you ever debug an agent that mysteriously has no tools.  The relay
runs in its own process, spawned by the AI CLI rather than by cmacs, so nothing
has ever called =cmacs-brigade-deftool= there and its registry is empty.  A
group name reaching that side would match nothing — silently.  Unrecognised
names pass through because most of what an agent uses (=project_read_file=,
=memory_search=, =gowl_*=) is a built-in MCP tool the brigade registry has never
seen; dropping those would strip an agent of nearly everything it was granted.

Two rules the relay enforces without needing a registry at all:

- Tools named =ai_*= or =brigade_*= are refused unconditionally, so an agent
  cannot spawn agents outside the orchestrator's budget accounting.
- The *privileged set* — =eval=, =bash=, =shell=, =execute_command=, =send_keys=,
  the C-patching tools, =crispy_eval=, =bacon_eval=, the podomation evaluators —
  is unreachable through =*= or a group.  Granting one is a deliberate act:
  name it outright or the agent does not get it.

You can ask what an agent would be permitted without running it:

#+begin_src elisp
(cmacs-brigade-tool-allowed-p "weather,project_read_file" "weather_now") ;; => t
(cmacs-brigade-tool-allowed-p "*" "eval")                               ;; => nil
(cmacs-brigade-allowlist-expand "weather")  ;; => "weather_now"
#+end_src

* A note on the safety tension

The easier it is to expose something, the easier it is to expose something
dangerous. That is inherent to the goal, not an oversight, and it is why
=:destructive= and =:confirm= exist on =deftool= from the first release rather
than being retrofitted once someone gets bitten.

Two rules follow:

- =eval=, =shell= and the C-patching tools are *default-deny* even for an
  agent that names them, unless explicitly opted in. The gate is in C at
  the dispatch point, because an allowlist in Elisp is bypassable by any
  agent that reaches =eval=.
- =:isolation none= is only as strong as the allowlist. No shipped agent
  definition uses it as a default.
