* Overview

The brigade is not a feature so much as a /fabric/: the layer every other
cmacs subsystem — and every user's own code — lays on top of to get AI
capability, agent orchestration, and memory.

It ships out-of-the-box features (a memory index over your notes, an agent
dashboard, GenMail, deliverable generators, AI in imgedit and vidstudio),
but its primary deliverable is the *extension surface*. Exposing something
of your own to every agent is one form in your init, and that one form
lights it up on all three delivery paths at once:

1. *in-process HTTP agents* — as a tool on the agent's executor
2. *CLI agents* (=claude-code=, =opencode=) — as an MCP tool reached through
   the =emacs --mcp-relay= bridge, scoped by the agent's capability token
3. *external MCP clients* — on cmacs's existing MCP server

Everything the shipped features use goes through the same public API you
get. There are deliberately no private back doors: if a built-in needs a
hook, that hook is public.

See [[file:extending.org][Extending the brigade]] — that is the document that matters.

* When the fabric loads

Lazily, and you should not have to think about it. Nothing requires =cmacs-brigade= at startup — its own eager-load block lives inside the file — so it is pulled in by whichever surface needs it first:

- opening a =cmacs-ai= chat, through an autoloaded hook registered in loaddefs;
- starting the MCP server, which loads the Elisp side before publishing from the C mirror;
- any =cmacs-brigade-*= command, =emacsctl brigade …=, or a D-Bus call.

Worth knowing because it used to be none of them: the fabric only existed after you ran a brigade command by hand, so a chat and an MCP client both saw a brigade with no tools and no way to tell that was why.

* Your first run

#+begin_src elisp
M-x cmacs-brigade          ; the dashboard
#+end_src

Then, from the dashboard:

1. =c= — create a plan. You get one example task using the shipped =researcher= agent.
2. =RET= — jump to it and replace the body with what you actually want done. The body /is/ the prompt.
3. =m= — pick a provider and model, if you do not want the agent's default.
4. Save the plan (=C-x C-s=), which adopts it, then =g= back on the dashboard.
5. =s= — start it.

The =ST= column tracks it; an error appears under the row. Nothing else needs configuring: agent definitions load themselves, and a task with no explicit worker runs in-process against the provider's API.

** What a failure means

| Message | Cause |
|---------+-------|
| =Authentication failed (HTTP 401)= | no API key for that provider — either export one or pick a CLI provider with =m= |
| =no agent definition named X= | the definition is not on `cmacs-brigade-agent-path'; press =A= to reload |
| =unknown worker X= | a =worker:= in the definition naming something unregistered |
| =unavailable isolation= | =worktree= needs git, =podman= needs podman |

** Choosing how it runs

The model string is =provider/model=. Which provider you name decides how the agent runs:

- =claude/claude-sonnet-4-6= — an HTTP provider, so it runs in-process, and tools are handed to it directly.
- =claude-code/opus= — a CLI provider, so it runs the =claude= CLI and tools go over a scoped MCP config instead.

You do not have to pick a worker; naming the provider is enough. See [[file:agents.org][Agents]] if you want to override that.

* Design principles

** Nothing is hardcoded

Every path, model, budget, endpoint, and backend is a =defcustom=. Shipped
values are /defaults/, never assumptions: your notes are not necessarily in
=~/Documents/notes= and your ollama is not necessarily on localhost. An ERT
test scans the brigade sources and fails if a literal path, model id, or
endpoint appears outside a =defcustom= form.

** Org is the plan, the dashboard is a view

A live org buffer is the durable plan model — TODO keywords are the state
machine, properties carry model/budget/tools, and org-agenda, org-clock,
refile, capture and git history work on it for free. The dashboard renders
the same data and never writes state of its own.

The ownership rule, stated once and enforced everywhere: *C is authoritative
for runtime, org is authoritative for intent.* The TODO keyword is a
projection of runtime state and an input channel for commands, never a
stored value.

** Agents run out of process

A =--gowl= cmacs instance /is/ the user's Wayland session. An agent that
blocks or errors in-process takes the desktop with it, so agents run in
supervised children and only trivial read-only work happens inline.

** Capability scoping is real, not advisory

Each agent gets a randomly minted token and a 0600 =.mcp.json= under
=$XDG_RUNTIME_DIR=; the allowlist is enforced server-side in C at the tool
dispatch point. An allowlist implemented in Elisp is bypassable by any
agent that reaches =eval=, so it is not implemented there.

* Requirements

The subsystem is gated on =--with-cmacs-ai-brigade=, which *hard-requires*
=--with-cmacs-ai= (configure errors otherwise — brigade drives ai-glib's
provider and tool-executor types directly).

=--with-cmacs-libreclaw= is optional and adds extra surfaces when present.

* Probing the build

#+begin_src elisp
(cmacs-brigade-available-p)          ;; => t when compiled in
(cmacs-brigade-capability :mcp)      ;; => t when the MCP host is available
(cmacs-brigade-capabilities)         ;; => (:libreclaw t :mcp t :f16c t)
#+end_src

=M-x cmacs-brigade-version= reports the same interactively.

=IS-CMACS-AI-BRIGADE= (and the lower-case alias =is-cmacs-ai-brigade=) is
always bound, even in a build with the feature off, so a user config can
branch on it without a =void-variable= error:

#+begin_src elisp
(when IS-CMACS-AI-BRIGADE
  (require 'cmacs-brigade))
#+end_src

The =:f16c= capability reports only that the F16C vector-scan path could be
/compiled/, not that this CPU has the instructions — that is decided at
runtime by =__builtin_cpu_supports=, with a scalar fallback, so one binary
runs on hosts with and without it.
