* Why a relay exists

cmacs's MCP server listens on a Unix socket. =claude --mcp-config= understands a
stdio command or an HTTP URL, and neither is a Unix socket, so a CLI agent
cannot reach cmacs directly.

=emacs --mcp-relay= is the stdio command it does understand. It speaks NDJSON on
stdin and stdout, forwards to the socket, and enforces the agent's allowlist in
between.

* No Lisp VM in the relay

It follows the =--bacon= / =--cmacs-lsp= never-return model: the hook runs in
=main()= before any Emacs initialisation.

That is not an optimisation, it is the security property. The relay is the thing
standing between an agent and the editor's whole tool surface. If it could
evaluate Lisp, an agent that got a prompt injection through would be evaluating
Lisp inside the process that is supposed to be restraining it.

stdout is protocol-only for the same reason: a stray message corrupts the
JSON-RPC stream.

* What it filters

| Method                       | Treatment                                                       |
|------------------------------+-----------------------------------------------------------------|
| =tools/list=                 | pruned to what the allowlist admits                             |
| =tools/call=                 | anything else answered locally, never forwarded                 |
| =resources/read=, =subscribe= | need the pseudo tool =resources= (=*= covers it), else denied    |
| =resources/list=, =templates/list= | answered locally with an empty list unless =resources= is granted |
| =prompts/get=                | needs the pseudo tool =prompts=, else denied                     |
| =prompts/list=               | empty list unless =prompts= is granted                          |
| anything that is not one JSON object per line | answered locally with a parse / invalid-request error; never forwarded |

Hiding beats refusing. A model that can see =eval= in the tool list will keep
trying it and burn turns; one that never learns it exists does not.

The denial is =-32601= "method not found" rather than a permission code — as far
as that agent is concerned the tool does not exist, which is also what
=tools/list= told it.

=resources/read= is gated because it is not a small thing: =buffer://= reads any
buffer and =file://{+path}= reads any file on disk with no workspace
confinement. An allowlist of two read-only tools must not hand that over for
free, so it takes the word =resources= in the allowlist (or =*=). The same holds
for prompts. A JSON-RPC batch (an array) would carry its own requests past the
per-method checks, so the relay accepts exactly one object per line and answers
anything else itself.

The relay reads the gate's two settings from its environment ---
=CMACS_BRIGADE_RESTRICT_PRIVILEGED= and =CMACS_BRIGADE_BLOCK_RECURSIVE=, written
by the provisioner from =cmacs-brigade-restrict-privileged-tools= and
=cmacs-brigade-block-recursive-tools=. It has no Lisp VM, so it cannot read
those variables itself; before the environment carried them it read the
uninitialised globals as nil, which meant the recursion block was silently off
in the relay and the privileged-tools restriction was never honoured for CLI
agents.

* Provisioning

Before a CLI agent starts, the brigade:

1. expands the agent's allowlist to concrete tool names;
2. opens a *scoped socket* for it (=cmacs-brigade-scope-open=): a second MCP
   listener inside cmacs, under =XDG_RUNTIME_DIR/cmacs/brigade/=, whose every
   session registers the full tool set and then removes what the allowlist
   does not admit --- the same C gate the relay uses, run by the process that
   owns the tools;
3. writes a 0600 =.mcp.json= under =XDG_RUNTIME_DIR= naming the relay, with the
   scoped socket path, the allowlist, the gate's policy and a token in its
   =env= block;
4. hands the path to the worker as =--mcp-config=.

Five decisions worth knowing:

- *The capability is the socket, not a string.* An earlier design minted a
  random token that nothing ever verified, beside the path of the unrestricted
  =cmacs-mcp-<pid>.sock=; an agent with a shell could =nc -U= the socket and
  have =eval=, and the allowlist was enforced only by a process the agent's own
  config file described. With a scoped socket, connecting directly yields the
  scoped surface. =CMACS_BRIGADE_TOKEN= is still exported for callers that key
  on it, but nothing about access depends on it. In a build without
  =--with-cmacs-mcp= there is no scope; the plain socket is used and the relay
  is the only gate, which is what it always was.
- *The token is random*, never derived from the agent's name or id. Agents quote
  their own context into prompts and logs constantly, so a secret derived from
  something they know about themselves is a secret by construction only.
- *It goes in =XDG_RUNTIME_DIR=*, not the workspace. A project =.mcp.json= is
  user-authored, usually git-tracked and shared by every agent; writing there
  would clobber it and make concurrent agents race.
- *The file is created 0600*, not written and then tightened. That gap is
  exactly when a credential is readable by anything on the machine.
- *Revoke runs before provision*, not only at teardown. A partial failure would
  otherwise leave the old token valid with no file naming it — a credential
  nobody can find to remove.

The filename is a random UUID rather than the agent id, since ids end up in
prompts and a path is a disclosure.

Every provision is revoked when the run ends, and all of them on
=kill-emacs-hook=.

* Where the allowlist is evaluated

Group names are expanded *in cmacs*, before the config is written. The relay
runs in its own process, spawned by the AI CLI, and has never had
=cmacs-brigade-deftool= called in it — its registry is empty, so a group name
reaching that side would match nothing, silently.

Unrecognised names pass through expansion untouched, because most of what an
agent uses (=project_read_file=, =memory_search=, =gowl_*=) is a built-in MCP
tool the brigade registry has never seen. Dropping them would quietly strip an
agent of nearly everything it was granted.

Two rules the relay enforces with no registry at all:

- =ai_*= and =brigade_*= are refused unconditionally while
  =cmacs-brigade-block-recursive-tools= is non-nil (the default), so an agent
  cannot spawn agents outside the orchestrator's budget accounting.
- The *privileged set* — =eval=, =bash=, =shell=, =execute_command=,
  =send_keys=, the C-patching tools, =crispy_eval=, =bacon_eval=, the podomation
  evaluators, the gowl input-recording tools and =gsurf_eval_js= — is never
  reachable through a group, and is withheld from =*= when
  =cmacs-brigade-restrict-privileged-tools= is set (off by default: the wildcard
  is the user's call about their own editor). Granting one under the
  restriction is a deliberate act: name it outright or the agent does not get it.

* The mailbox group

Five tools let an agent continue a conversation with another agent, or read
what one has been doing:

| Tool | What it does |
|------+--------------|
| =agent_send= | queue a message; wakes a task that has already finished |
| =agent_inbox= | what is queued for a task but not yet delivered |
| =agent_drop= | remove a queued message, or all of them |
| =agent_log= | read *any* task's transaction log, spawned by you or not |
| =agent_close= | finish with an agent and release its session |

They are a separate group from =agent= on purpose. =agent= is the five spawning
and polling tools; =mailbox= is the ability to start further paid turns on an
existing agent and to read other agents' activity. An agent granted =agent= does
not get =mailbox=, and a read-only debugging agent can be given =mailbox= —
=agent_log= is not destructive — without also being able to spend money.

=agent_log= is the sidecar-debugging tool: point a second agent at a
misbehaving one and it reads every instruction, tool call and reply, rather
than the account the first agent gives of itself. See [[file:mailbox.org][Mailboxes]].

* Checking

#+begin_src elisp
(cmacs-brigade-tool-allowed-p "weather,project_read_file" "weather_now") ;; => t
(cmacs-brigade-tool-allowed-p "*" "eval")                                ;; => t  (default)
(let ((cmacs-brigade-restrict-privileged-tools t))
  (cmacs-brigade-tool-allowed-p "*" "eval"))                             ;; => nil
(cmacs-brigade-tool-allowed-p "project_read_file" "resources")           ;; => nil
(cmacs-brigade-tool-privileged-p "eval")                                 ;; => t
(cmacs-brigade-allowlist-expand "weather")                               ;; => "weather_now"
(cmacs-brigade-scope-open "weather_now,project_read_file")               ;; => "/run/user/1000/cmacs/brigade/mcp-12345-….sock"
(cmacs-brigade-scope-list)                                               ;; => (("/run/user/…sock" . "weather_now,project_read_file"))
(cmacs-brigade-scope-close "/run/user/1000/cmacs/brigade/mcp-12345-….sock") ;; => t
#+end_src

Verified end to end against a live cmacs: with an allowlist of two tools the
relay showed *2 of 195*, the permitted call returned a real result, and =eval=
was denied. With =*= and the restriction on, all 195 were visible except =eval=.
The scoped socket is covered by =cmacs-brigade-scope-serves-only-the-allowlist=,
which speaks MCP to it directly and checks that =tools/list= carries the two
tools and not =eval=.

* External clients

An external Claude Code connects to cmacs's MCP socket directly, through the
existing shim, and sees the full tool set including everything registered with
=cmacs-brigade-deftool=. The relay is for *scoped* access, which is what an
agent the brigade spawned gets.

* Config dialects

The agents do not agree on a schema, so =cmacs-brigade-host-provision= takes a
=:format=:

| Format | Shape | Delivered as |
|---+---+---|
| =claude= (default) | ={"mcpServers": {...}}= | =--mcp-config PATH= |
| =opencode= | ={"mcp": {NAME: {"type": "local", ...}}}= | =OPENCODE_CONFIG=PATH= |
| =grok= | =[mcp_servers.NAME]= TOML | an overlay =GROK_HOME= |

The *dialect* is ours, because we own the server being published. The
*delivery* is ai-glib's, because it is that CLI's own mechanism; a provider
advertises which =AiAgentEndpoint= kinds it accepts and cmacs mints the one that
was asked for. Neither side learns the other's business, and ai-glib never
parses an MCP config.

=cmacs-brigade-host-format-for-provider= maps a provider symbol to a format, and
=cmacs-brigade-host-endpoint-kind= maps that format to the kind string ai-glib
expects.

Every existing caller is unchanged: =:format= defaults to =claude=.

* The stale sweep

=cmacs-brigade--provisions= is in-memory only, so a crash --- or, under =--gowl=,
a compositor death --- used to leave 0600 config files in the runtime directory
forever. Each is a live capability token naming a socket nobody is listening on,
and a harness that provisions per buffer multiplies them.

Config filenames therefore carry the owning pid: =mcp-<pid>-<uuid>.json=. The
pid is not a secret, is not derived from the agent, and the uuid still carries
all the unguessability --- which is why the uuid is there at all, since ids reach
prompts and a path is a disclosure.

Scoped sockets carry the same shape, =mcp-<pid>-<uuid>.sock=, in the same
directory, and are swept by the same rule.

=cmacs-brigade-host-sweep-stale= runs once per session from the first provision
and removes any config or socket whose pid is gone *and* which is older than
=cmacs-brigade-host-stale-age= (default 300s). Both conditions are required:
=process-attributes= returning nil is weaker than kill(2)'s EPERM rule, since it
cannot distinguish a dead pid from one this Emacs may not inspect. This mirrors
=cmacs_mcp_sweep_stale_sockets=, which solves the same problem for the sockets.

Files in the older uuid-only shape are left alone --- they carry no pid to judge
by.

* Reaching grok

grok needs two things the other agents do not, and both were found the hard way.

** The server is named =cmacs-brigade=, not =cmacs=

grok resolves its config sources by merging them per *server name*, and a name
that also appears in a project-scoped source --- a repository's own
=.mcp.json= --- makes the merged entry *repo-local*, even when the surviving
definition came from the global config. Repo-local servers are not started in a
folder absent from =~/.grok/trusted_folders.toml=, silently and with no error
anywhere the user can see.

cmacs's own repository ships a git-tracked =.mcp.json= whose server is spelled
exactly =cmacs=, and the harness runs the agent in the project root --- so the
obvious name was the one name guaranteed to fail there.

claude and opencode keep the plain =cmacs=: they read a dedicated config file,
which is neither merged by name nor trust-gated. That asymmetry is why only
grok was affected.

This is a mitigation rather than a guarantee. A project whose =.mcp.json=
happens to use =cmacs-brigade= reintroduces it, and nothing on the cmacs side
can detect that.

*Do not work around it by writing a trusted =trusted_folders.toml= into the
overlay.* That also starts the project's own unvetted =.mcp.json= servers.

** Diagnosing it

#+begin_src bash
  GROK_HOME=<overlay> grok mcp doctor cmacs-brigade --json
#+end_src

=grok mcp doctor= reports the trust scope *and* the handshake, which is what you
need.

*=grok mcp list= is a trap.* It reads =config.toml= only and applies neither the
project-scope merge nor the trust rule, so it cheerfully prints a server that
will never start. It is possible to "confirm" the mechanism twice that way while
it has never worked in that directory.

A healthy result looks like:

#+begin_example
  cmacs-brigade (stdio: .../src/emacs --mcp-relay)
    ✓ command found     ✓ server started
    ✓ handshake OK      ✓ 216 tools discovered
#+end_example

** If the handshake fails

=conflict initialized response id: expected 0, got 0= is a JSON-RPC id *type*
mismatch --- a numeric id answered as a string. It reads as nonsense because
both sides render the same. Fixed in mcp-glib; any other MCP server built
against an older copy fails the same way until it is rebuilt.

* Provisioning needs the brigade loaded

=cmacs-ai= cannot =require= the brigade at top level, because the brigade
requires =cmacs-ai=. It therefore loads =cmacs-brigade-host= at the point of
use.

Guarding on =fboundp= alone --- which is what it used to do --- made tool
provisioning depend on whether something else had already pulled the brigade in:
a dashboard, a timer, an earlier chat buffer. The same provider got tools in one
session and none in the next, and the failure message blamed a build flag for a
feature that was compiled in the whole time. If you add another frontend, load
it at use rather than hoping.
