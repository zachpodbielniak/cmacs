* Why a relay exists

cmacs's MCP server listens on a Unix socket. =claude --mcp-config= understands a
stdio command or an HTTP URL, and neither is a Unix socket, so a CLI agent
cannot reach cmacs directly.

=emacs --mcp-relay= is the stdio command it does understand. It speaks NDJSON on
stdin and stdout, forwards to the socket, and enforces the agent's allowlist in
between.

* No Lisp VM in the relay

It follows the =--bacon= / =--cmacs-lsp= never-return model: the hook runs in
=main()= before any Emacs initialisation.

That is not an optimisation, it is the security property. The relay is the thing
standing between an agent and the editor's whole tool surface. If it could
evaluate Lisp, an agent that got a prompt injection through would be evaluating
Lisp inside the process that is supposed to be restraining it.

stdout is protocol-only for the same reason: a stray message corrupts the
JSON-RPC stream.

* What it filters

| Method       | Treatment                                                  |
|--------------+------------------------------------------------------------|
| =tools/list=   | pruned to what the allowlist admits                        |
| =tools/call=   | anything else answered locally, never forwarded            |

Hiding beats refusing. A model that can see =eval= in the tool list will keep
trying it and burn turns; one that never learns it exists does not.

The denial is =-32601= "method not found" rather than a permission code — as far
as that agent is concerned the tool does not exist, which is also what
=tools/list= told it.

* Provisioning

Before a CLI agent starts, the brigade:

1. mints a fresh random token;
2. expands the agent's allowlist to concrete tool names;
3. writes a 0600 =.mcp.json= under =XDG_RUNTIME_DIR= naming the relay, with the
   socket path, the allowlist and the token in its =env= block;
4. hands the path to the worker as =--mcp-config=.

Four decisions worth knowing:

- *The token is random*, never derived from the agent's name or id. Agents quote
  their own context into prompts and logs constantly, so a secret derived from
  something they know about themselves is a secret by construction only.
- *It goes in =XDG_RUNTIME_DIR=*, not the workspace. A project =.mcp.json= is
  user-authored, usually git-tracked and shared by every agent; writing there
  would clobber it and make concurrent agents race.
- *The file is created 0600*, not written and then tightened. That gap is
  exactly when a credential is readable by anything on the machine.
- *Revoke runs before provision*, not only at teardown. A partial failure would
  otherwise leave the old token valid with no file naming it — a credential
  nobody can find to remove.

The filename is a random UUID rather than the agent id, since ids end up in
prompts and a path is a disclosure.

Every provision is revoked when the run ends, and all of them on
=kill-emacs-hook=.

* Where the allowlist is evaluated

Group names are expanded *in cmacs*, before the config is written. The relay
runs in its own process, spawned by the AI CLI, and has never had
=cmacs-brigade-deftool= called in it — its registry is empty, so a group name
reaching that side would match nothing, silently.

Unrecognised names pass through expansion untouched, because most of what an
agent uses (=project_read_file=, =memory_search=, =gowl_*=) is a built-in MCP
tool the brigade registry has never seen. Dropping them would quietly strip an
agent of nearly everything it was granted.

Two rules the relay enforces with no registry at all:

- =ai_*= and =brigade_*= are refused unconditionally, so an agent cannot spawn
  agents outside the orchestrator's budget accounting.
- The *privileged set* — =eval=, =bash=, =shell=, =execute_command=,
  =send_keys=, the C-patching tools, =crispy_eval=, =bacon_eval=, the podomation
  evaluators — is unreachable through =*= or a group. Granting one is a
  deliberate act: name it outright or the agent does not get it.

* The mailbox group

Five tools let an agent continue a conversation with another agent, or read
what one has been doing:

| Tool | What it does |
|------+--------------|
| =agent_send= | queue a message; wakes a task that has already finished |
| =agent_inbox= | what is queued for a task but not yet delivered |
| =agent_drop= | remove a queued message, or all of them |
| =agent_log= | read *any* task's transaction log, spawned by you or not |
| =agent_close= | finish with an agent and release its session |

They are a separate group from =agent= on purpose. =agent= is the five spawning
and polling tools; =mailbox= is the ability to start further paid turns on an
existing agent and to read other agents' activity. An agent granted =agent= does
not get =mailbox=, and a read-only debugging agent can be given =mailbox= —
=agent_log= is not destructive — without also being able to spend money.

=agent_log= is the sidecar-debugging tool: point a second agent at a
misbehaving one and it reads every instruction, tool call and reply, rather
than the account the first agent gives of itself. See [[file:mailbox.org][Mailboxes]].

* Checking

#+begin_src elisp
(cmacs-brigade-tool-allowed-p "weather,project_read_file" "weather_now") ;; => t
(cmacs-brigade-tool-allowed-p "*" "eval")                                ;; => nil
(cmacs-brigade-tool-privileged-p "eval")                                 ;; => t
(cmacs-brigade-allowlist-expand "weather")                               ;; => "weather_now"
#+end_src

Verified end to end against a live cmacs: with an allowlist of two tools the
relay showed *2 of 195*, the permitted call returned a real result, and =eval=
was denied. With =*=, all 195 were visible except =eval=.

* External clients

An external Claude Code connects to cmacs's MCP socket directly, through the
existing shim, and sees the full tool set including everything registered with
=cmacs-brigade-deftool=. The relay is for *scoped* access, which is what an
agent the brigade spawned gets.

* Config dialects

The agents do not agree on a schema, so =cmacs-brigade-host-provision= takes a
=:format=:

| Format | Shape | Delivered as |
|---+---+---|
| =claude= (default) | ={"mcpServers": {...}}= | =--mcp-config PATH= |
| =opencode= | ={"mcp": {NAME: {"type": "local", ...}}}= | =OPENCODE_CONFIG=PATH= |
| =grok= | =[mcp_servers.NAME]= TOML | an overlay =GROK_HOME= |

The *dialect* is ours, because we own the server being published. The
*delivery* is ai-glib's, because it is that CLI's own mechanism; a provider
advertises which =AiAgentEndpoint= kinds it accepts and cmacs mints the one that
was asked for. Neither side learns the other's business, and ai-glib never
parses an MCP config.

=cmacs-brigade-host-format-for-provider= maps a provider symbol to a format, and
=cmacs-brigade-host-endpoint-kind= maps that format to the kind string ai-glib
expects.

Every existing caller is unchanged: =:format= defaults to =claude=.

* The stale sweep

=cmacs-brigade--provisions= is in-memory only, so a crash --- or, under =--gowl=,
a compositor death --- used to leave 0600 config files in the runtime directory
forever. Each is a live capability token naming a socket nobody is listening on,
and a harness that provisions per buffer multiplies them.

Config filenames therefore carry the owning pid: =mcp-<pid>-<uuid>.json=. The
pid is not a secret, is not derived from the agent, and the uuid still carries
all the unguessability --- which is why the uuid is there at all, since ids reach
prompts and a path is a disclosure.

=cmacs-brigade-host-sweep-stale= runs once per session from the first provision
and removes any config whose pid is gone *and* which is older than
=cmacs-brigade-host-stale-age= (default 300s). Both conditions are required:
=process-attributes= returning nil is weaker than kill(2)'s EPERM rule, since it
cannot distinguish a dead pid from one this Emacs may not inspect. This mirrors
=cmacs_mcp_sweep_stale_sockets=, which solves the same problem for the sockets.

Files in the older uuid-only shape are left alone --- they carry no pid to judge
by.
