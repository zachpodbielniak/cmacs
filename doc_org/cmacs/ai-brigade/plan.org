* A plan is an org file

Headlines are tasks, the body is the prompt, properties carry the agent and its
budget, and the TODO keyword shows what is happening. org-agenda, org-clock,
refile, capture, export and git history then work on it for free — which is the
whole reason the plan is a file and not a data structure.

#+begin_example
,#+TODO: TODO(t) NEXT(n) INPROGRESS(i) WAIT(w) HOLD(h) | DONE(d) FAILED(f) CANCELLED(c)

,* TODO Survey the competition                            :brigade:
  :PROPERTIES:
  :AGENT:  researcher
  :BUDGET: 0.50
  :END:
  Compare their feature set against ours and produce a cited brief.
#+end_example

A headline is a task when it has an =:AGENT:= property or a =:brigade:= tag.
Everything else is ordinary org — a plan file is still a file, and putting a
runtime record behind every heading someone wrote would make the dashboard
meaningless.

=M-x cmacs-brigade-plan-create= scaffolds one. =M-x cmacs-brigade-plan-mode=
turns an existing org file into a plan.

* Who owns what

The design that stops the two representations drifting is *disjoint field
ownership*.

| Owner | Fields                                                          |
|-------+-----------------------------------------------------------------|
| Org   | title, body, =:AGENT:=, =:MODEL:=, =:BUDGET:=, =:TOOLS:=, =:ISOLATION:=, =:DEPENDS:=, tags, priority |
| C     | state, turns, tokens, cost, timestamps, error — rendered into =:BRIGADE-*:= |

C never writes an intent field. Elisp never sets a runtime field except through
a DEFUN. Nothing is owned twice, so there is nothing to merge and no
last-write-wins.

** The TODO keyword

Looks like an exception, and is not.

Outbound it is a *projection* of the C state. Inbound it is a *command*: typing
=C-c C-t= is requesting a transition, and the state machine decides whether that
request is legal.

| You set      | From        | Means                          |
|--------------+-------------+--------------------------------|
| =NEXT=         | draft       | queue it                       |
| =TODO=         | queued      | unqueue it                     |
| =TODO=         | running     | *refused* — cancel it first    |
| =CANCELLED=    | any live    | cancel — always allowed        |
| =DONE=         | running     | *refused* — the agent decides  |
| =NEXT=         | done/failed | retry                          |

A refusal restores the keyword and says why. Leaving it where you put it would
display a state the task is not in, which is worse than declining the edit, and
obeying it would orphan a live agent that is still spending money.

The exact state is always in =:BRIGADE-STATE:=; several states share a keyword,
so that property is what a program should read.

A =DONE= task may still be resumable. Sending it a message with =agent_send=
moves it back through =queued= to =running= on the session it already had — the
same transition a retry makes. So =DONE= means "answered", not "will never run
again"; what makes it resumable is its conversation record, which the dashboard
shows and =agent_close= releases. See [[file:mailbox.org][Mailboxes]].

=WAIT= is reached in two ways: an agent that stopped to ask you something, and a
resumed turn that could not start yet but is worth retrying. Neither is a state
a plan re-adopt can un-queue — =WAIT= to =TODO= is refused — so an unrelated
spawn cannot strand a task that is waiting to be answered.

* Surviving a restart

The runtime task table is a C hash that dies with the process. The plans do
not — they are org files — so the org side is what carries a task's history
across a restart, and two halves of that have to work.

*Runtime state is written back into the plan.* Every transition and every
progress update queues a render of the plan the task belongs to, applied once
you are idle (=cmacs-brigade-plan-render-idle=, 0.4s). The render writes
=:BRIGADE-STATE:=, =:BRIGADE-TURNS:=, =:BRIGADE-TOKENS:=, =:BRIGADE-COST:= and
the TODO keyword, refuses to touch a file that changed on disk underneath it or
that has conflict markers, and updates plans whose buffer has been killed
(=cmacs-brigade-plan-write-when-closed=).

*The plans are adopted again on startup.* =cmacs-brigade-plan-restore= scans
=cmacs-brigade-plan-directory= for org files with a =:brigade:=-tagged headline
and adopts each one, so the dashboard shows your work rather than an empty
table. It runs once when the brigade loads and once more the first time the
dashboard opens; =M-x cmacs-brigade-plan-restore= with a prefix argument
rescans. Set =cmacs-brigade-plan-restore-on-start= to nil to turn the automatic
pass off.

Restoring reads the recorded state *directly* rather than treating the keyword
as a command. That distinction is load-bearing: a freshly created runtime record
is =draft=, so a =DONE= keyword read as a request would be a request to finish a
task that had not started, the state machine would refuse it, and the refusal
path would rewrite the headline back to =TODO=. Reopening cmacs would destroy
the outcome the plan existed to record.

A task that was live when the editor exited comes back =interrupted=, not
=running=. Nothing is running: the process died with the editor, and showing it
as live would have the dashboard, the concurrency cap and the notifier all
believing in an agent that is not there. =INTERRUPTED= to =QUEUED= is the retry.

Two things restore deliberately does not do. It does not run in batch, because a
test or a =--script= has no business rewriting your plans on the way past. And
it skips a file whose =:PROPERTIES:= drawer has no =:END:= — the shape a crash
or a half-finished sync leaves — because adopting one does not fail, it hangs
inside org, and on the startup path that is indistinguishable from cmacs
refusing to boot.

* Identity

Org's own =:ID:= when =org-id= is available — which buys =org-id-goto=,
=org-store-link= and refile safety for nothing — falling back to
=:BRIGADE-ID:=. Written once on adopt, never rewritten, so renaming a headline
does not orphan its history.

Copying a subtree brings its =:ID:= along, and this happens constantly. The
second occurrence in buffer order gets a fresh id, because what the person meant
was another task, not a second view of the same one.

* When things are written

*Adopt* (org → runtime) runs on save, on =g=, and on a keyword change. It reads
every task into one atomic transaction, and writes back only what the runtime
returned.

*Render* (runtime → org) never touches the buffer directly. The runtime hands
over changed records and the org layer applies them, to =:BRIGADE-*:= properties
and the keyword only.

Three rules about what a person is actually doing when this fires:

- Renders are *queued*, drained on an idle timer. Nothing rewrites the buffer
  between two keystrokes.
- Headlines are *never reordered*. Order is human-owned, permanently;
  re-sorting someone's buffer under them is the most destructive thing this code
  could do.
- A buffer whose file changed on disk, or which contains conflict markers,
  *refuses to render*. The runtime data is reconstructible and your edits are
  not.

With the buffer closed — the common case once agents are running — updates are
batched and flushed to the file. The alternative, a journal reconciled later, is
drift by another name.

Anything that was running becomes =interrupted=, which is neither done nor
failed. It was abandoned, and nobody watched it stop. Nothing resumes
automatically: =interrupted= can only be retried or dropped.

* Checking for drift

=M-x cmacs-brigade-plan-lint= reports any disagreement between the file and the
runtime, rather than leaving it to be inferred from a dashboard that looks
wrong.

The property tests in =test/cmacs/cmacs-brigade-plan-tests.el= assert the
invariants directly: adopt is idempotent, render is byte-identical when
repeated, a copied subtree yields distinct ids, an illegal keyword is restored,
a stale buffer refuses, and order survives.

* Writing a task from Lisp

One function composes a task headline, and everything that creates one goes
through it — voice dictation, the compose transient, a clone. Three
hand-written copies of this had already drifted apart on whether the tag went
on, how the body was indented, and whether the file was created if missing.

#+begin_src elisp
(cmacs-brigade-plan-append-task
 "~/notes/01_projects/personal/brigade/plan.org"
 (list :title  "Survey the competition"
       :prompt "Read the last quarter of release notes and summarise what
changed."
       :agent  "researcher"
       :model  "claude-code/sonnet"
       :budget "0.50"
       :tools  '(memory_search web_search)
       :cwd    "~/src/project"
       :properties '(("NOTIFY" . "chat:*cmacs-ai: grok*"))))
#+end_src

It creates the file if absent, appends the headline, adopts it, and returns the
new task id. An empty value is left out of the drawer entirely rather than
written blank: an empty =:MODEL:= is a different request from no =:MODEL:=, and
the runner reads the absent one as "whatever the agent definition says".

The body is indented, which is not cosmetic. A prompt is prose someone wrote,
and prose contains lines starting with =*= — a bullet, a glob, a footnote. At
column zero org reads that as a headline, and the rest of the prompt silently
becomes a separate task, so the agent runs the first sentence of its
instruction and nothing else.

| Function                          | Does                              |
|-----------------------------------+-----------------------------------|
| =cmacs-brigade-plan-append-task=    | compose, adopt, return the id     |
| =cmacs-brigade-plan-read-task=      | the intent fields of a task, as a plist |
| =cmacs-brigade-plan-ensure-file=    | create an empty plan if absent    |
| =cmacs-brigade-plan-task-property=  | one property of one task          |
| =cmacs-brigade-plan-task-prompt=    | a task's prompt, read back from the file |

=cmacs-brigade-plan-read-task= reads what a human wrote, not what the runtime
made of it — so a task whose per-task overrides produced a derived agent reads
back as the base agent it was written with. That is what a clone copies.
