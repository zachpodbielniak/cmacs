* What this is

=M-x cmacs-ai-harness= opens an agentic AI session in a buffer: a transcript the library owns, rendered natively, with an editable prompt at the end.

It is *not* [[file:cmacs-ai.org][=cmacs-ai-chat=]], and the difference is worth stating because the two look similar from the outside:

| | =cmacs-ai-chat= | =cmacs-ai-harness= |
|---+---+---|
| The buffer is | an Org document | a rendered view |
| History is | text you can edit and save | the library's, redrawn from blocks |
| Tool calls | not grouped | grouped and summarised by ai-glib |
| Slash commands and =@= mentions | no | yes, from the same files other harnesses read |
| Saving | autosaves as Org | exports on request as markdown, Org or text |

A chat is a conversation you keep. A harness is an agent you are driving, and the transcript is a view of what it did.

* The three entry points

| Command | What it asks |
|---+---|
| =cmacs-ai-harness= | nothing --- uses =cmacs-ai-harness-provider=, =cmacs-ai-harness-model= and =default-directory= |
| =cmacs-ai-harness-with-provider= | provider, then model |
| =cmacs-ai-harness-with-provider-in-directory= | provider, directory, then model |

The directory is not cosmetic. =CLAUDE.md=, =.claude=, the project's own command files and every relative path a tool touches resolve against it --- an agent started in the wrong directory is a different agent.

* Keys

| Key | Does |
|---+---|
| =C-c C-c= | send the prompt |
| =C-c C-k= | cancel the run, or clear the prompt when idle |
| =C-c C-g= | write the prompt in a dedicated buffer |
| =C-c C-e= | export the session as Org |
| =C-c E= | export the session as markdown |
| =C-c C-t= | expand or collapse the block at point |
| =C-c C-p= | switch provider, carrying the old CLI's own history |
| =C-c C-r= | reset: a genuinely fresh session on the same provider |
| =C-c C-n= | show what the wrapped CLI remembers |
| =C-c C-u= | ask the provider what it has been spending (=C-u= for history) |
| =TAB= | complete a =/command= or an =@path= |

=C-c C-k= is one key for two things because that is what the terminal harness's =^C= does, and the two are never ambiguous: there is either a run to stop or there is not.

** The compose buffer

=C-c C-g= opens =*cmacs-ai harness compose*= seeded with whatever is already in the prompt, so reaching for a real buffer part-way through a long prompt does not lose it. =C-c C-c= there installs the text as the prompt and closes the buffer; =C-c C-k= discards it.

The terminal harness hands the prompt to =$EDITOR= for this. Inside Emacs that would be an editor inside an editor, so it is just a buffer.

* Export

=C-c C-e= (Org) and =C-c E= (markdown) prompt with =read-file-name=, so it is the same directory browsing and completion as =C-x C-f= rather than a bespoke picker. The default name mirrors [[file:cmacs-ai.org][=cmacs-ai-chat-save-name-format=]] with =harness= in it:

: 260816-225824-harness-ollama.org

controlled by =cmacs-ai-harness-export-name-format=, under =cmacs-ai-harness-dir= (the same directory chats are archived in --- a session is a session).

The extension comes from ai-glib rather than from here, so an Org export and =ai-tui='s =/export org= cannot disagree about what to call it.

Three things about the export are worth knowing, all of them ai-glib's doing:

- *Blocks export expanded whatever the buffer shows.* A collapsed tool group renders as one summary line, and a file recording "Edited 3 files" without saying which is not a record of anything.
- *The rendering is not the content.* The =›= markers and the =✳ thinking ⌄= chrome orient a reader on screen and are noise in a file --- in Org, =>= is not even syntax. Prose blocks export their own text; tool and todo blocks keep their markers, because there =✓= and =+21-6= /are/ the information.
- *Prose passes through, output is fenced.* Models already write markdown, so escaping an answer would ruin every code fence in it.

* The AI menu

Right-click (or =cmacs-ai-menu-pick=) offers a *Harness* group in these buffers:

| Action | Does |
|---+---|
| Write this prompt for me | with an empty prompt, asks what you want and drafts one; with a draft already there, strengthens it without broadening the scope |
| Summarize this session | reads the /exported/ transcript, so it can say what the agent did and not only what it narrated |
| Next steps from this session | a checklist of what to do next |
| Explain this block | the block under the pointer |
| Copy this block | to the kill ring |
| Export session as markdown / Org | the same as the keys above |

* Configuration

| Variable | Default | Means |
|---+---+---|
| =cmacs-ai-harness-provider= | nil | provider symbol, or the configured default |
| =cmacs-ai-harness-model= | nil | model, or the provider's own default |
| =cmacs-ai-harness-dir= | =$XDG_DATA_HOME/cmacs-ai/= | where exports are offered first |
| =cmacs-ai-harness-export-name-format= | =%y%m%d-%H%M%S-harness-<provider>= | export file name, without extension |
| =cmacs-ai-harness-prompt= | =› = | the prompt marker |
| =cmacs-ai-harness-enable-tools= | t | give the agent cmacs's tools |
| =cmacs-ai-harness-system-prompt= | (a short one) | instructions, or nil |
| =cmacs-ai-harness-cli-tool-allowlist= | =*= | what a CLI agent may call |
| =cmacs-ai-harness-default-directory-function= | project root | where a new harness runs |
| =cmacs-ai-harness-executor-functions= | nil | hook, =(EXECUTOR PROVIDER)= |
| =cmacs-ai-harness-run-chat-executor-functions= | nil | also run the chat hook |
| =cmacs-ai-harness-import-native-context= | t | carry a CLI's own history across a provider switch |
| =cmacs-ai-harness-native-context-limit= | 65536 | byte ceiling on what is carried |
| =cmacs-ai-harness-process-timeout= | nil | ms for one CLI run; 0 removes the deadline |

Faces are one per ai-glib style role --- =cmacs-ai-harness-tool-name=, =cmacs-ai-harness-added=, and so on. The library's tags are *roles, not colours*: =added= says "this run is an addition" and says nothing about green, so the mapping is cmacs's and a theme can override any of it.

* Session control

ai-glib grew mid-flight provider switching, native-history import, session reset and usage reporting at the same time as =ai-tui= grew a panel system, a theme picker and an animation loop. The capabilities are worth having. The chrome is not, because Emacs already has better versions of all of it: a buffer /is/ a panel, =customize-face= /is/ a theme picker, and nothing here needs to animate. So each of these is an ordinary command that prints an ordinary message, and every result lands in an ordinary buffer.

** Switching provider mid-session

=C-c C-p= moves the conversation to another provider. The transcript on screen, the message history behind it, the system prompt and the working directory all stay; only who answers the next turn changes. It is refused while a turn is in flight, and refused if the incoming provider cannot accept the tool endpoint this session is using --- in which case the current provider is left untouched rather than half-swapped.

The interesting part is what a CLI leaves behind. A wrapped coding agent keeps a transcript of its own that this buffer never sees: the blocks here are what the library observed, and the agent remembers a great deal more. With =cmacs-ai-harness-import-native-context= on (the default), the switch reads that transcript first and hands it to the incoming provider as context, so the conversation survives the move. =cmacs-ai-harness-show-carried-context= shows exactly what was carried.

Trimming to =cmacs-ai-harness-native-context-limit= keeps the /end/ of the transcript --- the recent turns --- and says so in the text it hands over, because a model given a silently shortened history cannot tell anything is missing.

This build reads =claude-code=, =claude-tmux=, =codex-cli= and =grok-build=. The others keep history in SQLite and are deliberately *not* half-read: a partial import is invisible to the model that receives it. =ai-tui= carries 700 lines of its own readers for those, plus a sqlite3 dependency, which ai-glib kept out of the library on purpose; cmacs uses the library's readers and says "nothing readable" for the rest.

** Reset is not clear

=C-c C-r= and a cleared buffer are different operations and the difference matters.

=/clear= empties the transcript this buffer renders. A wrapped CLI keeps its *own* session id, so after a clear it carries on resuming the conversation you thought you had thrown away --- the buffer looks empty and the agent does not.

=C-c C-r= drops that session id, turns off =continue-session=, and builds a new conversation. That also forgets tool approvals, todos and agent results, and gives the session a new executor --- so tools are re-wired afterwards, which is why the command does it for you. Provider, model, system prompt and working directory are kept.

** What the CLI remembers

=C-c C-n= shows the wrapped CLI's own transcript: which file it lives in, how many messages survived the last compaction, how many were dropped before that boundary, and the text itself. This is the same text a provider switch would carry, so it answers "what would I be handing over" before you hand it over.

** Usage

=C-c C-u= asks the provider what it has been spending; =C-u C-c C-u= asks for past periods instead of the current quota windows.

The answer arrives in its own buffer when the provider replies, and *not* as a return value. The query spawns the CLI as a JSON-RPC peer and can sit there for half a minute. Blocking Emacs for that would be bad on its own; under =--gowl= Emacs is also the compositor, so it would freeze the desktop rather than merely the editor. Only some CLIs report at all --- codex and grok do.

** Deadlines

A wrapped CLI gets thirty minutes for one run, ai-glib's default, so a CLI wedged on a half-open socket cannot pin the session forever. ai-glib's own =ai= and =ai-tui= binaries disable it outright, on the grounds that a long agentic run legitimately outlives any deadline you would pick and being killed mid-edit is worse than waiting. Set =cmacs-ai-harness-process-timeout= to 0 for the same behaviour here.

* Tools

A harness has cmacs's whole MCP tool surface --- buffers, files, project
search, =apropos=, =describe-function=, the lot --- on top of ai-glib's own
=bash=, =read=, =write=, =edit=, =glob=, =grep=. Roughly sixty tools, filtered by
the three =cmacs-ai-mcp-bridge-*= knobs =cmacs-ai-chat= already uses.

=/tools= lists them. =/todos= shows the agent's todo list.

** Two mechanisms, chosen by provider

They are genuinely different, and ai-glib refuses to pretend otherwise.

- An *HTTP model* (claude, openai, gemini, grok, ollama, openai-compatible and any endpoint you named in =cmacs-ai-openai-compatible-endpoints=) is sent a =tools= array
  built from the conversation's =AiToolExecutor=. cmacs adopts that executor
  into its own handle registry, registers the MCP bridge on it, and sets
  =local-tools=.
- A *command-line agent* (claude-code, claude-tmux, opencode, grok-build,
  antigravity, cursor, codex-cli) runs
  its own tools in its own process and ignores that array entirely ---
  =ai_conversation_set_local_tools= silently refuses one. It is handed an *MCP
  config* naming this cmacs instead: =cmacs-brigade-host-provision= mints a
  random token and a 0600 file under =XDG_RUNTIME_DIR= describing
  =emacs --mcp-relay=, and the agent connects back.  Codex is the one CLI
  ai-glib declares no MCP endpoint kind for, so a codex harness gets no
  cmacs tools; the brigade's own =codex= worker delivers them through a
  =CODEX_HOME= overlay instead.

The mode line says which: =60 tools= for the first, =mcp= for the second, and a
warning face for *no tools* if wiring failed. That indicator is not decoration
--- a provider that silently took none is otherwise invisible from the
transcript.

** Dialects

The agents do not agree on a config schema. =cmacs-brigade-host-provision= takes
a =:format= --- =claude=, =opencode= or =grok= --- and emits the right one; the
provider decides how the file is delivered (a =--mcp-config= flag,
=OPENCODE_CONFIG=, an overlay =GROK_HOME=). Writing the dialect anywhere but
beside the credential lifecycle would be a second place that has to agree about
the 0600 write, the revoke-before-provision and the sweep.

For grok the server is named =cmacs-brigade= rather than =cmacs=, because grok
scopes MCP servers by name across config sources and a name a project's own
=.mcp.json= already uses is judged repo-local and never started in an untrusted
folder. See [[file:ai-brigade/mcp.org][Brigade and MCP]].

** When an agent says it has no tools

The mode line is the first thing to read: =60 tools=, =mcp=, or a warning when
wiring failed. After that, =*Messages*= carries the reason --- the wiring says
so out loud rather than failing quietly, because a session that looks
tool-enabled and has none is invisible from the transcript.

For a CLI agent, the agent's own diagnostics are the authority on whether the
server actually started:

#+begin_src bash
  GROK_HOME=<overlay> grok mcp doctor cmacs-brigade --json   # grok
  claude mcp list                                            # claude-code
#+end_src

=grok mcp list= is *not* a useful check --- it reads the config file without
applying grok's project-scope merge or its trust rule, so it prints servers that
will never start.

** What a CLI agent may call

=cmacs-ai-harness-cli-tool-allowlist= defaults to =*=, matching the chat buffer.

A harness buffer is a person typing a prompt and watching every tool call render
in front of them --- the trust level of =M-x eval-expression=, not of an
unattended worker running against a budget. Withholding =eval= from an agent you
are driving turn by turn inside your own editor buys nothing and produces
exactly the failure this feature fixes: an agent narrating tool calls it cannot
make. Set =cmacs-brigade-restrict-privileged-tools= to =t= to hold =eval=,
=bash= and the C-patching tools back from =*=.

** Adding your own

#+begin_src elisp
  (add-hook 'cmacs-ai-harness-executor-functions
            (lambda (executor _provider)
              (cmacs-ai-tools-register executor "my_tool" "..." params #'fn)))
#+end_src

A *sibling* of =cmacs-ai-chat-executor-functions=, not the same hook: that one's
members were written for chat buffers and include the brigade's agent-spawning
tools, so running them here would silently change what every existing member is
handed. Set =cmacs-ai-harness-run-chat-executor-functions= to opt into both.

** Exports carry tool output

A transcript exported with =C-c C-e= includes tool blocks verbatim --- command
output, file contents, MCP results. Worth knowing before sharing one.

* How it works

#+begin_example
  provider ──emits AiEvent──▶ AiConversation ──folds into──▶ AiTranscript
                              (the driver)                   (GListModel<AiViewBlock>)
                                                                     │
                                        cmacs-ai-harness-block-render
                                                                     │
                                                      text + spans ──▶ Emacs text properties
#+end_example

The grouping, the summarising and the input pipeline all live in ai-glib. This buffer knows nothing about what a tool is --- exactly as =ai-tui= does not.

** Why a C bridge and not cmacs-gi

ai-glib's own documentation shows this frontend written in Elisp over GObject Introspection. That does not work here yet: [[file:cmacs-gi.org][cmacs-gi]] skips out-parameters entirely and has no signal support, and the harness needs both. =ai_rendered_text_get_span()= and =ai_completion_result_get_item_fields()= are out-parameter APIs *because* a plain struct behind a pointer does not survive =g-ir-scanner=, and =::block-changed= is what makes streaming appear at all.

Teaching cmacs-gi those two things is worth doing and is a bigger, riskier change to a subsystem everything else already depends on. So =cmacs/ai/cmacs-ai-harness.c= is a purpose-built bridge, in the shape =cmacs-ai-stream.c= already uses.

** Two things a frontend gets wrong

Both are handled in one place here, and both are silent when wrong:

1. *Span offsets are byte offsets into UTF-8.* =byte-to-position= converts. Skip it and every face after the first accented filename lands somewhere else.
2. *=::block-changed= is not optional.* Streaming mutates a block in place, which the insertion signal does not report. Without it the buffer shows the first delta of each reply and then stops.

** Evil, and why the mode is not a =special-mode=

The obvious base class for a buffer with a read-only transcript is =special-mode=, and it is the wrong one. Two things follow from it and both are wrong here: the buffer becomes read-only outright, and *Evil gives modes derived from =special-mode= normal state* --- so under Doom every letter you type at the prompt is a motion or an operator, and the buffer looks broken rather than modal.

So the mode derives from =fundamental-mode=, the transcript is protected by a =read-only= text property covering exactly the part that needs it, and the buffer opens in *insert* state --- the same treatment eshell, vterm and a commit message get, because the thing you do here is type. =ESC= still reaches normal state for reading back through the transcript with the motions you already know.

The =evil-set-initial-state= call is inside =with-eval-after-load=, not behind a bare =fboundp= guard as some other cmacs modes use: that guard silently does nothing when the file loads before Evil, and the failure mode is landing in normal state, which does not look like an Evil problem when you hit it.

** Both stickiness flags on the read-only property

=cmacs-ai-harness--read-only-props= is =(read-only t front-sticky t
rear-nonsticky t)= and neither flag is optional:

- =rear-nonsticky= is what lets the first character of the prompt be
  typed at all.  Without it the property is inherited by whatever is
  inserted after the separator, and the buffer cannot be typed in.
- =front-sticky= is what makes the run unmodifiable in the *middle*.
  With =rear-nonsticky= alone -- the comint idiom, and what this used to
  be -- Emacs decides inserted text would join neither neighbouring
  interval and permits the insertion, so only the run's edges were
  protected: the prompt glyph and every transcript block could be typed
  into.

The test asserts it by inserting mid-run, using the constant rather than
a copy of its value -- a literal in the test would assert how Emacs
behaves rather than how the harness marks its blocks, and would keep
passing after someone dropped =front-sticky= from the real one.

** Block ids, not positions

=cmacs-ai-harness-block-at= reports an =:id= that is unique for the life of the process. The buffer's region map is keyed on it, because positions shift when blocks are removed and ids do not.
