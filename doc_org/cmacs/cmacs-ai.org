#+TITLE: cmacs-ai
#+SUBTITLE: ai-glib coding agent for cmacs
#+OPTIONS: toc:2 num:nil

* Overview

The =cmacs-ai= subsystem wraps =ai-glib= (the multi-provider
GObject-based AI library) and surfaces it as a first-class
coding-agent surface inside cmacs.  It is independent of
=cmacs-libreclaw=: libreclaw orchestrates conversations across
channels (Matrix, email, the bridge); =cmacs-ai= is raw, low-
latency, single-conversation model invocation tuned for editing.

Enable with =--with-cmacs-ai= at configure time.  The canonical
=libai-glib-1.0.a= is built once from =deps/ai-glib= and shared
with =--with-cmacs-libreclaw= when both are enabled.

* Providers

| Symbol           | Wire     | Env / setup                          |
|------------------+----------+--------------------------------------|
| =claude=         | HTTP     | =ANTHROPIC_API_KEY= / =CLAUDE_API_KEY= |

| =gemini=         | HTTP     | =GEMINI_API_KEY=                     |
| =grok=           | HTTP     | =XAI_API_KEY= / =GROK_API_KEY=       |

| =opencode=       | CLI      | =opencode= on PATH                   |
| =claude-tmux=    | CLI/tmux | =claude= + tmux on PATH              |

* Chat buffers

=M-x cmacs-ai-chat= opens a fresh chat buffer in
=cmacs-ai-chat-mode= (derived from =org-mode=).  History above the
=* Compose= sentinel is read-only; =C-c C-c= sends the compose body
and streams the response into a fresh =** assistant= heading.

Keymap:

| Key         | Command                       |
|-------------+-------------------------------|
| =C-c C-c=   | =cmacs-ai-chat-send-compose=  |
| =C-c C-k=   | =cmacs-ai-chat-cancel-stream= |
| =C-c C-l=   | =cmacs-ai-chat-clear-history= |
| =C-c C-s=   | =cmacs-ai-chat-save=          |
| =C-c C-o=   | =cmacs-ai-chat-resume=        |

** Saving & resuming chats

Chats are archived automatically (mirroring how libreclaw persists
its rooms).  When =cmacs-ai-chat-autosave= is non-nil (the default) a
chat is written to =cmacs-ai-chat-dir= at three points: right after
you send a message, after each assistant response completes, and when
the buffer is killed — so a conversation survives a crash, a cancel,
or an accidental close.  The archive holds the conversation history
(the preamble and the turns above =* Compose=); the editable compose
region is excluded.  The file name comes from
=cmacs-ai-chat-save-name-format= (default
=%y%m%d-%H%M%S-<provider>.org=, e.g. =260605-142345-claude.org=).
=C-c C-s= (=cmacs-ai-chat-save=) writes the same archive on demand and
always works, regardless of =cmacs-ai-chat-autosave=.

=M-x cmacs-ai-resume-chat= (or =C-c C-o= from a chat buffer) reopens
an archived chat: it restores the transcript *and* rebuilds the
ai-glib session by replaying the visible turns, so the model keeps
full prior context and further messages append to the same file.
Picking an already-open resumed chat just switches to it.

Two things are intentionally not restored: tool-call / tool-result
blocks are replayed as plain text turns only (the rebuilt session
carries the conversation, not the verbatim tool I/O — this avoids
provider errors from an orphaned =tool_result=); and each chat is its
own archive file (there is no per-project single-file model like
libreclaw's cmacs channel).

* Generic calls

For scripting and user configs, =cmacs-ai-call= makes a one-shot AI
call from Elisp and returns the answer as a string -- with or without
tools.  It is the layer a config reaches for; gate on =IS-CMACS-AI= if
your config must also run on a build without =--with-cmacs-ai=.

#+begin_src emacs-lisp
;; Plain call, returns a string.
(cmacs-ai-call "Summarise this in one line: ...")
(cmacs-ai-call "why is the sky blue?" :provider 'ollama :model "llama3.2")

;; Agentic call: give the model the built-in tools (bash/read/write/
;; edit/glob/grep/ls/web_fetch); the final answer is returned.
(cmacs-ai-call "What files are in my home directory?" :builtin-tools t)
#+end_src

=cmacs-ai-call= takes a plist: =:provider= (symbol), =:system=,
=:model=, =:max-tokens=, =:tools= (a list of tool specs),
=:builtin-tools=, =:mcp-bridge= (expose the cmacs MCP surface; needs
=--with-cmacs-mcp=), and =:search-provider=.  Any tool option builds a
throwaway executor, uses it, and frees it under =unwind-protect=.  It
signals =cmacs-ai-error= on failure.

*Custom tools.*  =cmacs-ai-define-tool= builds a tool spec whose Elisp
callback's *return value* is handed back to the model -- so the model
can act on it:

#+begin_src emacs-lisp
(cmacs-ai-call
 "How many lines are in ~/.bashrc?"
 :tools (list (cmacs-ai-define-tool
               "count_lines" "Count the lines in a file"
               '(("path" "string" "Absolute file path" t))
               (lambda (_name input _id)
                 (let ((path (alist-get 'path (json-parse-string
                                               input :object-type 'alist))))
                   (number-to-string
                    (with-temp-buffer
                      (insert-file-contents (expand-file-name path))
                      (count-lines (point-min) (point-max)))))))))
#+end_src

The callback is called as =(funcall CALLBACK NAME INPUT-JSON ID)= and
must return a string (nil signals a tool error to the model).  The
executor runs synchronously on the main thread, so callbacks may safely
touch buffers and Emacs state.

Under the hood, =cmacs-ai-call= wraps the C primitive =cmacs-ai--call=
(positional: =PROMPT &optional PROVIDER SYSTEM MODEL EXECUTOR
MAX-TOKENS=); the no-tools path is equivalent to =cmacs-ai-prompt-sync=.

** From C, cmacsgi, D-Bus, emacsctl, and MCP

Because the calls are DEFUNs, C code and any client of the eval bridge
can drive them.  =cmacsgi eval '(cmacs-ai-call "...")'= works with no
extra plumbing.  Typed convenience verbs exist too:

- *emacsctl*: =emacsctl ai prompt= (no tools) and =emacsctl ai call=
  (add =-t/--tools= for the built-in agent tools).  Both take
  =-p/--provider=, =-m/--model=, =-s/--system=, =-f/--file=, positional
  prompt, or stdin.
- *D-Bus*: =org.cmacs.Editor1.Ai.Prompt (ssss)= and
  =org.cmacs.Editor1.Ai.Call (ssssb)= (the trailing boolean enables the
  built-in tools).
- *MCP*: the =ai_prompt= and =ai_call= tools (=ai_call= takes a
  =tools= boolean).

External callers cannot register Elisp tools, so their tool-enabled
call uses the server-side built-in executor.

*DANGER (=--gowl=).*  A tool-enabled call runs a synchronous multi-turn
loop (capped at ~20 turns) on the target's main thread.  Under =emacs
--gowl= that thread is the Wayland compositor -- a long loop freezes the
desktop.  Keep external tool loops short, and prefer =ai prompt= (no
tools) when driving a live =--gowl= session.

* Inline ghost-text completion

=cmacs-ai-completion-mode= is a buffer-local minor mode that
drives idle-timer FIM completion.  After
=cmacs-ai-completion-idle-delay= seconds of no input, a request is
fired with the buffer prefix+suffix as FIM context; the result
renders as a =shadow=-faced overlay accepted with =TAB=.

Default provider is =claude-code= to avoid per-keystroke HTTP
costs.  Override via =cmacs-ai-completion-provider=.

* Voice loop

=M-x cmacs-ai-voice-chat= opens a chat buffer wired for full voice
round-trip:

1. =cmacs-whisper-dictate= transcribes recorded speech.
2. =ai-glib= streams the reply.
3. =cmacs-piper-speak-region= speaks each completed sentence as it
   streams in.

Requires =cmacs-whisper=, =cmacs-piper=, =cmacs-audio= all enabled.

* Coding agent

=M-x cmacs-ai-agent-open= opens (or resumes) the agent chat for
the current project root.  Before the first turn it builds a
project-aware system prompt:

- The first matching file from =cmacs-ai-agent-project-files=
  (default: =CLAUDE.md=, =AGENTS.md=, =README.org=, =README.md=) is
  read in full and attached as the "Project agent contract".
- The absolute project root path is included.

This makes the assistant honor the project's own conventions
without manual cut-and-paste.

* Tool use

=cmacs-ai-tools-new= returns an =AiToolExecutor= handle with
ai-glib's built-ins pre-registered: =bash=, =read=, =write=,
=edit=, =glob=, =grep=, =ls=, =web_fetch=.  Per the project default
all tools are enabled (full trust).  Set =cmacs-ai-tool-confirm=
to ='destructive= for a per-call prompt on bash/write/edit, or to a
function for custom approval.

The =web_fetch= built-in is model-aware: HTML responses are converted
to readable markdown-style text (scripts and styles stripped, headings
and links preserved; images surface as Markdown =![alt](URL)= with the
src resolved to an absolute URL, so the model can cite or embed real
image links), =http://= URLs are upgraded to =https://=, a real
=User-Agent= and a 30-second timeout are applied, and converted bodies
are cached in-process for 15 minutes.  It accepts an optional =prompt=
argument -- when the model supplies one, a sub-model reads the fetched
page and returns only the requested information instead of the whole
page (extraction runs through the chat's active provider).

Each chat buffer is /also/ auto-augmented with cmacs's own MCP tool
surface (buffer / file / project / eval / apropos / describe by
default) on top of these built-ins -- see [[*MCP bridge][MCP bridge]] below.

Custom Elisp tools are registered via =cmacs-ai-tools-register=:

#+BEGIN_SRC elisp
(let ((exec (cmacs-ai-tools-new)))
  (cmacs-ai-tools-register
   exec
   "open-file"
   "Open FILE in cmacs."
   (cons '(("file" "string" "Path to open" t))
         (lambda (_name input-json _id)
           (find-file (alist-get 'file
                                  (json-read-from-string input-json)))
           "opened"))))
#+END_SRC

** Web search

ai-glib's =web_search= tool returns ranked results (title, URL, source
domain, snippet) and can optionally fetch the top results' pages.
Unlike =web_fetch= it is not a free built-in -- it is registered on a
chat/agent buffer's executor only when a search backend is configured.
=cmacs-ai-chat--init= does this automatically from
=cmacs-ai-search-provider= (default ='auto=):

| Provider symbol | Backend                                          |
|-----------------+--------------------------------------------------|
| =auto=          | Brave or Bing if its key is set, else DuckDuckGo |
| =brave=         | Brave Search (needs a key)                       |
| =bing=          | Bing Search (needs a key)                        |
| =duckduckgo=    | Keyless DuckDuckGo (best-effort, no SLA)         |
| =nil=           | Disabled                                         |

Keyed backends read =cmacs-ai-search-api-key=, falling back to the
=BRAVE_API_KEY= / =BING_API_KEY= environment variable.  A keyed
provider with no key available logs a message and leaves =web_search=
off; =auto= always succeeds thanks to the keyless fallback.

Once registered, the model may pass the tool's options: =count=,
=freshness= (any/day/week/month/year), =safesearch=
(off/moderate/strict), =country=, =language=, =site=, and
=fetch_content= (fetch and attach the top results' page text via the
=web_fetch= pipeline).  Results are cached in-process for 5 minutes.

Switch the backend for an open chat at runtime with
=M-x cmacs-ai-chat-set-search-provider=.  Inspect the active tool set
with =(cmacs-ai-tools-list EXECUTOR)= -- it lists the built-ins,
=web_search= (once a provider is set), custom tools, and bridged MCP
tools.

#+BEGIN_SRC elisp
;; Enable web_search explicitly on a standalone executor.
(let ((exec (cmacs-ai-tools-new)))
  (cmacs-ai-tools-set-search-provider exec 'duckduckgo)
  (member "web_search" (cmacs-ai-tools-list exec)))   ; => t
#+END_SRC

** Inline images

When =cmacs-ai-chat-inline-images= is non-nil (the default), image
links in an assistant response render inline after each turn.  Have
the model embed images as bare Org links, e.g.
=[[https://host/pic.png]]= (a described link =[[url][text]]= shows the
text, not the image).  Local/file images are previewed synchronously
via Org; remote =http(s)= images are fetched *asynchronously* and
shown when they arrive, so a slow or dead URL never blocks Emacs
(Org's own remote-image download is synchronous and would freeze the
UI).  Non-image responses, error statuses, and undecodable data are
ignored silently.  Image width is capped at
=cmacs-ai-chat-image-max-width= (or ~92% of the chat window).
Toggling =org-link-preview= (=C-c C-x C-v=) clears the previews.

* Image generation

Generate an image and put it where you are working.  In an Org buffer the
image is attached to the current node, linked, and previewed inline; the
same machinery is reachable from an =ai-image= babel block, from the chat
buffer, and over MCP / D-Bus / =emacsctl=.

** Quick start

With point in an Org buffer, under a heading:

: M-x cmacs-ai-image RET a brass telescope on a wooden desk RET

A moment later the buffer contains:

#+BEGIN_EXAMPLE
,* My heading
:PROPERTIES:
:ID:       8f3a1c22-...
:END:

,#+CAPTION: a brass telescope on a wooden desk
[[attachment:cmacs-ai-20260728-142233.png]]
#+END_EXAMPLE

...with the image rendered inline.  The bytes live in the node's
=org-attach= directory, so the figure travels with the node, is found by
export, and survives the file being moved.

Generation is asynchronous: Emacs stays responsive for the tens of
seconds these take, and the image appears when it arrives.

** Providers, models and capabilities

Only three providers generate images.  Claude and Ollama expose no image
API at all, and asking them says so rather than failing obscurely.

| Provider | Models                                                    | Reference images                          |
|----------+-----------------------------------------------------------+-------------------------------------------|
| Gemini   | Nano Banana, Nano Banana 2, Nano Banana Pro, Imagen 4 / 3 | up to 14 (Nano Banana Pro); none (Imagen) |
| OpenAI   | GPT Image 2 / 1.5 / 1, DALL-E 3 / 2                       | up to 16 (GPT Image); 1 + mask (DALL-E 2) |
| Grok     | Grok Imagine, Grok Imagine Quality, Grok 2 Image          | 1 (Imagine); none (Grok 2)                |

Models differ in far more than that.  =M-x cmacs-ai-image-list-models=
opens a buffer listing each model's limits, geometry vocabulary and
capabilities; =cmacs-ai-image-models= returns the same thing as data.

Options a model cannot honour are dropped rather than sent and rejected,
so a request aimed at the wrong model degrades instead of erroring.  Two
things are never dropped silently, because doing so would change the
result invisibly: reference images beyond a model's limit, and an
unsupported operation.

** Where images are stored

In Org, =org-attach= takes ownership.  If the node has no =ID= or =DIR=
property yet, one is created -- that is how Org locates the attachment
directory, and it is why an =:ID:= appears in the example above.

Everywhere else -- a non-Org buffer, a read-only one, or a position
before the first heading, where there is no node to attach to -- the
image goes to =cmacs-ai-image-dir= (default
=$XDG_DATA_HOME/cmacs-ai/images/=) and a bare path is inserted instead of
a link.  A message says which happened.

=cmacs-ai-image-attach-method= controls whether the file is moved
(default) or copied into the attachment directory.  Generated images
start in a temporary file, so moving is both correct and cheaper.

*** Illustrating prose you have already written

=cmacs-ai-image-from-selected-text= is the one to reach for when the
text describing the picture is already in the buffer.  Select it and run
the command: the selection becomes the prompt, is left exactly as it
was, and the image goes in on a fresh line immediately after it.

#+BEGIN_EXAMPLE
,* Chapter one
A hyacinth macaw perched on a brass telescope, cinematic lighting.
    <- select this line, M-x cmacs-ai-image-from-selected-text

,* Chapter one
A hyacinth macaw perched on a brass telescope, cinematic lighting.
,#+CAPTION: A hyacinth macaw perched on a brass telescope, cinematic lighting.
[[attachment:cmacs-ai-20260728-142233.png]]
#+END_EXAMPLE

=cmacs-ai-image= also accepts the region as a prompt, but inserts at
point -- and point sits at whichever end of the region you finished
selecting at, so the image can land *above* the text instead of below
it.  This command always puts it after.

The insertion point is held with a marker, so it stays correct even if
you carry on editing elsewhere in the buffer while the image generates.

Suggested bindings, beside the other cmacs-ai ones:

#+BEGIN_SRC elisp
(global-set-key (kbd "C-c a i i") #'cmacs-ai-image)
(global-set-key (kbd "C-c a i s") #'cmacs-ai-image-from-selected-text)
(global-set-key (kbd "C-c a i e") #'cmacs-ai-image-edit)
(global-set-key (kbd "C-c a i r") #'cmacs-ai-image-regenerate)
(global-set-key (kbd "C-c a i m") #'cmacs-ai-image-list-models)
#+END_SRC

** Parameters

=cmacs-ai-image-generate-async= takes an options plist covering the whole
request surface.  Omitting a key leaves the provider on its own default
rather than on ours:

| Group      | Keys                                                        |
|------------+-------------------------------------------------------------|
| Prompt     | =:prompt= =:negative= =:system=                             |
| Operation  | =:operation= (generate / edit / variation / upscale)        |
| Geometry   | =:size= =:custom-size= =:aspect= =:resolution=              |
| Appearance | =:quality= =:style= =:style-preset= =:background=           |
| Output     | =:format= =:compression= =:response-format=                 |
| Sampling   | =:seed= =:guidance= =:steps= =:strength= =:temperature= =:top-p= =:top-k= |
| Policy     | =:moderation= =:person-generation= =:watermark= =:enhance-prompt= =:language= |
| Editing    | =:references= =:mask= =:fidelity= =:partial-images=         |
| Escape     | =:extra= (plist spliced verbatim into the request body)     |

Geometry is expressed two incompatible ways: the Gemini family thinks in
aspect ratios plus a resolution tier, OpenAI in pixel dimensions.  Both
are carried, and each provider uses whichever applies, so you need not
know which is in play.

=:extra= exists because image APIs gain parameters faster than a binding
can track them.  Nothing in it is validated; an unknown key reaches the
provider exactly as written.

** Reference images and editing

This is what makes Nano Banana Pro worth reaching for: several input
images, each doing a different job.

: M-x cmacs-ai-image-edit

References come from the image at point, from the marked files in Dired,
or are read one at a time.  With a prefix argument each is also given a
*role*:

#+BEGIN_SRC elisp
(cmacs-ai-image-edit
 "combine these into a concert poster"
 '(("palette.png" . "style")
   ("macaw.jpg"   . "subject")
   ("venue.jpg"   . "background")))
#+END_SRC

Order is preserved and significant.  Roles matter because no wire format
has a field for them -- ai-glib folds the labels into the prompt text,
which is the only channel the model reads.  Unlabelled references are
passed through in order.

For a masked edit, the transparent areas of the mask are the ones
regenerated:

#+BEGIN_SRC elisp
(cmacs-ai-image-generate-async
 handle "replace the sky with a storm" #'ignore
 '(:operation "edit" :references ("photo.png") :mask "sky-mask.png"
   :fidelity "high"))
#+END_SRC

** The =ai-image= babel block

Lets a figure live in the document that describes it:

#+BEGIN_EXAMPLE
,#+BEGIN_SRC ai-image :provider gemini :aspect 16:9 :resolution 2k
A hyacinth macaw perched on a brass telescope, cinematic lighting
,#+END_SRC
#+END_EXAMPLE

=C-c C-c= generates and puts the link in =#+RESULTS:=, so re-evaluating
regenerates the figure in place.  Register the language first, as with
the =ai= block:

: (cmacs-ai-image-block-register)

| Header arg   | Meaning                                              |
|--------------+------------------------------------------------------|
| =:provider=  | gemini / openai / grok                               |
| =:model=     | model id                                             |
| =:file=      | write here instead of attaching to the node          |
| =:ref=       | reference image, =PATH= or =PATH::ROLE=; repeatable  |
| =:aspect= =:size= =:resolution= | geometry                          |
| =:count= =:quality= =:style= =:background= =:format= =:compression= | as above |
| =:negative= =:seed= =:guidance= =:steps= =:strength= | as above           |
| =:moderation= =:fidelity= =:operation= | as above                       |

This path is *synchronous* -- org-babel has no async protocol -- so it
blocks for as long as generation takes.  =cmacs-ai-image-timeout=
(default 180 s) bounds the wait.

** Chat integration

Two ways to get an image out of a chat buffer.

=/image PROMPT= in the compose region generates one directly, with no
model turn involved.

The =generate_image= tool lets the model decide to draw something
mid-conversation.  It is on by default; set
=cmacs-ai-chat-enable-image-tool= to nil to withhold it.  Generated
images are attached to the chat node, so the existing end-of-turn preview
renders them.

The tool is deliberately *not* named =ai_generate_image=.  The MCP bridge
hides every tool matching =^ai_= from in-process chat buffers to stop the
model calling itself recursively, and an in-process chat buffer is
exactly where this one has to be visible.

** MCP, D-Bus and emacsctl

The same generation is reachable without an Emacs UI:

#+BEGIN_SRC sh
emacsctl ai generate-image -p gemini -a 16:9 "a brass telescope"

emacsctl ai generate-image \
  -m gemini-3-pro-image-preview \
  -r logo.png::style -r subject.jpg::subject \
  -b notes.org "combine these into a poster"
#+END_SRC

The MCP tool is =generate_image=; the D-Bus method is =GenerateImage= on
=org.cmacs.Editor1.Ai=.  All three block the cmacs main thread for the
duration, which is tens of seconds -- worth knowing before wiring one
into something latency-sensitive.

References travel as a single comma-separated =PATH= or =PATH::ROLE=
string on all three surfaces, because the MCP bridge's schema translator
cannot carry a nested list.

** Troubleshooting

- *"provider does not support image generation"* -- you asked Claude or
  Ollama.  Use gemini, openai or grok.

- *"Authentication failed"* -- the provider's key is missing from the
  environment: =GEMINI_API_KEY=, =OPENAI_API_KEY=, =XAI_API_KEY=.

- *The model answered with text* -- surfaces as an invalid-response
  error rather than an empty success.  Usually the prompt was declined;
  rephrasing helps.

- *A content-policy refusal* -- arrives as an invalid-request error with
  the provider's own explanation quoted, which is the useful part.

- *"attaching failed; using ..."* -- there was no Org node to attach to
  (before the first heading, or a read-only buffer).  The image was
  saved to =cmacs-ai-image-dir= instead; nothing was lost.

- *An option seemed to be ignored* -- it probably was, because the model
  does not support it.  =cmacs-ai-image-list-models= says which does
  what.

** Low-level API

| Function                          | Purpose                                  |
|-----------------------------------+------------------------------------------|
| =cmacs-ai-image-generate-async=   | generate; returns a job handle           |
| =cmacs-ai-image-generate-sync=    | blocking variant, for org-babel          |
| =cmacs-ai-image-cancel=           | abandon a job by handle                  |
| =cmacs-ai-image-models=           | per-model capabilities and limits        |

The async callback receives

: (:images ((:data BYTES :mime M :url U :base64 B :revised R) ...))

or =(:error MSG)=.  =BYTES= is a unibyte string, already materialised
whether the provider returned inline data or a URL -- so a caller can
write it straight to a file without knowing which.

* GObject Introspection

The cmacs-ai init path prepends
=$top_srcdir/deps/ai-glib/build/release= to GIRepository's search
path and eagerly requires =AiGlib-1.0=.  After =init_cmacs_ai=
runs, the typelib is reachable from:

- Elisp: =(gi-require "AiGlib" "1.0")= returns =t=.
- The bacon =cmacsgi= builtin.
- The MCP =gi_*= tools.

* MCP tools

Built with =--with-cmacs-mcp=, six tools are exposed:

| Tool                | Args                                       |
|---------------------+--------------------------------------------|
| =ai_prompt=         | =prompt= req, =provider=, =system=, =model= |
| =ai_call=           | as =ai_prompt= + =tools= (bool; built-in agent tools) |
| =ai_list_providers= | (none)                                     |
| =ai_list_models=    | =provider= (opt; default: all providers)   |
| =ai_open_chat=      | =prompt=, =provider=, =model= (all opt)    |
| =generate_image=    | =prompt= req, =references=, =provider=, =model=, =aspect=, =size=, =quality=, =buffer= |

=ai_list_models= returns a JSON object mapping each provider to its
model-name array (network for API providers, static tables for CLI
providers); an unavailable provider reports inline instead of
failing the call.  The underlying DEFUNs are
=cmacs-ai-list-models PROVIDER= and =cmacs-ai-prompt-sync PROMPT
&optional PROVIDER SYSTEM MODEL=.  D-Bus parity:
=org.cmacs.Editor1.Ai= (=ListProviders= / =ListModels= / =Prompt= /
=OpenChat=).

* MCP bridge

The /outbound/ direction (above) lets external agents drive the
in-editor AI.  The /inbound/ mirror -- this section -- lets the
in-process AI drive cmacs's own MCP tool surface.

Each chat buffer's =AiToolExecutor= is automatically augmented with
cmacs's editor-aware tools (buffer / file / project / eval / apropos
/ describe by default), so the model gets the same toolset external
Claude Code already uses to drive cmacs, on top of ai-glib's
filesystem-level built-ins.

Without the bridge, AI edits land on disk bypassing cmacs buffers
(no undo, no save-hooks); with it, edits go through =edit_buffer= /
=replace_in_buffer= and respect editor invariants.

** Default allowlist

| Tool group           | Tools                                              |
|----------------------+----------------------------------------------------|
| eval / introspection | =eval=, =describe_function=, =describe_variable=, =apropos=, =completions= |
| buffer               | =list_buffers=, =get_buffer_content=, =set_buffer_content=, =create_buffer=, =edit_buffer=, =replace_in_buffer=, =search_buffer=, =goto_line= |
| window               | =list_windows=, =list_frames=                       |
| project              | =project_root=, =project_read_file=, =project_list_files=, =project_find_files=, =project_grep= |
| process + debug      | =list_processes=, =backtrace=, =memory_info=, =process_status=, =recent_messages=, =describe_mode=, =list_hooks= |

** Extending

Patterns are PCRE (the bridge uses GLib's GRegex), NOT Emacs
=\`X\'= syntax.  To add shell access + the full GObject Introspection
surface:

#+BEGIN_SRC elisp
(dolist (re '("^bacon_eval$" "^crispy_eval$" "^gi_"))
  (add-to-list 'cmacs-ai-mcp-bridge-allowlist re))
#+END_SRC

To open a single read-only chat:

#+BEGIN_SRC elisp
(let ((cmacs-ai-mcp-bridge-readonly-only t))
  (cmacs-ai-chat 'claude))
#+END_SRC

** Recursion guard

The C layer always denies =^ai_= regardless of allowlist contents,
to prevent the in-process AI from invoking =ai_open_chat= /
=ai_prompt= on itself.  Not configurable.

** Trust

Bridged MCP tools obey =cmacs-ai-tool-confirm= the same way ai-glib's
built-ins do (see /Tool use/).  Default nil = full trust.
