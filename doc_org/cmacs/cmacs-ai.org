#+TITLE: cmacs-ai
#+SUBTITLE: ai-glib coding agent for cmacs
#+OPTIONS: toc:2 num:nil

* Overview

The =cmacs-ai= subsystem wraps =ai-glib= (the multi-provider
GObject-based AI library) and surfaces it as a first-class
coding-agent surface inside cmacs.  It is independent of
=cmacs-libreclaw=: libreclaw orchestrates conversations across
channels (Matrix, email, the bridge); =cmacs-ai= is raw, low-
latency, single-conversation model invocation tuned for editing.

Enable with =--with-cmacs-ai= at configure time.  The canonical
=libai-glib-1.0.a= is built once from =deps/ai-glib= and shared
with =--with-cmacs-libreclaw= when both are enabled.

* Providers

| Symbol           | Wire     | Env / setup                          |
|------------------+----------+--------------------------------------|
| =claude=         | HTTP     | =ANTHROPIC_API_KEY= / =CLAUDE_API_KEY= |
| =openai=         | HTTP     | =OPENAI_API_KEY=                     |
| =gemini=         | HTTP     | =GEMINI_API_KEY=                     |
| =grok=           | HTTP     | =XAI_API_KEY= / =GROK_API_KEY=       |
| =ollama=         | HTTP     | =OLLAMA_HOST= (default localhost)    |
| =claude-code=    | CLI      | =claude= on PATH                     |
| =opencode=       | CLI      | =opencode= on PATH                   |
| =claude-tmux=    | CLI/tmux | =claude= + tmux on PATH              |
| =grok-build=     | CLI      | =grok= on PATH (or =GROK_PATH=)      |

=grok= and =grok-build= are two different backends, not two names for one. =grok= is xAI's HTTP API and takes API model ids; =grok-build= wraps the agentic =grok= CLI and takes /its/ model ids (=grok-4.6=, =grok-4.5=), which the API rejects and vice versa. Run =grok models= to see what the installed CLI offers.

Three things about =grok-build= differ from the other CLI providers:

- It carries no =mcp-config-path=, so =cmacs-ai-client-set-mcp-config= returns nil for it and a grok-build agent gets no cmacs tools — only grok's own built-ins. (=opencode= is the same.)
- Skipping permissions on it emits =--permission-mode bypassPermissions=, which also lifts grok's sandbox. The client's working directory is then the only bound on what it can reach; see [[*Why a CLI agent could not call its tools][Why a CLI agent could not call its tools]].
- =max-tokens= does nothing: =grok= has no such flag. Bound a run with a smaller model instead.

* Chat buffers

=M-x cmacs-ai-chat= opens a fresh chat buffer in
=cmacs-ai-chat-mode= (derived from =org-mode=).  History above the
=* Compose= sentinel is read-only; =C-c C-c= sends the compose body
and streams the response into a fresh =** assistant= heading.

** One heading per exchange

What you send produces exactly one =** TIMESTAMP provider/model= heading, no
matter how many times the model stops to call a tool along the way. Tool calls
and their results nest under it as =***= entries, and whatever the model says
after them continues beneath.

The heading is opened by the model's first *text*, not by the stream. A model
segment that only calls a tool has nothing to show, and creating its heading up
front is what used to litter a transcript with empty ones — a bootstrap that
read six files produced seven headings, most of them blank.

Two things follow that are worth knowing if you write code against this:

- =cmacs-ai-chat--assistant-marker= is nil in the gaps between the streams of a
  tool loop. It means "no segment is appending right now", not "the chat is
  idle".
- =cmacs-ai-chat--turn-open= is the one that spans the whole exchange. Anything
  asking whether the chat is busy — the brigade loopback, for one — has to read
  that, or it will deliver a message into the middle of a turn.

Keymap:

| Key         | Command                       |
|-------------+-------------------------------|
| =C-c C-c=   | =cmacs-ai-chat-send-compose=  |
| =C-c C-k=   | =cmacs-ai-chat-cancel-stream= |
| =C-c C-l=   | =cmacs-ai-chat-clear-history= |
| =C-c C-s=   | =cmacs-ai-chat-save=          |
| =C-c C-o=   | =cmacs-ai-chat-resume=        |

** Saving & resuming chats

Chats are archived automatically (mirroring how libreclaw persists
its rooms).  When =cmacs-ai-chat-autosave= is non-nil (the default) a
chat is written to =cmacs-ai-chat-dir= at three points: right after
you send a message, after each assistant response completes, and when
the buffer is killed — so a conversation survives a crash, a cancel,
or an accidental close.  The archive holds the conversation history
(the preamble and the turns above =* Compose=); the editable compose
region is excluded.  The file name comes from
=cmacs-ai-chat-save-name-format= (default
=%y%m%d-%H%M%S-<provider>.org=, e.g. =260605-142345-claude.org=).
=C-c C-s= (=cmacs-ai-chat-save=) writes the same archive on demand and
always works, regardless of =cmacs-ai-chat-autosave=.

=M-x cmacs-ai-resume-chat= (or =C-c C-o= from a chat buffer) reopens
an archived chat: it restores the transcript *and* rebuilds the
ai-glib session by replaying the visible turns, so the model keeps
full prior context and further messages append to the same file.
Picking an already-open resumed chat just switches to it.

Two things are intentionally not restored: tool-call / tool-result
blocks are replayed as plain text turns only (the rebuilt session
carries the conversation, not the verbatim tool I/O — this avoids
provider errors from an orphaned =tool_result=); and each chat is its
own archive file (there is no per-project single-file model like
libreclaw's cmacs channel).

* Generic calls

For scripting and user configs, =cmacs-ai-call= makes a one-shot AI
call from Elisp and returns the answer as a string -- with or without
tools.  It is the layer a config reaches for; gate on =IS-CMACS-AI= if
your config must also run on a build without =--with-cmacs-ai=.

#+begin_src emacs-lisp
;; Plain call, returns a string.
(cmacs-ai-call "Summarise this in one line: ...")
(cmacs-ai-call "why is the sky blue?" :provider 'ollama :model "llama3.2")

;; Agentic call: give the model the built-in tools (bash/read/write/
;; edit/glob/grep/ls/web_fetch); the final answer is returned.
(cmacs-ai-call "What files are in my home directory?" :builtin-tools t)
#+end_src

=cmacs-ai-call= takes a plist: =:provider= (symbol), =:system=,
=:model=, =:max-tokens=, =:tools= (a list of tool specs),
=:builtin-tools=, =:mcp-bridge= (expose the cmacs MCP surface; needs
=--with-cmacs-mcp=), =:search-provider=, and =:directory=.  Any tool
option builds a throwaway executor, uses it, and frees it under
=unwind-protect=.  It signals =cmacs-ai-error= on failure.

** Where the built-in tools run

=:directory= decides where the built-in tools work: relative paths
resolve against it, and =bash= runs its command there.

#+begin_src emacs-lisp
(cmacs-ai-call "what is in this project, and does it build?"
               :builtin-tools t
               :directory "~/src/project")
#+end_src

Without it they use the Emacs process's own working directory, which for
a long-lived editor is wherever you last visited a file — almost never
what the model meant by =src/main.c=. An absolute path from the model is
always used as given.

The same knob exists on an executor you build yourself:

#+begin_src emacs-lisp
(let ((exec (cmacs-ai-tools-new)))
  (cmacs-ai-tools-set-working-directory exec "~/src/project")
  ...)
#+end_src

=nil= restores the default. Underneath, this is ai-glib's
=ai_tool_executor_set_working_directory=; =bash= spawns through
=GSubprocess= rather than =popen= so the directory can be set at all,
which also makes the command cancellable and keeps its output valid
UTF-8.

*Custom tools.*  =cmacs-ai-define-tool= builds a tool spec whose Elisp
callback's *return value* is handed back to the model -- so the model
can act on it:

#+begin_src emacs-lisp
(cmacs-ai-call
 "How many lines are in ~/.bashrc?"
 :tools (list (cmacs-ai-define-tool
               "count_lines" "Count the lines in a file"
               '(("path" "string" "Absolute file path" t))
               (lambda (_name input _id)
                 (let ((path (alist-get 'path (json-parse-string
                                               input :object-type 'alist))))
                   (number-to-string
                    (with-temp-buffer
                      (insert-file-contents (expand-file-name path))
                      (count-lines (point-min) (point-max)))))))))
#+end_src

The callback is called as =(funcall CALLBACK NAME INPUT-JSON ID)= and
must return a string (nil signals a tool error to the model).

Callbacks may safely touch buffers and Emacs state. On the synchronous
=cmacs-ai-call= path they simply run on the main thread; on the
background path (=cmacs-ai-tools-run-async=, which is what an in-process
brigade agent uses) the tool loop runs on a worker thread, so the call is
marshalled to the main thread and waited for. It has to be: Emacs's
allocator is not thread-safe, so every =Lisp_Object= involved must be
built where Lisp lives, and only C strings cross the boundary.

The run's own messages — the assistant's turns and the results of any
tools it called — are appended back onto the session before the callback
fires. That is what lets the same session be run again as a continuation
rather than a restart: without it, ai-glib's executor copies the message
list, appends to its copy and frees it, so a second run would show the
model its original instruction and the new question with no trace of what
it had already said or done.

Because every turn re-sends the whole session, a conversation that runs
for dozens of turns costs quadratically in the number of turns — quietly,
since nothing about a long one looks different from a short one until the
bill arrives. =cmacs-ai-history-limit= (default 200 messages) caps it,
dropping from the oldest end. That end is both the part the model is
least likely to still need and the only part safe to lose: standing
instructions live in the client's system prompt, not in the message list,
so they are never what gets dropped. Zero or negative keeps everything,
which is right only if you are watching the cost yourself.

Note that =cmacs-ai-session-append-message= takes only =user= and
=assistant=. There is no =system= role here: a system prompt belongs to
the client, and is set with =cmacs-ai-client-set-system-prompt=.

=cmacs-ai-tool-call-timeout= (120 seconds) bounds that wait. The main
thread picks the call up from its GLib dispatch, which happens whenever
Emacs reaches the event loop, so in practice it is immediate; if it is
not, the agent gets a timeout error for that one tool rather than the
worker parking forever. Raise it if you have Elisp tools that
legitimately take minutes.

Under the hood, =cmacs-ai-call= wraps the C primitive =cmacs-ai--call=
(positional: =PROMPT &optional PROVIDER SYSTEM MODEL EXECUTOR
MAX-TOKENS=); the no-tools path is equivalent to =cmacs-ai-prompt-sync=.

** From C, cmacsgi, D-Bus, emacsctl, and MCP

Because the calls are DEFUNs, C code and any client of the eval bridge
can drive them.  =cmacsgi eval '(cmacs-ai-call "...")'= works with no
extra plumbing.  Typed convenience verbs exist too:

- *emacsctl*: =emacsctl ai prompt= (no tools) and =emacsctl ai call=
  (add =-t/--tools= for the built-in agent tools).  Both take
  =-p/--provider=, =-m/--model=, =-s/--system=, =-f/--file=, positional
  prompt, or stdin.
- *D-Bus*: =org.cmacs.Editor1.Ai.Prompt (ssss)= and
  =org.cmacs.Editor1.Ai.Call (ssssb)= (the trailing boolean enables the
  built-in tools).
- *MCP*: the =ai_prompt= and =ai_call= tools (=ai_call= takes a
  =tools= boolean).

External callers cannot register Elisp tools, so their tool-enabled
call uses the server-side built-in executor.

*DANGER (=--gowl=).*  A tool-enabled call runs a synchronous multi-turn
loop (capped at ~20 turns) on the target's main thread.  Under =emacs
--gowl= that thread is the Wayland compositor -- a long loop freezes the
desktop.  Keep external tool loops short, and prefer =ai prompt= (no
tools) when driving a live =--gowl= session.

* Inline ghost-text completion

=cmacs-ai-completion-mode= is a buffer-local minor mode that
drives idle-timer FIM completion.  After
=cmacs-ai-completion-idle-delay= seconds of no input, a request is
fired with the buffer prefix+suffix as FIM context; the result
renders as a =shadow=-faced overlay accepted with =TAB=.

Default provider is =claude-code= to avoid per-keystroke HTTP
costs.  Override via =cmacs-ai-completion-provider=.

* Voice loop

=M-x cmacs-ai-voice-chat= opens a chat buffer wired for full voice
round-trip:

1. =cmacs-whisper-dictate= transcribes recorded speech.
2. =ai-glib= streams the reply.
3. =cmacs-piper-speak-region= speaks each completed sentence as it
   streams in.

Requires =cmacs-whisper=, =cmacs-piper=, =cmacs-audio= all enabled.

* Coding agent

=M-x cmacs-ai-agent-open= opens (or resumes) the agent chat for
the current project root.  Before the first turn it builds a
project-aware system prompt:

- The first matching file from =cmacs-ai-agent-project-files=
  (default: =CLAUDE.md=, =AGENTS.md=, =README.org=, =README.md=) is
  read in full and attached as the "Project agent contract".
- The absolute project root path is included.

This makes the assistant honor the project's own conventions
without manual cut-and-paste.

* Tool use

=cmacs-ai-tools-new= returns an =AiToolExecutor= handle with
ai-glib's built-ins pre-registered: =bash=, =read=, =write=,
=edit=, =glob=, =grep=, =ls=, =web_fetch=.  Per the project default
all tools are enabled (full trust).  Set =cmacs-ai-tool-confirm=
to ='destructive= for a per-call prompt on bash/write/edit, or to a
function for custom approval.

The =web_fetch= built-in is model-aware: HTML responses are converted
to readable markdown-style text (scripts and styles stripped, headings
and links preserved; images surface as Markdown =![alt](URL)= with the
src resolved to an absolute URL, so the model can cite or embed real
image links), =http://= URLs are upgraded to =https://=, a real
=User-Agent= and a 30-second timeout are applied, and converted bodies
are cached in-process for 15 minutes.  It accepts an optional =prompt=
argument -- when the model supplies one, a sub-model reads the fetched
page and returns only the requested information instead of the whole
page (extraction runs through the chat's active provider).

Each chat buffer is /also/ auto-augmented with cmacs's own MCP tool
surface (buffer / file / project / eval / apropos / describe by
default) on top of these built-ins -- see [[*MCP bridge][MCP bridge]] below.

Custom Elisp tools are registered via =cmacs-ai-tools-register=:

#+BEGIN_SRC elisp
(let ((exec (cmacs-ai-tools-new)))
  (cmacs-ai-tools-register
   exec
   "open-file"
   "Open FILE in cmacs."
   (cons '(("file" "string" "Path to open" t))
         (lambda (_name input-json _id)
           (find-file (alist-get 'file
                                  (json-read-from-string input-json)))
           "opened"))))
#+END_SRC

** Web search

ai-glib's =web_search= tool returns ranked results (title, URL, source
domain, snippet) and can optionally fetch the top results' pages.
Unlike =web_fetch= it is not a free built-in -- it is registered on a
chat/agent buffer's executor only when a search backend is configured.
=cmacs-ai-chat--init= does this automatically from
=cmacs-ai-search-provider= (default ='auto=):

| Provider symbol | Backend                                          |
|-----------------+--------------------------------------------------|
| =auto=          | Brave or Bing if its key is set, else DuckDuckGo |
| =brave=         | Brave Search (needs a key)                       |
| =bing=          | Bing Search (needs a key)                        |
| =duckduckgo=    | Keyless DuckDuckGo (best-effort, no SLA)         |
| =nil=           | Disabled                                         |

Keyed backends read =cmacs-ai-search-api-key=, falling back to the
=BRAVE_API_KEY= / =BING_API_KEY= environment variable.  A keyed
provider with no key available logs a message and leaves =web_search=
off; =auto= always succeeds thanks to the keyless fallback.

Once registered, the model may pass the tool's options: =count=,
=freshness= (any/day/week/month/year), =safesearch=
(off/moderate/strict), =country=, =language=, =site=, and
=fetch_content= (fetch and attach the top results' page text via the
=web_fetch= pipeline).  Results are cached in-process for 5 minutes.

Switch the backend for an open chat at runtime with
=M-x cmacs-ai-chat-set-search-provider=.  Inspect the active tool set
with =(cmacs-ai-tools-list EXECUTOR)= -- it lists the built-ins,
=web_search= (once a provider is set), custom tools, and bridged MCP
tools.

#+BEGIN_SRC elisp
;; Enable web_search explicitly on a standalone executor.
(let ((exec (cmacs-ai-tools-new)))
  (cmacs-ai-tools-set-search-provider exec 'duckduckgo)
  (member "web_search" (cmacs-ai-tools-list exec)))   ; => t
#+END_SRC

** Inline images

When =cmacs-ai-chat-inline-images= is non-nil (the default), image
links in an assistant response render inline after each turn.  Have
the model embed images as bare Org links, e.g.
=[[https://host/pic.png]]= (a described link =[[url][text]]= shows the
text, not the image).  Local/file images are previewed synchronously
via Org; remote =http(s)= images are fetched *asynchronously* and
shown when they arrive, so a slow or dead URL never blocks Emacs
(Org's own remote-image download is synchronous and would freeze the
UI).  Non-image responses, error statuses, and undecodable data are
ignored silently.  Image width is capped at
=cmacs-ai-chat-image-max-width= (or ~92% of the chat window).
Toggling =org-link-preview= (=C-c C-x C-v=) clears the previews.

* Image generation

Generate an image and put it where you are working.  In an Org buffer the
image is attached to the current node, linked, and previewed inline; the
same machinery is reachable from an =ai-image= babel block, from the chat
buffer, and over MCP / D-Bus / =emacsctl=.

** Quick start

With point in an Org buffer, under a heading:

: M-x cmacs-ai-image RET a brass telescope on a wooden desk RET

A moment later the buffer contains:

#+BEGIN_EXAMPLE
,* My heading
:PROPERTIES:
:ID:       8f3a1c22-...
:END:

,#+CAPTION: a brass telescope on a wooden desk
[[attachment:cmacs-ai-20260728-142233.png]]
#+END_EXAMPLE

...with the image rendered inline.  The bytes live in the node's
=org-attach= directory, so the figure travels with the node, is found by
export, and survives the file being moved.

Generation is asynchronous: Emacs stays responsive for the tens of
seconds these take, and the image appears when it arrives.

** Providers, models and capabilities

Only three providers generate images.  Claude and Ollama expose no image
API at all, and asking them says so rather than failing obscurely.

| Provider | Models                                                    | Reference images                          |
|----------+-----------------------------------------------------------+-------------------------------------------|
| Gemini   | Nano Banana, Nano Banana 2, Nano Banana Pro, Imagen 4 / 3 | up to 14 (Nano Banana Pro); none (Imagen) |
| OpenAI   | GPT Image 2 / 1.5 / 1, DALL-E 3 / 2                       | up to 16 (GPT Image); 1 + mask (DALL-E 2) |
| Grok     | Grok Imagine, Grok Imagine Quality, Grok 2 Image          | 1 (Imagine); none (Grok 2)                |

Models differ in far more than that.  =M-x cmacs-ai-image-list-models=
opens a buffer listing each model's limits, geometry vocabulary and
capabilities; =cmacs-ai-image-models= returns the same thing as data.

Options a model cannot honour are dropped rather than sent and rejected,
so a request aimed at the wrong model degrades instead of erroring.  Two
things are never dropped silently, because doing so would change the
result invisibly: reference images beyond a model's limit, and an
unsupported operation.

** Where images are stored

In Org, =org-attach= takes ownership.  If the node has no =ID= or =DIR=
property yet, one is created -- that is how Org locates the attachment
directory, and it is why an =:ID:= appears in the example above.

Everywhere else -- a non-Org buffer, a read-only one, or a position
before the first heading, where there is no node to attach to -- the
image goes to =cmacs-ai-image-dir= (default
=$XDG_DATA_HOME/cmacs-ai/images/=) and a bare path is inserted instead of
a link.  A message says which happened.

=cmacs-ai-image-attach-method= controls whether the file is moved
(default) or copied into the attachment directory.  Generated images
start in a temporary file, so moving is both correct and cheaper.

** Commands

| Command                       | What it does                                        |
|-------------------------------+-----------------------------------------------------|
| =cmacs-ai-image-menu=         | transient: compose a request option by option       |
| =cmacs-ai-image=              | generate from a prompt, or the active region        |
| =cmacs-ai-image-from-selected-text= | illustrate the selection, inserting after it  |
| =cmacs-ai-image-edit=         | generate conditioned on reference images            |
| =cmacs-ai-image-regenerate=   | re-run the image at point from its =#+CAPTION=      |
| =cmacs-ai-image-variations=   | several images for one prompt                       |
| =cmacs-ai-image-save-as=      | copy the image at point elsewhere                   |
| =cmacs-ai-image-list-models=  | show what each model supports                       |

A prefix argument to =cmacs-ai-image= asks for provider, model and
options -- but only the options the chosen model actually honours, so
there is no way to interactively request something that would be
silently dropped.

*** The transient menu

=M-x cmacs-ai-image-menu= opens a transient for composing a request a
piece at a time, rather than remembering which plist keys exist:

#+BEGIN_EXAMPLE
Compose an image request
 gemini / gemini-3-pro-image-preview   up to 14 references
 Multi-reference conditioning, up to 4K

Model                Geometry              Appearance
 p provider  gemini   a aspect      16:9    q quality     —
 m model     nano...  R resolution  2k      y style       —

Output               Prompt                References
 f format    —        t prompt      ...     r add reference  2 of 14
 c compress  —        N negative    —       e set a reference's role
 n count     2        S seed        42      d remove a reference

Generate
 g generate at point      M list models
 G generate from selection, insert after it
#+END_EXAMPLE

What makes it worth using over the plain commands is that it is
*capability-aware*.  Every option is offered against the model actually
selected: the aspect ratios come from that model's own list, the quality
words from its own vocabulary, and options the model cannot honour are
not shown at all rather than shown and silently dropped.  Pick
=gpt-image-2= and you get pixel sizes, transparency and masks but no
aspect ratio; pick Nano Banana Pro and you get ratios and a resolution
tier but no pixel sizes.  Changing the model re-reads all of it.

Reference images accumulate --- as many as the model accepts, and it
says how many that is --- and each can carry a role saying what it is
for.  =e= changes a role afterwards, =d= drops one.

Emptying any prompt clears that option, which is how you get back to the
model's own default.  =C-k= resets everything.

*** Illustrating prose you have already written

=cmacs-ai-image-from-selected-text= is the one to reach for when the
text describing the picture is already in the buffer.  Select it and run
the command: the selection becomes the prompt, is left exactly as it
was, and the image goes in on a fresh line immediately after it.

#+BEGIN_EXAMPLE
,* Chapter one
A hyacinth macaw perched on a brass telescope, cinematic lighting.
    <- select this line, M-x cmacs-ai-image-from-selected-text

,* Chapter one
A hyacinth macaw perched on a brass telescope, cinematic lighting.
,#+CAPTION: A hyacinth macaw perched on a brass telescope, cinematic lighting.
[[attachment:cmacs-ai-20260728-142233.png]]
#+END_EXAMPLE

=cmacs-ai-image= also accepts the region as a prompt, but inserts at
point -- and point sits at whichever end of the region you finished
selecting at, so the image can land *above* the text instead of below
it.  This command always puts it after.

The insertion point is held with a marker, so it stays correct even if
you carry on editing elsewhere in the buffer while the image generates.

Suggested bindings, beside the other cmacs-ai ones:

#+BEGIN_SRC elisp
(global-set-key (kbd "C-c a i RET") #'cmacs-ai-image-menu)
(global-set-key (kbd "C-c a i i") #'cmacs-ai-image)
(global-set-key (kbd "C-c a i s") #'cmacs-ai-image-from-selected-text)
(global-set-key (kbd "C-c a i e") #'cmacs-ai-image-edit)
(global-set-key (kbd "C-c a i r") #'cmacs-ai-image-regenerate)
(global-set-key (kbd "C-c a i m") #'cmacs-ai-image-list-models)
#+END_SRC

** Parameters

=cmacs-ai-image-generate-async= takes an options plist covering the whole
request surface.  Omitting a key leaves the provider on its own default
rather than on ours:

| Group      | Keys                                                        |
|------------+-------------------------------------------------------------|
| Prompt     | =:prompt= =:negative= =:system=                             |
| Operation  | =:operation= (generate / edit / variation / upscale)        |
| Geometry   | =:size= =:custom-size= =:aspect= =:resolution=              |
| Appearance | =:quality= =:style= =:style-preset= =:background=           |
| Output     | =:format= =:compression= =:response-format=                 |
| Sampling   | =:seed= =:guidance= =:steps= =:strength= =:temperature= =:top-p= =:top-k= |
| Policy     | =:moderation= =:person-generation= =:watermark= =:enhance-prompt= =:language= |
| Editing    | =:references= =:mask= =:fidelity= =:partial-images=         |
| Escape     | =:extra= (plist spliced verbatim into the request body)     |

Geometry is expressed two incompatible ways: the Gemini family thinks in
aspect ratios plus a resolution tier, OpenAI in pixel dimensions.  Both
are carried, and each provider uses whichever applies, so you need not
know which is in play.

=:extra= exists because image APIs gain parameters faster than a binding
can track them.  Nothing in it is validated; an unknown key reaches the
provider exactly as written.

** Reference images and editing

This is what makes Nano Banana Pro worth reaching for: several input
images, each doing a different job.

: M-x cmacs-ai-image-edit

References come from the image at point, from the marked files in Dired,
or are read one at a time.  With a prefix argument each is also given a
*role*:

#+BEGIN_SRC elisp
(cmacs-ai-image-edit
 "combine these into a concert poster"
 '(("palette.png" . "style")
   ("macaw.jpg"   . "subject")
   ("venue.jpg"   . "background")))
#+END_SRC

Order is preserved and significant.  Roles matter because no wire format
has a field for them -- ai-glib folds the labels into the prompt text,
which is the only channel the model reads.  Unlabelled references are
passed through in order.

For a masked edit, the transparent areas of the mask are the ones
regenerated:

#+BEGIN_SRC elisp
(cmacs-ai-image-generate-async
 handle "replace the sky with a storm" #'ignore
 '(:operation "edit" :references ("photo.png") :mask "sky-mask.png"
   :fidelity "high"))
#+END_SRC

** Chat integration

Two ways to get an image out of a chat buffer.

=/image PROMPT= in the compose region generates one directly, with no
model turn involved.

The =generate_image= tool lets the model decide to draw something
mid-conversation.  It is on by default; set
=cmacs-ai-chat-enable-image-tool= to nil to withhold it.  Generated
images are attached to the chat node, so the existing end-of-turn preview
renders them.

The tool is deliberately *not* named =ai_generate_image=.  The MCP bridge
hides every tool matching =^ai_= from in-process chat buffers to stop the
model calling itself recursively, and an in-process chat buffer is
exactly where this one has to be visible.

** MCP, D-Bus and emacsctl

The same generation is reachable without an Emacs UI:

#+BEGIN_SRC sh
emacsctl ai generate-image -p gemini -a 16:9 "a brass telescope"

emacsctl ai generate-image \
  -m gemini-3-pro-image-preview \
  -r logo.png::style -r subject.jpg::subject \
  -b notes.org "combine these into a poster"
#+END_SRC

The MCP tool is =generate_image=; the D-Bus method is =GenerateImage= on
=org.cmacs.Editor1.Ai=.  All three block the cmacs main thread for the
duration, which is tens of seconds -- worth knowing before wiring one
into something latency-sensitive.

References travel as a single comma-separated =PATH= or =PATH::ROLE=
string on all three surfaces, because the MCP bridge's schema translator
cannot carry a nested list.

** Troubleshooting

- *"provider does not support image generation"* -- you asked Claude or
  Ollama.  Use gemini, openai or grok.

- *"Authentication failed"* -- the provider's key is missing from the
  environment: =GEMINI_API_KEY=, =OPENAI_API_KEY=, =XAI_API_KEY=.

- *The model answered with text* -- surfaces as an invalid-response
  error rather than an empty success.  Usually the prompt was declined;
  rephrasing helps.

- *A content-policy refusal* -- arrives as an invalid-request error with
  the provider's own explanation quoted, which is the useful part.

- *"attaching failed; using ..."* -- there was no Org node to attach to
  (before the first heading, or a read-only buffer).  The image was
  saved to =cmacs-ai-image-dir= instead; nothing was lost.

- *An option seemed to be ignored* -- it probably was, because the model
  does not support it.  =cmacs-ai-image-list-models= says which does
  what.

* MCP bridge

The /outbound/ direction (above) lets external agents drive the
in-editor AI.  The /inbound/ mirror -- this section -- lets the
in-process AI drive cmacs's own MCP tool surface.

Each chat buffer's =AiToolExecutor= is automatically augmented with
cmacs's editor-aware tools (buffer / file / project / eval / apropos
/ describe by default), so the model gets the same toolset external
Claude Code already uses to drive cmacs, on top of ai-glib's
filesystem-level built-ins.

Without the bridge, AI edits land on disk bypassing cmacs buffers
(no undo, no save-hooks); with it, edits go through =edit_buffer= /
=replace_in_buffer= and respect editor invariants.

** Default allowlist

| Tool group           | Tools                                              |
|----------------------+----------------------------------------------------|
| eval / introspection | =eval=, =describe_function=, =describe_variable=, =apropos=, =completions= |
| buffer               | =list_buffers=, =get_buffer_content=, =set_buffer_content=, =create_buffer=, =edit_buffer=, =replace_in_buffer=, =search_buffer=, =goto_line= |
| window               | =list_windows=, =list_frames=                       |
| project              | =project_root=, =project_read_file=, =project_list_files=, =project_find_files=, =project_grep= |
| process + debug      | =list_processes=, =backtrace=, =memory_info=, =process_status=, =recent_messages=, =describe_mode=, =list_hooks= |

** Extending

Patterns are PCRE (the bridge uses GLib's GRegex), NOT Emacs
=\`X\'= syntax.  To add shell access + the full GObject Introspection
surface:

#+BEGIN_SRC elisp
(dolist (re '("^bacon_eval$" "^crispy_eval$" "^gi_"))
  (add-to-list 'cmacs-ai-mcp-bridge-allowlist re))
#+END_SRC

To open a single read-only chat:

#+BEGIN_SRC elisp
(let ((cmacs-ai-mcp-bridge-readonly-only t))
  (cmacs-ai-chat 'claude))
#+END_SRC

to prevent the in-process AI from invoking =ai_open_chat= /
=ai_prompt= on itself.  Not configurable.

* Running a chat in a project directory

#+begin_src elisp
M-x cmacs-ai-chat-with-provider-in-directory   ; prompts for both
M-x cmacs-ai-chat-here                         ; this buffer's directory
#+end_src

This matters mainly for the CLI providers. A command-line agent finds its project by where its process starts: =CLAUDE.md=, the =.claude= directory, a project MCP config and the repository itself are all resolved from there. An agent launched in =~/Documents/gnuisaince= is a different agent from the same binary launched anywhere else, and nothing about the conversation would tell you which one you got.

Both the CLI subprocess and the buffer's =default-directory= follow, so the filesystem and project tools resolve against the same tree. The directory also goes in the buffer name, since that is what distinguishes two otherwise identical chats.

The directory prompt behaves like =C-x C-f= for directories: it lists the roots you saved first, then browses the filesystem as you type, and only offers directories. Anywhere is still reachable, the saved ones just do not have to be remembered.

For the directories you return to, list them and they appear at the top:

#+begin_src elisp
(setq cmacs-ai-chat-directories
      (list "~/Documents/gnuisaince" "~/source/projects/cmacs"))

;; or make every chat start somewhere specific
(setq cmacs-ai-chat-default-directory "~/Documents/gnuisaince")
#+end_src

From Lisp, =cmacs-ai-chat-open= takes it as a third argument.

An HTTP provider has no subprocess to place anywhere, so the directory only affects the buffer; =cmacs-ai-client-set-working-directory= returns nil there to say so.

* Bootstrapping from the project

When a chat is opened in a directory and that directory holds a =CLAUDE.md= or an =AGENTS.md=, its contents are folded into the session's system prompt — so an HTTP model arrives already knowing the project's standing instructions, the way a CLI agent does.

Only for the HTTP providers. =claude-code=, =claude-tmux= and =opencode= read those files themselves from the directory their process starts in, and injecting a copy would send the same instructions twice.

Three details worth knowing:

- *It happens on the first send, not when the chat opens.* Opening a chat costs nothing, and the instructions are only worth sending if a conversation actually happens.
- *Nothing appears in the transcript.* The conversation reads as what you typed; the file goes into the system prompt, which is also why it is sent once rather than prepended to every turn.
- *The larger file wins* when both are present, on the assumption that the fuller document is the one being maintained. When they are the same size the order of =cmacs-ai-chat-bootstrap-files= decides.

#+begin_src elisp
(setq cmacs-ai-chat-bootstrap t                        ; the feature
      cmacs-ai-chat-bootstrap-files '("CLAUDE.md" "AGENTS.md")
      cmacs-ai-chat-bootstrap-max-bytes 200000
      cmacs-ai-chat-bootstrap-announce t)
#+end_src

** Telling the model to act on it

Putting the file in the system prompt is not enough on its own. There it reads as background — a description of the project — so a model whose instructions include a startup ritual will answer /hey there/ with /hey!/ and perform none of it.

So the first message also carries a short directive, prepended invisibly, immediately before what you typed:

#+begin_example
Before replying, carry out any startup or bootstrap steps CLAUDE.md
specifies above -- reading the files it points at, loading memory,
whatever it asks for.  Do that first, report only what matters about
it, then answer what follows.

hey there
#+end_example

It rides the first turn only, and the buffer still shows just what you typed. =cmacs-ai-chat-bootstrap-directive= is the format string (=%s= is the file); nil sends the file with no accompanying instruction.

** =@file= imports

A bootstrap file is very often not instructions at all but a manifest of them:

#+begin_example
# Bootstrap
Read the following in order:
- @SOUL.org
- @IDENTITY.org
- @USER.org
#+end_example

That convention comes from Claude Code, and a CLI agent resolves it itself because it can open files. An HTTP model cannot, so unexpanded it receives a couple of hundred bytes naming files it has no way to follow — and behaves exactly as if the project had said nothing.

So the references are resolved and inlined, in the order listed, each delimited and named. Relative paths resolve against the file containing them, so a nested import means what it says; imports nest to =cmacs-ai-chat-bootstrap-max-depth= (5), and a file named twice is sent once with a note in its place.

A reference is only expanded when it resolves to a readable file. That is what keeps =zach@example.com=, a decorator, or an =@= in prose from being mistaken for an import; anything unresolved is left exactly as written, so the model still sees a file was meant even when it is missing.

Set =cmacs-ai-chat-bootstrap-expand-imports= to nil to send the manifest verbatim.

Worth knowing what this costs: a 181-byte manifest in a real project expands to about 67 kB, and it lives in the system prompt, so you pay for it on every turn of that conversation rather than once.

Past =-max-bytes= the file is skipped rather than truncated: half a document of standing instructions is worse than none. The size cap matters because this lands in the system prompt and is therefore paid for on every turn, not just the first.

=-announce= puts one line in the echo area the first time. Nothing is added to the conversation either way; it is on by default because the alternative is silently sending a file from your disk to a remote API with no record that it happened.

* Choosing a model

Every provider prompt is followed by a model prompt, completing on what that provider actually offers:

- =claude-code= and =claude-tmux= offer =haiku=, =sonnet=, =opus= and =fable=, plus the full model ids — and additionally accept =ollama/NAME=, which runs a local model through the CLI (see below).
- =opencode= offers its =vendor/model= names, =ollama= whatever you have pulled, and the HTTP providers their catalogues.

It is not a closed list — every provider ships new model names between cmacs releases, and requiring a match would make the newest model the one thing the prompt cannot express. An empty answer takes the provider's own default.

A provider that cannot answer (no key, no daemon, no network) simply offers no completions rather than blocking; =cmacs-ai-read-model-timeout= bounds the wait.

The heading on each reply names the provider symbol you selected and the model that answered, as =claude-code/sonnet= — the provider half is the symbol, not ai-glib's display name, so it matches what you type at the prompt.

** What the shipped system prompt says

=cmacs-ai-system-prompt= is not only "be a helpful coding assistant". It also
states the conventions of the tools cmacs ships, because a model cannot infer
them from a tool schema:

- *Subagents are asynchronous, so do not poll.* =agent_spawn= returns an id
  immediately — a spawn that blocked would hold the turn open for minutes — and
  the [[file:ai-brigade/dashboard.org][loopback]] delivers a message into this
  conversation when the agent finishes. A model that has not been told so sits
  in an =agent_status= loop until it gives up, which costs turns and money and
  learns nothing. Spawn, say what you spawned, stop. Collect with
  =agent_result= when the message arrives.
- *Only the tools in the list exist.* The prompt describes conventions, not
  grants; nothing here implies a tool was given to this session.
- *The editor is live.* Read before writing, and do not save or revert a buffer
  you were not asked to.

Replace it wholesale if you want something else — it is one string, and nothing
downstream parses it.

** A local model through the claude CLI

=claude-code= and =claude-tmux= treat a model beginning with =ollama/= as a request to use Ollama as the /transport/: ai-glib spawns

: ollama launch claude --model NAME -- <the claude arguments>

rather than =claude= directly, omitting claude's own =--model= because Ollama supplies it. Answer the model prompt with =ollama/qwen3.5:9b= after choosing =claude-code=, or write the pair as one string anywhere a =PROVIDER/MODEL= is taken:

: claude-code/ollama/qwen3.5:9b

This is a different thing from the =ollama= provider, which talks HTTP to the Ollama server with no CLI in the picture. Use the CLI form when you want that harness — its prompt handling, its tool conventions — around a model that never leaves the machine; use the plain =ollama= provider when you just want the model.

The claude CLI must still be installed; =OLLAMA_PATH= overrides the launcher binary. =ai -p claude-code -m ollama/NAME --dry-run "hi"= prints the exact command without running it.

* Why a CLI agent could not call its tools

A command-line agent run non-interactively has nobody to approve anything. Claude and opencode both default to asking before using a tool, and with no prompt to answer, every tool that would need approval is simply unavailable — so the agent can /see/ the tools it was granted, list their schemas, and report that it has no way to invoke them.

cmacs therefore tells CLI providers not to ask: =--dangerously-skip-permissions= for claude-code and claude-tmux, =OPENCODE_PERMISSION= set to allow-all for opencode, =--permission-mode bypassPermissions= for grok-build. This is what libreclaw does for the same four, and it applies to a chat buffer and to the brigade's CLI workers alike.

=grok-build= costs more than the others do here, and it is worth knowing before you point a chat at it: grok's bypass mode *also disables its sandbox*, so unlike the claude and opencode cases there is no second layer left underneath. The working directory is the whole boundary.

Set =cmacs-ai-cli-skip-permissions= to nil to turn it off, understanding that a CLI chat then has no working tools.

The name of the flag is accurate and worth taking seriously — it removes claude's own confirmation step entirely, including for writes and shell commands. What bounds the agent is not that prompt but the *capability token* in its MCP config: the tool allowlist is enforced server-side by the C gate, the privileged set (=eval=, =shell=, the C-patching tools) is unreachable through =*= or a group, and the token is revoked when the buffer is killed. See [[file:ai-brigade/mcp.org][MCP]] for what that gate does and does not cover. An agent's own built-in tools -- reading and writing files, running commands in its working directory -- are not covered by it, which is the other reason [[file:ai-brigade/index.org][running a chat in a directory]] matters.

* Tool calls in the transcript

Off by default. A tool loop can run a dozen calls whose arguments and output are each a JSON block, which buries the conversation those calls were in service of — the transcript stops reading as a conversation and becomes a log.

The tools still run when this is off; only the rendering is suppressed, and the model's own account of what it did is unaffected.

#+begin_src sh
CMACS_AI_SHOW_TOOL_CALLS=1 emacs      # for one debugging session
#+end_src

=true=, =TRUE=, =1=, =yes= and =on= all turn it on; anything else, including unset, leaves it off.

#+begin_src elisp
(setq cmacs-ai-chat-show-tool-calls t)   ; or permanently
#+end_src

=M-x cmacs-ai-chat-toggle-tool-calls= flips it for the current chat only, so turning it on to debug one conversation does not make every other chat noisy. It affects turns from that point on; what has already been rendered stays.
