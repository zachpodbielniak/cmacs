#+TITLE: cmacs-brigade-undo — Undo for Agent Actions
#+AUTHOR: Zach Podbielniak
#+OPTIONS: toc:2 num:t

* Overview

An agent edits a buffer, moves a window, switches your context, writes a file. =cmacs-brigade-undo= answers "undo what the agent just did".

#+begin_src text
M-x cmacs-brigade-undo              undo the last undoable agent action
C-u 3 M-x cmacs-brigade-undo        the last three, newest first
M-x cmacs-brigade-undo-task         everything one brigade run did
M-x cmacs-brigade-undo-agent        everything one agent did
M-x cmacs-brigade-actions           the action log: inspect, undo, undo from here
#+end_src

Every capability runs through one dispatch point, =cmacs-brigade-call-tool= / =cmacs-brigade-call-tool-async= ([[file:cmacs-capability.org][cmacs-capability.org]]), whichever surface it arrived on: MCP, D-Bus forwarding, =emacsctl tool=, an in-process agent, bacon. That is where the action log hooks in, so every agent action is seen once, in one place, whatever reached it.

The pieces:

| File | What it holds |
|------+---------------|
| =lisp/cmacs/cmacs-brigade-undo.el= | the log, records, staleness, undo, commands, the =*cmacs agent actions*= buffer, the generated decision table |
| =lisp/cmacs/cmacs-brigade-undo-capture.el= | the per-tool capture functions the families' =:undo= declarations name |
| =lisp/cmacs/cmacs-brigade-undo-tools.el= | the =action_log= and =action_undo= tools |
| =lisp/cmacs/cmacs-brigade-tools.el= | the dispatch: capture before, change groups around, log after |
| =lisp/cmacs/cmacs-brigade-registry.el= | the =:undo= key of =cmacs-brigade-deftool= |

* How a call is recorded

** Before the handler: capture

A tool declares how it is undone with =:undo= on its =cmacs-brigade-deftool= form. Before the handler runs, the dispatch asks that declaration for an /undo record/: plain data about the state the call is about to change, plus the functions that check and restore it. Capturing before is the only general way — the result of a call rarely says what was there before it.

#+begin_src emacs-lisp
;; A capture function, named: called with the handler's own arguments.
(cmacs-brigade-deftool set-buffer-content ...
  :destructive t
  :undo 'cmacs-brigade-undo-capture-buffer-text
  ...)

;; A FORM, evaluated with the parameters bound, before the body.
(cmacs-brigade-deftool my-rewrite "..." ((buffer string "Buffer"))
  :destructive t
  :undo (cmacs-brigade-undo-buffer-record buffer)
  (my/rewrite buffer))

;; A declared "cannot", with the reason the user will read.
(cmacs-brigade-deftool gowl-close-client ...
  :destructive t
  :undo '(irreversible "a closed application cannot be reopened as it was")
  ...)
#+end_src

The capture returns one of:

| Answer | Meaning |
|--------+---------|
| a record (a plist) | what undoing needs |
| =nil= | nothing to undo for this call (asking a module for the state it is already in) |
| =irreversible=, =(irreversible REASON)= | it cannot be undone, and why |

A capture that signals makes the call "irreversible: the state before the call could not be captured: …" — it never fails the call. The log is a record, not a gate.

What is logged:

| Tool | Logged as |
|------+-----------|
| =:destructive= with =:undo= | its record, or "nothing to undo", or irreversible with its reason |
| =:destructive= without =:undo= | "irreversible: no undo declared" |
| not destructive, no =:undo= | not logged at all — reads are not actions |
| not destructive with =:undo= | logged (it said it can be undone) |

A call that fails is not logged: the caller was told it failed.

** Around the handler: one change group

When the record names buffers (=:buffers=), the dispatch wraps the handler in a change group in each (=prepare-change-group= … =accept-change-group= + =undo-amalgamate-change-group=, then an =undo-boundary=). The agent's edit is then ONE entry in that buffer's own undo list: a plain =C-/= in the buffer takes back the whole edit, however many separate changes the handler made. This holds for a call that fails half way too — its partial edit is one =C-/=.

** After the handler: complete and log

The record's =:after= function completes it with what the call left: the region it changed, between two markers; the hash of the file it wrote; the geometry the window ended up with. The call then joins the *action log*, an in-memory ring of =cmacs-brigade-undo-log-size= entries (200), newest first. Each entry has:

| Field | |
|-------+---|
| id | increasing integer, =#ID= everywhere |
| time | when the call returned |
| caller | the dispatch's agent string (=mcp=, =dbus=, =bacon=, an in-process agent's name) and the brigade task, if any |
| surface | =mcp=, =dbus=, =cli=, =agent=, =lisp= |
| tool, arguments | as the caller sent them |
| result | first line, 120 characters |
| record | the undo record |
| state | =done=, =undone=, =failed-to-undo=, =irreversible=, =stale=, =nothing-to-undo= |

An entry leaving the ring releases what its record holds (markers, a backup copy).

* Undoing

** Staleness

Before an inverse runs, the world must still be what the agent left:

| Kind | Stale when |
|------+------------|
| buffer edit | the text between the markers is no longer what the agent wrote (the user may edit elsewhere in the buffer meanwhile); the buffer was killed |
| file write | the file's sha256 is no longer that of what the agent wrote; the file is gone |
| window layout | the frame's windows (buffers, edges, selection) changed; the frame is gone |
| gowl window | it is closed, or moved/resized since (neither where the agent left it nor what the agent asked for) |
| focus, layout, workspace, context | changed again since |
| created/visited buffer | modified since, or already killed |
| point | moved since |

A second rule applies to everything: an older action refuses while a NEWER action that changed the same object (the record's =:object=) is still done — "#7 edit_buffer changed the same thing later; undo it first". Undoing newest first is always the order that works.

A refused undo says, in one sentence, what changed, and leaves the entry =stale= (it can be tried again once the world is back). It never clobbers the user's later work.

=cmacs-brigade-undo-force= (and =F= in the log buffer) skips both checks, after asking. It is for the user only: no tool passes it.

** Buffer edits: the buffer's undo list first

The inverse of a buffer edit prefers the buffer's own undo list: when the change group the dispatch recorded is still intact at the head of =buffer-undo-list= (nothing recorded since, not truncated by =undo-limit=), it undoes exactly that group, as =C-/= would. Otherwise it falls back to the snapshot: the region between the markers is replaced by the text that was there. A buffer over =cmacs-brigade-undo-max-bytes= (1 MiB) is not snapshotted; its edit can be undone only while the change group is intact.

The undo is itself one change group in the buffer, so =C-/= there re-applies the agent's edit. That is the only redo there is: undo of an undo is not offered anywhere else, and =action_undo= logs itself as "nothing to undo".

When the buffer was unmodified before the agent's edit and the undo brings back exactly that text, the buffer is unmodified again.

** Order and stopping

| Command | Order | Stops |
|---------+-------+-------|
| =cmacs-brigade-undo= (=N=) | the last N with an undo record, newest first | at the first refusal; irreversible entries are passed over and counted |
| =cmacs-brigade-undo-task= | that task's actions, newest first | at the first that cannot be undone, saying which and why |
| =cmacs-brigade-undo-agent= | that agent's actions, newest first | likewise |
| =U= in the log | the entry and everything its caller did after it | likewise |
| =action_undo= | the caller's own, by id or the last COUNT | likewise |

* The log buffer

=M-x cmacs-brigade-actions= lists the log (=*cmacs agent actions*=), refreshed as entries arrive:

| Key | |
|-----+---|
| =RET= | inspect: caller, arguments, result, state and reason, what undo would do |
| =u= | undo this entry |
| =U= | undo it and everything the same caller did after it |
| =F= | force-undo (asks) |
| =g= | refresh |

In the brigade dashboard, =cmacs-brigade-undo-dashboard-task= undoes the task on the current line.

* The tools

| Tool | |
|------+---|
| =action_log= | read-only. The caller's OWN actions, newest first, one line each, with what undoing would do. =all=true= lists every caller's, only for an agent name or task id in =cmacs-brigade-undo-log-all-callers= |
| =action_undo= | destructive, asks. Undoes the caller's own actions only — by =id=, or the last =count= — staleness check always on |

Who the caller is comes from the dispatch (=cmacs-brigade-current-call=), never from an argument. A caller with a task (a CLI agent on its scoped socket, an in-process run) owns exactly that task's entries; the task id is the editor's own record. Without a task, entries with the same agent string and no task: every external MCP client not on a scoped socket shares the agent =mcp=, and so shares an identity. A request for another caller's =#ID= is answered exactly as one for an id that does not exist.

Arguments, results and reasons in =action_log= go through =cmacs-redact-text= ([[file:cmacs-redact.org][cmacs-redact.org]]); a missing redaction file fails the tool closed. The log buffer is the user's own view and shows them as they are.

* Privacy and disk

Records hold buffer and file contents, so the log is never written to disk by default.

| Option | Default | |
|--------+---------+---|
| =cmacs-brigade-undo-log-size= | 200 | entries kept |
| =cmacs-brigade-undo-max-bytes= | 1 MiB | largest buffer or file a record keeps a copy of |
| =cmacs-brigade-undo-backup-large-files= | nil | keep a backup copy of a larger file under =$XDG_STATE_HOME/cmacs/undo/= (0700, files 0600), deleted when the entry is undone or leaves the log; otherwise such a write is irreversible with that reason |
| =cmacs-brigade-undo-persist-metadata= | nil | append id, time, tool, agent, task and state — never arguments, results or records — to =$XDG_STATE_HOME/cmacs/undo/actions.jsonl= |
| =cmacs-brigade-undo-log-all-callers= | nil | who may =action_log all=true= |

A file the agent CREATED is undone by moving it to the trash (=delete-by-moving-to-trash=), not by deleting it.

* Writing an undo for your own tool

The record is a plist; the machinery reads these keys and leaves the rest to your functions:

| Key | |
|-----+---|
| =:summary= | one line: what undoing would do |
| =:object= | what the call changed, compared with =equal=, for the newest-first rule |
| =:buffers= | buffers to wrap in a change group |
| =:after= | =(RECORD RESULT)= → the completed record, =nil= (nothing changed after all) or =(irreversible REASON)= |
| =:stale= | =(RECORD)= → =nil=, or a sentence saying what changed |
| =:inverse= | =(RECORD)= → undo; signal on failure (=cmacs-brigade-undo-stale= for "the world changed") |
| =:cleanup= | =(RECORD)= → release what it holds |

The building blocks: =cmacs-brigade-undo-buffer-record=, =-created-buffer-record=, =-killed-buffer-record=, =-point-record=, =-file-record=, =-window-record=, and =cmacs-brigade-undo-compose= to combine several. A capture function's docstring's first line is what the decision table below says about the tool.

* Decisions for every destructive tool

* Limits

- The right-click menu (=cmacs-ai-actions=) calls a tool's handler directly, as the user's own action, and is not logged; buffer edits made that way are still in the buffer's undo list.
- An =:async= tool is logged when it calls =done= (a tool that finishes after its timeout is still logged); its change groups span only its synchronous part.
- imgedit's document undo stack does not say who pushed a step: undoing an agent's imgedit step after an edit made in =cmacs-imgedit-mode= takes back that edit instead. The newest-first rule covers logged edits only.
- =gsurf_navigate= is not stale when the page redirected or the user followed a link; only a closed view refuses.
- =screensaver_set_wallpaper= knows the previous wallpaper only when a tool started it.
- A context switch's undo switches back; what the switch opened stays open (switches never close anything).
- gowl: a tiled window's geometry is the layout's — its undo puts it back in the tile layer, not at a pixel position.
