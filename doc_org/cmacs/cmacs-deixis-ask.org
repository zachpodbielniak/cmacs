#+TITLE: cmacs-deixis-ask — "explain THAT"
#+AUTHOR: Zach Podbielniak
#+OPTIONS: toc:t num:t

* Overview

Deictic questions.  [[file:cmacs-deixis.org][cmacs-deixis]] binds a spoken "this" or "that" to what the pointer rested on while the word was said, and runs deictic /commands/ with it ("move that there").  =lisp/cmacs/cmacs-deixis-ask.el= adds /questions/: point at something and ask about it, and what was pointed at becomes the model's context.

#+begin_example
what is that?                     explain this
summarise that                    what does this error mean
translate that into German        why is this failing
compare this and that             what is the difference between this and that
and that one?                     what is this window
#+end_example

There are three stages, and each is small:

| Stage               | What                                                                                                            | Where                                 |
|---------------------+-----------------------------------------------------------------------------------------------------------------+---------------------------------------|
| referent -> content | /extractors/, most specific first, in a public registry                                                         | =cmacs-deixis-ask-register-extractor= |
| privacy             | a gate before anything is read, and redaction of what was read                                                  | =cmacs-deixis-ask-refusal=            |
| asking              | =cmacs-ai-textops-stream=: the answer streams into the [[file:cmacs-ai.org][cmacs-ai-output]] window, which keeps its session for follow-ups | =cmacs-deixis-ask-run=                |

There is no configure flag and no mode of its own.  By voice it rides =cmacs-deixis-mode=; by hand it is =M-x cmacs-deixis-ask-at-pointer= and an entry in the AI right-click menu.  No new prompt stack: the provider and model are the text operations' (=cmacs-ai-textops-provider=, =cmacs-ai-textops-model=) unless =cmacs-deixis-ask-provider= / =-model= say otherwise.

* Two doors

** By voice

=cmacs-deixis-filter= resolves an utterance's demonstratives, tries the deictic commands, and then -- new -- runs =cmacs-deixis-unclaimed-functions= with =(TEXT BINDINGS)= until one returns non-nil.  =cmacs-deixis-ask-utterance= is on that hook (an autoload cookie puts it there).  Because the hook is asked only /after/ the commands, a question can never take an utterance a command matches.

When the utterance is a question (see [[*What is taken as a question][below]]):

1. each distinct thing pointed at is checked for privacy; one refusal refuses the whole question, aloud;
2. the loop is put in =thinking= with its reply marked open, which is what makes talking over the answer a barge-in;
3. the things are read, one after the other, by callbacks;
4. the answer streams into the result window /and/ into the loop's own sentence queue (=cmacs-voice-loop--feed-reply=, =cmacs-voice-loop-speak=) -- the path a chat reply takes, so =cmacs-voice-loop-speak= nil silences it and the loop's housekeeping returns to listening, with the follow-up window open, when the speech is done.

The result window is not selected for a spoken question: it must not pull the selected window out from under what you are doing.

*Barge-in.*  The loop enters =hearing= from =thinking= or =speaking= only when you talk over a reply.  It stops the speech itself; this file's state hook then stops what the loop does not know about -- an extraction still in flight is dropped and the model's stream is cancelled, when =cmacs-voice-loop-barge-in-cancels-stream= is on.  Text that still arrives is shown but not spoken.

*Follow-ups.*  "And that one?", "what about this?", "how about that one too?" continue the conversation with a new referent: the new thing is read and sent as a follow-up turn on the /same session/, through the window's own compose region -- so it is rendered, sealed, recorded for promote-to-chat and streamed exactly as a typed =C-c C-c= follow-up, and what was sent, context included, is there to read.  A draft you had typed in the compose region is put back.  A follow-up needs a settled answer no older than =cmacs-deixis-ask-followup-seconds= (300); otherwise -- the window closed, the answer cancelled by a barge-in, too long ago -- the earlier question is asked afresh about the new thing.  A follow-up form with no earlier question at all is not a question, and goes on to the voice route.

=cmacs-deixis-ask-voice= nil turns the voice door off: "what is that?" then goes on to the route, annotated, as before this file.

** By hand

=M-x cmacs-deixis-ask-at-pointer= asks about what the pointer is on /now/.  What "that" is comes from =cmacs-deixis-referent-now= (new in cmacs-deixis.el): the active region, unless the pointer is on another window; else what the pointer is on; else point.  The compositor's pointer ring is the one place that knows which window is under the pointer, so when it is not sampling it is switched on for the one lookup and off again, which empties it.

The question is read after the privacy gate has passed (a refused thing costs no typing).  Over another program's window, or while another program has the keyboard (a minibuffer read would then wait for keys that go elsewhere), it comes from a gowl menu card on top of everything, with the rows of =cmacs-deixis-ask-menu= and a last row for typing something else in a floating minibuffer -- the AI field commands' chooser, reused.  With the keyboard in Emacs it is one minibuffer read with those questions as completions.  A question that names the whole thing ("what is this window", "summarise this page") reads the whole thing.

Bind it wherever suits.  In the compositor, so it works over any window:

#+begin_src emacs-lisp
(gowl-add-keybind "Super+Ctrl+q" 'custom "(cmacs-deixis-ask-at-pointer)"
                  "Ask about what the pointer is on")
#+end_src

*The AI menu.*  =cmacs-deixis-ask-register-menu= adds "Ask about this..." to the Ask group through =cmacs-ai-register-action=, the menu's own extension point, so it is in the right-click menu, the =C-c a= transient and =cmacs-ai-run-action= alike.  It asks about the click's target, not the pointer: by the time a menu row is chosen the pointer is on the menu.

* From referent to content

=cmacs-deixis-ask-extract= asks the gate, then tries the extractors that apply to the referent in order until one answers.  It never blocks and gives up after =cmacs-deixis-ask-extract-timeout= seconds.

| Extractor | Order | Applies to                                    | Reads                                                                                 |
|-----------+-------+-----------------------------------------------+---------------------------------------------------------------------------------------|
| =gsurf=   |    10 | a buffer showing a gsurf web view             | URL, title, and the selection or the text nearest the pointed place                   |
| =field=   |    20 | another program's window that has the keyboard | the text /selected/ in its focused field                                              |
| =buffer=  |    50 | a position, region or point in an Emacs buffer | the thing there, its diagnostics, its file and major mode                             |
| =ocr=     |    60 | any other window, with a compositor            | tesseract over a box around the pointed place, or the whole window                    |

** An Emacs buffer

=cmacs-deixis-ask-buffer-thing= chooses what is "at" the position, the most specific of, in the buffer's own terms:

| Thing               | When                                                                                         |
|---------------------+----------------------------------------------------------------------------------------------|
| =region=            | a region referent, or the active region when the position is inside it                       |
| =shown=             | the question was about the whole file/buffer: what the window shows of it                    |
| =compilation-error= | a compilation message is there: its line and the lines under it that carry no message of their own (gcc's excerpt and caret), up to =cmacs-deixis-ask-error-lines=; the file and line it is about come from the data =compilation-next-error= works from |
| =subtree=           | Org: the subtree                                                                             |
| =defun=             | code: the function, by tree-sitter when the buffer has a parser, else the major mode's       |
| =paragraph=         | the paragraph                                                                                |
| =lines=             | the line is blank or nearly so: it and =cmacs-deixis-ask-context-lines= either side          |
| =line=              | the line                                                                                     |

Anything longer than =cmacs-deixis-ask-max-chars= (6000) is cut to that much around the pointed position, on whole lines, and the prompt says so.  Narrowing is respected.  The flymake diagnostics over the thing's span are added -- eglot reports through flymake, so a language server's are among them -- which is what lets "why is this failing" on a function see what the checker says about it.  The description names the major mode and the file.

** A web view

A gsurf buffer has no text in it, so it has its own extractor, ahead of =buffer=.  One asynchronous script (=cmacs-gsurf-run-javascript-async=) returns JSON: the title, the selection, the text nearest the pointed place, and the start of the page's text.  "Nearest" is the element under the pointed place, widened to an ancestor until it holds =cmacs-deixis-ask-web-min-chars= (200) characters -- the element itself is often one word of a link.  The place is the frame pixel the referent now carries (=:frame-x=, =:frame-y=, added to =cmacs-deixis--frame-referent=) as a fraction of the window's body; the middle of the view when there is none.  Only numbers are formatted into the script.  A selection beats the pointed place; "this page" takes the page.

** Another program's window

*(a) The field.*  Only when the pointed window holds the keyboard -- text-input reaches the focused window and no other -- and only for a /selection/: a headless edit-field session (=cmacs-gowl-edit-field-read-async=, see [[file:cmacs-gowl-edit-field.org][cmacs-gowl-edit-field]]) reads the field, the selection is taken, and the session is released at once.  The deny list and the password refusal are that file's own.  The clipboard fallback is never used: it types Ctrl+A and Ctrl+C at the application.  A field with a caret and no selection is not this extractor's; the next one reads what was pointed at.

*(b) The screen.*  =cmacs-deixis-ask-ocr-region= is a box of =cmacs-deixis-ask-ocr-box= (900x420 layout pixels) centred on the pointed position and moved to lie inside the window, so it never reaches into a neighbour; a smaller window, and "what is this window", read the whole window.  The capture and the asynchronous tesseract run are the gowl tools' =cmacs-gowl-tools--screen-text= -- what the =gowl_screen_text= tool calls -- entered as a model would enter it, so its guard refuses a region that shows a window the rules withhold.

*(c) The picture.*  Not implemented, because the interface does not exist: =cmacs-ai-chat-stream= and =cmacs-ai-session-append-message= take text only (=ai_message_new_user= with a string), so a cropped image cannot be handed to a multimodal model.  Where OCR finds no text the question is reported as unanswerable.

** Adding an extractor

#+begin_src emacs-lisp
(cmacs-deixis-ask-register-extractor
 'pdf
 :order 30
 :applies (lambda (referent _scope)
            (with-current-buffer (plist-get referent :buffer)
              (derived-mode-p 'pdf-view-mode)))
 :extract (lambda (referent _scope done)
            ;; Call DONE exactly once, now or later.
            (funcall done (list :source 'pdf
                                :description "a page of a PDF"
                                :text (my-pdf-page-text referent)))))
#+end_src

=:extract= calls =DONE= with a context plist (=:source=, =:description=, =:text=, optional =:extra=, =:foreign=, =:clipped=), with =nil= ("not mine after all: try the next"), with =(:failed WHY)= or with =(:refused WHY)=.  It must not block.  Signalling counts as =nil=, with the error kept for the final report.  Mark text that did not come from an Emacs buffer =:foreign= so that it is redacted.

* Two referents

"Compare this and that" and "what is the difference between this and that" bind two demonstratives; each distinct thing is read by its own extractor and the prompt carries two numbered contexts, with the words marked the way the annotated utterance marks them:

#+begin_example
The user pointed at something on screen and said:

  compare this [this=①] and that [that=②]

Compare the two: what they share, then how they differ.

① text from an Emacs buffer (c-mode; file ~/src/a.c; lines 10-42; the function at the pointed position)
<<<
...
>>>

② text read by OCR off the part of a window around the pointed position of another program; expect recognition errors and neighbouring text
<<<
...
>>>
#+end_example

Unlike =cmacs-deixis-annotate= there is no legend: the legend names windows by title, and the blocks say what each thing is.  One thing said twice ("what is this and why is this here") is one context.

* What is taken as a question

=cmacs-deixis-ask-match= decides.  An utterance is a question only when *every demonstrative resolved to something that still exists*, and then when either holds:

1. Its canonical form (=cmacs-deixis-canonical=: lower-cased, fillers dropped, each demonstrative replaced by =<object>= or =<place>=; =cmacs-deixis-ask-lead-ins= such as "so" and "okay" taken off the front) matches one of =cmacs-deixis-ask-questions=.
2. The catch-all (=cmacs-deixis-ask-catch-all=, on by default): its first word is one of =cmacs-deixis-ask-question-words= *and* the voice route it was on is one of =cmacs-deixis-ask-catch-all-routes= (=chat= and agent routes: the ones whose utterances were going to a model anyway).

| Shipped question | Says                                                        | Canonical forms                                                        |
|------------------+-------------------------------------------------------------+------------------------------------------------------------------------|
| =what-is=        | "what is that", "what's this", "what is this window"        | =what is <object>= ...                                                 |
| =explain=        | "explain this", "could you describe that to me"             | =explain <object> ...=                                                 |
| =summarise=      | "summarise that", "sum that up", "summarize this page"      | =summarise <object> ...=                                               |
| =translate=      | "translate that", "translate this into German"              | =translate <object> ...=                                               |
| =meaning=        | "what does this error mean", "what does that say"           | =what does <object> ... mean=                                          |
| =why=            | "why is this failing", "why doesn't that compile"           | =why is <object> ...=                                                  |
| =compare=        | "compare this and that", "what is the difference between this and that", "how does this differ from that" | =compare <object> and <object>= ...      |
| =and-that=       | "and that one?", "what about this?" -- a follow-up          | =and <object>=                                                         |

What is deliberately *not* taken:

- anything a deictic command matches ("move that there", "close that") -- commands are tried first;
- anything with no demonstrative ("what is the weather"), or one that points at nothing;
- requests to /do/ something: "can you close that", "make this bigger".  "Can", "could", "would" and "will" are not in the question words on purpose -- a model with tools on the chat route can carry the request out, and an answer in a window cannot;
- on the =commands= route or a function route, anything but the shipped questions;
- a follow-up form when there is no question to follow up.

Everything not taken goes on to its route exactly as before.

** Defining one

=cmacs-deixis-define-question= is the sibling of =cmacs-deixis-define-command=.  The shapes differ -- a question's "body" is always the same, so there is no argument list and no body -- which is why it is a macro of its own:

#+begin_src emacs-lisp
(cmacs-deixis-define-question who-wrote
    "\\`who wrote <object>\\'"
  "Who wrote the pointed thing."
  :instruction "Name the author if the text says; do not guess.")
#+end_src

=:instruction= is added to the prompt under what was said.  =:followup t= makes the utterance continue the last answer.

* Privacy

Decided before any text is read, and again on what was read.  All of it runs under =cmacs-redact-as-model= ([[file:cmacs-redact.org][cmacs-redact]]): a question the user asked is still text composed for a model.

| What                                         | Rule                                                                                                                              |
|----------------------------------------------+-----------------------------------------------------------------------------------------------------------------------------------|
| the window pointed at                        | =cmacs-redact-window= (app id, title, pid); excluded -> refused                                                                   |
| the buffer pointed at                        | =cmacs-redact-buffer-p=; excluded -> refused                                                                                      |
| a web view                                   | the buffer check (which judges by URL and title) and =cmacs-redact-url=; excluded -> refused, and the page's script never runs    |
| a window on =cmacs-gowl-edit-field-deny=     | the field read is refused by the edit-field code; the OCR read by =cmacs-deixis-ask-deny-applies-to-ocr= (default on)             |
| a password or PIN field                      | refused by the edit-field code, whatever the lists say                                                                            |
| text from a field, OCR or a web page         | through =cmacs-redact-text=; if that fails the text is dropped, not sent                                                          |
| text of an Emacs buffer                      | sent as it is                                                                                                                     |
| a window's title and app id                  | not sent unless =cmacs-deixis-ask-send-window-identity=, and then as the rules rewrite them                                       |
| a web page's URL and title                   | sent, the URL as =cmacs-redact-url= rewrites it, the title through =cmacs-redact-text=                                            |
| the rules cannot be asked                    | refused (fail closed), in the gate and in the text                                                                                |

A refusal is /visible/ (the echo area, and a toast on the gowl bar -- the echo area is not in view while another program has the screen; =cmacs-deixis-ask-toast=) and /spoken/ when the question was.  Every privacy refusal reads =cmacs-deixis-ask-refusal-text=, the same words whatever was matched, so a refusal says nothing about the rule set.  A refused spoken question is still /taken/: it does not go on to another model by the chat route.

*Why OCR and field text are redacted when the AI field's is not.*  The AI field commands ([[file:cmacs-gowl-ai-field.org][cmacs-gowl-ai-field]]) send a field verbatim, because the user asked for that exact text to be rewritten, and a rewrite of redacted text would be written back into the field.  Here the text is whatever happened to be in a box around a pointer, and a box catches things nobody pointed at -- the neighbouring line, the account number in the header.  So it is redacted.  The text of an Emacs buffer is not: the buffer check has passed, the thing is exactly what was pointed at, and the other =cmacs-ai= actions send buffer text the same way.

*Why the deny list stops OCR too.*  The list names windows whose text fields are never read: password managers, password prompts, the lock screen.  Reading the same window's pixels is the same breach by another road.

* Nothing blocks

Under =emacs --gowl= all of this runs on the compositor's thread.  The field read, the page's script, tesseract and the model are callbacks; every extraction has a timeout; a newer question or a barge-in bumps a generation counter and late results are dropped.  The screen capture and the PNG write before tesseract starts are synchronous, exactly as in the =gowl_screen_text= tool.  The one wait is typing a question in the minibuffer, in the door by hand.

* Additions to cmacs-deixis.el

Three, all additive:

- =cmacs-deixis-unclaimed-functions=: the hook =cmacs-deixis-filter= runs, after the commands, for an utterance with demonstratives that no command took.
- =cmacs-deixis-referent-now= (and =cmacs-deixis--pointer-now=): what the pointer is on at this moment, with nothing spoken.
- =:frame-x= / =:frame-y= on a frame referent: the pixel it was resolved from.

* Reaching into other files

Stated so that a change there knows about here.  The voice path sets the loop's =cmacs-voice-loop--stream-open= and =--tts-tail= and calls =--set-state=, =--feed-reply= and =cmacs-voice-loop-speak= (cmacs-deixis.el already uses =--arm= and =--last-target=).  Speech is tapped with =:before= advice on =cmacs-ai-output-append=, =cmacs-ai-output-finish= and =cmacs-ai-output--settle-followup=, installed at the first spoken question -- the same device the loop uses on =cmacs-ai-chat--stream-callback=, and it acts only on this file's result buffer while a spoken question is in flight.  The follow-up path reads =cmacs-ai-output--compose-marker=, =--session=, =--request= and =--done=.  The door by hand calls =cmacs-gowl-ai-field--choose= and =--read-instruction=; the OCR path calls =cmacs-gowl-tools--screen-text=; the deny check calls =cmacs-gowl-edit-field--denied-p=.

* Tests

=test/cmacs/cmacs-deixis-ask-tests.el= is pure ERT, 37 tests.  The compositor, gsurf, the edit-field session, tesseract, the model and the voice loop are stubs; the redaction functions are stubbed too, so the result does not depend on the privacy rules of the machine running the suite.  The buffer extractor, the question table, the prompt, =cmacs-ai-textops-stream= and the result window's follow-up path are the real code.  Covered: extractor selection per referent kind and the open registry; the thing chosen at a position (function, paragraph, lone line, Org subtree, region, compilation error) and its size limits; diagnostics; refusal of an excluded buffer, window, URL, denied window, closed window and of everything when the rules signal, each before any read; redaction of foreign text; the OCR box arithmetic; field selection falling through to OCR; the web view; the question table, including what is *not* taken; two referents end to end; a spoken answer shown and spoken; "and that one?" reusing the session; barge-in; the door by hand, the menu card and the AI menu entry.

Not covered, and needing a live session: the text-input read against a real application, tesseract on real pixels, a page's JavaScript in WebKit, a real provider's stream (in particular what a cancelled stream delivers), and speech with a real barge-in.
