#+TITLE: output_lrg — An Independent libregnum/raylib Display Backend
#+AUTHOR: Zach Podbielniak
#+OPTIONS: toc:2 num:t

* Overview

~output_lrg~ is a third GNU Emacs display backend in cmacs, a peer to the
terminal backend (~emacs -nw~) and the graphical *pgtk* backend.  Where pgtk
renders through GTK + Cairo, ~output_lrg~ renders the *entire* Emacs UI —
every glyph, cursor, fringe, region and modeline — through the *libregnum*
engine and its GObject raylib wrapper *graylib* (raylib 6.0 on GLFW/X11).

It is *opt-in*: plain ~emacs~ / ~./src/emacs~ still starts pgtk.  The backend
is selected only by the ~--lrg[=MODE]~ command-line flag (or by setting
~initial-window-system~ to ~lrg~).

#+begin_src sh
./src/emacs --lrg          # == --lrg=2d, the default render mode
./src/emacs --lrg=2d       # explicit
./src/emacs --lrg=3d       # 3D: the frame as floating panel(s) in a scene
./src/emacs --lrg=3d:per-window:workshop   # one panel per window, grid floor
./src/emacs --lrg=3dvr     # reserved -- builds the 3D surface (mono) for now
#+end_src

See [[*3D mode]] for the full SPEC grammar, arrangements, environments and
runtime controls.

raylib owns the OS window and the input event loop; Emacs's own ~pselect~
loop is unchanged and is woken by a timer file descriptor.  ~(window-system)~
returns ~lrg~ on these frames.

Enable at build time with ~--with-cmacs-lrgterm~ (requires
~--with-cmacs-libregnum~ — it reuses libregnum's archive and its ~Lrg*~
surface/atlas types — and ~--with-cmacs-glib~; it does *not* require
~--with-pgtk~, though cmacs normally builds both so they coexist).

* Why a third backend

The motivation is the long-term "Stark mode" direction: an Emacs UI that can
live in a real-time 3D/VR scene.  Rather than bolt 3D onto pgtk, ~output_lrg~
is a clean, GPU-native backend whose architecture is *2D-first but
3D/VR-ready* through a render-mode seam (see [[*Render modes (2D + 3D; VR
reserved)]]).  It renders pixel-faithful flat 2D (~--lrg~) and a configurable
real-time 3D workspace (~--lrg=3d~); VR is the reserved next step.

* Quick start

#+begin_src sh
# Build (full cmacs flag set plus the backend):
./configure --with-pgtk --with-cairo ... --with-cmacs-libregnum \
            --with-cmacs-glib --with-cmacs-lrgterm
make -j$(nproc)

# Run it (just run exports the libregnum/graylib LD_LIBRARY_PATH):
LD_LIBRARY_PATH=deps/libregnum/deps/graylib/build/lib:$LD_LIBRARY_PATH \
  ./src/emacs --lrg
#+end_src

Everything you expect from a graphical Emacs works: proportional/monospace
fonts with antialiasing and full font-lock colour, modelines, window splits
and dividers, the region, scrolling, the cursor, the system clipboard, and
text decorations (underline/box/strike/overline).

** Desktop launchers

=make install= (and the container build) install two extra application
entries alongside the usual /Emacs/ and /Emacs (Client)/:

- *Emacs Libregnum* — launches =emacs --lrg= (=etc/emacs-libregnum.desktop=).
- *Emacs Libregnum (Client)* — =emacsclient --lrg= (=etc/emacsclient-libregnum.desktop=).

Both set =StartupWMClass=cmacs= (the WM class of the raylib window) so the
desktop associates the window with the launcher icon.  The plain /Emacs/
entries are unchanged and still start pgtk.

The client launcher mirrors =emacsclient.desktop= (an =sh -c= wrapper: files
→ =emacsclient --lrg "$@"=, none → =emacsclient --lrg --create-frame= so a
plain icon click still opens a frame instead of erroring with "file name or
argument required").  It deliberately does *not* pass an empty
=--alternate-editor== the way the pgtk client does: that would make
=emacsclient= auto-start a generic =emacs --daemon= (no =--lrg=).  A daemon
*can* host the lrg window on demand now (the =-lrg= request calls
=cmacs-lrg-attach=; see below), but only if it was started inside a graphical
session -- so the launcher relies instead on =--lrg='s built-in fallback to
=emacs --lrg= (a dedicated process that owns the window from startup and
serves later clients).

** =emacsclient --lrg=

=emacsclient= accepts =--lrg[=MODE]= (it appears in =emacsclient --help= and
=emacs --help=).  Because the libregnum backend is *one window per process*,
=--lrg= never opens a *second* raylib window; instead it:

1. *Reuses* a running =emacs --lrg='s frame — the client sends a =-lrg MODE=
   request and the server (=server.el=) selects and raises its existing
   =output_lrg= frame, opening the files there.
2. *Creates one on demand* in the connected server when it has no lrg frame yet
   — the =-lrg= handler calls =cmacs-lrg-attach=, which opens the raylib window
   *in the server process* and makes an lrg frame, instead of falling through to
   a pgtk frame.  This is how you "attach" lrg to a daemon: the daemon must run
   inside a graphical session (=DISPLAY=/=WAYLAND_DISPLAY= set in *its* env, so
   GLFW can create the window); a headless =emacs.service= cannot, and
   =cmacs-lrg-attach= errors cleanly there.
3. *Falls back* to launching =emacs --lrg[=MODE]= when no server is reachable
   — =--lrg= defaults the =--alternate-editor= to =emacs --lrg= for you (an
   explicit =-a= still wins).

So =emacsclient --lrg file= opens =file= in your running libregnum Emacs,
spins up the lrg window inside your daemon if one is running there, or starts a
fresh =emacs --lrg= if no server is reachable.

=M-x cmacs-lrg-attach= (=cmacs-lrg-attach &optional MODE=) is the underlying
command: it opens the lrg window in the *current* process on demand (raising the
existing lrg frame if there already is one).  MODE is "2d" (default), "3d" or
"3dvr"; it runs =cmacs-lrg-set-render-mode= before creating the frame (the
runtime equivalent of =--lrg=MODE=).

* Architecture

A strict four-layer stack.  The backend calls *only* graylib / libregnum
GObject APIs — never raylib directly.  Font *rasterisation* stays Emacs-side
(it needs Emacs font objects); only raw RGBA pixel buffers cross into
libregnum, so libregnum stays Cairo/FreeType-free and headless-unit-testable.

#+begin_example
Layer 4  Elisp + MCP + D-Bus + GI        lisp/term/lrg-win.el,
         (runtime control/introspection) cmacs/mcp/cmacs-mcp-tools-lrgterm.c
Layer 3  cmacs/lrgterm/  plain Emacs C    struct terminal hooks, redisplay
         glue (cannot be GObject)         interface, font-driver blit, events
Layer 2  libregnum  src/term/ Lrg* types  LrgGlyphAtlas, LrgFrameSurface
         (Libregnum-1.typelib)            (abstract) + Lrg2DSurface, ...
Layer 1  graylib  Grl* raylib wrappers    GrlWindow, GrlTexture, draw_*,
         (Graylib-1.typelib)              clipboard, input, monitor
              raylib / GLFW  (never called directly above Layer 1)
#+end_example

** Layer 2 — libregnum ~Lrg*~ GObject types (~deps/libregnum/src/term/~)

All GObject-Introspectable (scanned into ~Libregnum-1.typelib~), so they are
drivable from Elisp via ~(gi-require "Libregnum")~ and from any GI language:

- ~LrgGlyphAtlas~ (final) — the GPU glyph cache: a GL-free shelf packer with
  lazy page textures and a ~page-added~ signal.  Receives raw RGBA only.
- ~LrgFrameSurface~ (abstract, derivable) — the draw + present + projection
  facade and the *single seam* that makes 3D/VR additive.  Vtable:
  ~begin_frame~/~end_frame~, ~clear~, ~fill_rect~, ~draw_rect_outline~,
  ~draw_line~, ~push_clip~/~pop_clip~, ~draw_glyph~, ~draw_texture_region~,
  and ~pick~ (maps a pixel back to a logical cell, regardless of projection).
- ~Lrg2DSurface~ (final) — the concrete orthographic, pixel-exact v1 surface.
  Owns a ~GrlWindow~; presents to the *default framebuffer*.
- ~LrgTextRenderer~ (interface) — the abstract glyph-drawing contract so
  alternative renderers (e.g. SDF for crisp 3D text) can swap in.
- ~LrgRenderMode~ (enum): ~LRG_RENDER_MODE_2D~, ~_3D~ (both implemented),
  ~_3DVR~ (reserved — builds the 3D surface, mono).  3D adds
  ~Lrg3DSurface~ + ~LrgScenePanel~, ~LrgSpatialCamera~, the
  ~LrgSceneArrangement~ / ~LrgPanelEnvironment~ GInterfaces (+ built-in impls)
  and ~LrgModeRegistry~ (string-id → GType, the extension seam for new modes).
- Boxed: ~LrgGlyphKey~ ={font_id, glyph_code}=, ~LrgGlyphMetrics~ =(UV region,
  bearings, advance, is_color)=.  ~GrlColor~ is reused, not duplicated.

** Layer 3 — ~cmacs/lrgterm/~ (plain Emacs C glue)

*** Input parity with pgtk

The event loop (~lrg_read_socket~) translates raylib/GLFW input into the
same Emacs events pgtk produces:

- *Modifiers are event-carried and authoritative.*  graylib chains onto
  GLFW's key/button/focus callbacks and records the modifier bitmask GLFW
  computes from the window system's own tracking (xkb state on Wayland) —
  the same source GTK reads.  Polled key state latches: when a compositor
  global shortcut (GNOME's ~Super+Shift+S~ screenshot) swallows a
  modifier's key-release, raylib's cache reports Super held forever and
  every following key gets a phantom ~s-~ prefix.  The event-carried mask
  self-corrects on the very next key or button event, focus change or not.
  A polled fallback (with focus-stale filtering, driven by graylib's
  focus-generation counter so a loss+regain between two polls still
  counts) covers the pre-first-event window and non-GLFW platforms.
- *Shift parity*: special keys carry ~S-~ (~S-<tab>~, ~S-<f5>~,
  ~C-S-a~) exactly like pgtk; plain characters never do (case is already
  encoded in the char).
- *Real timestamps* (monotonic ms) on every event — double/triple-click
  counting works; with the old constant-0 stamps every same-spot click
  looked "within ~double-click-time~".
- *Full button set*: side/extra mouse buttons map to ~mouse-8~/~mouse-9~,
  and horizontal wheel/trackpad tilt emits ~HORIZ_WHEEL_EVENT~ with
  pgtk's direction convention (vertical already matched).
- *Mouse motion during ~track-mouse~* (drag tools) — see the
  ~mouse_moved~ / ~lrg_mouse_position~ contract note in the source.

~M-x cmacs-lrgterm-input-state~ echoes the live tracker for diagnosis —
check ~:armed~ first: ~t~ means the GLFW callback chain is live and
modifiers are event-carried; ~nil~ means the polled fallback is in
effect (headless, non-GLFW platform, or a window not yet up).  ~:serial~
should climb as you type; ~:event-mods~/~:emacs-mods~ show the raw and
translated masks, ~:focus-gen~ the focus-change counter.
~cmacs-lrgterm--mods-from-event-bits~ exposes the pure translation for
tests (~test/cmacs/cmacs-lrgterm-tests.el~, graylib's
~tests/test-input-event-mods.c~).  (Getting the GLFWwindow for the chain
uses ~glfwGetCurrentContext()~ — raylib's ~GetWindowHandle()~ returns the
NATIVE X11/Wayland handle, not the GLFWwindow, a trap that once left this
whole mechanism silently inert.)

*** Frame-parameter parity with pgtk

~lrg-create-frame~ defaults ~menu-bar-lines~, ~tab-bar-lines~ and
~tool-bar-lines~ to *0* (a number, like every other GUI backend), not the
unset ~nil~.  This is load-bearing: generic window code does arithmetic on
them — e.g. ~window-deletable-p~ evaluates ~(> (frame-parameter f
'tab-bar-lines) 0)~ — and a ~nil~ there signals ~(wrong-type-argument
number-or-marker-p nil)~, which aborts ~window--delete~ so that
~quit-window~ / ~quit-windows-on~ silently fail to close a window.  The
visible symptom was that every bottom popup (which-key, transient,
~*Completions*~, ~*Help*~) stayed open under ~--lrg~ and had to be closed by
hand, while pgtk (which sets the same defaults) worked.  lrg draws none of
these bars, so it forces ~0~ rather than following
~Vmenu-bar-mode~/~Vtab-bar-mode~/~Vtool-bar-mode~ the way pgtk does — which
is also consistent with ~cmacs-lrg-frame-geometry~ reporting all three bar
sizes as 0.

*** Text rendering (the font bridge)

lrg reuses Emacs's stock Cairo FreeType/HarfBuzz font drivers (~ftcrfont~ /
~ftcrhbfont~) *unchanged* for font discovery, opening, metrics and shaping —
font matching, fontsets and bidi behave exactly as under pgtk.  Only the
final pixel blit is redirected: the RIF's ~draw_glyph_string~ calls
~lrg_font_draw_glyph_string~ directly (NOT ~font->driver->draw~, which is the
Cairo painter), which rasterises each glyph via the font's ~cr_scaled_font~
into a small ARGB surface, converts it to an alpha-coverage RGBA mask
=(255,255,255,coverage)=, uploads it to the per-display ~LrgGlyphAtlas~ on a
cache miss, and paints it as a textured quad tinted by the face foreground.

*** Rendering / presentation model (full repaint, present on unblock)

lrg presents through a *double-buffered swap* of the default framebuffer (the
rlgl FBO bug rules out a retained off-screen surface — see §The load-bearing
risk in the plan).  Because each swap shows a different buffer, lrg cannot
honour Emacs's *incremental* RIF draws; those draw hooks are gated to no-ops
(an internal ~lrg_drawing~ flag) and instead the *whole* frame is repainted
from the current glyph matrix on every present: ~lrg_present_frame~ does
~begin_frame~ → ~clear~ → ~expose_frame~ (which re-runs the RIF draws with
~lrg_drawing~ true) → ~end_frame~ (~grl_window_swap_buffers~).  Repainting from
the matrix reuses all of Emacs's layout and is immune to the FBO bug.

The *timing* of the present is the subtle part.  Emacs wraps every redisplay
in ~block_buffer_flips~ … ~unblock_buffer_flips~ so a frame is never shown
half-updated; ~frame_up_to_date~ and all the RIF draw hooks therefore run while
buffer flips are *blocked*.  So lrg's real present point is the per-frame
~terminal->buffer_flipping_unblocked_hook~ (~lrg_buffer_flipping_unblocked~),
which Emacs calls from ~unblock_buffer_flips~ once the redisplay completes —
mirroring pgtk's ~buffer_flipping_unblocked_hook~.  This single hook is what
puts typed text, the blinking cursor, scrolling and every other redisplay on
screen; presenting from ~frame_up_to_date~ alone (while flips are blocked)
shows nothing, which was a real early bug.  ~lrg_capture-screen~ and the
~lrgterm_dump_screen~ MCP tool present out-of-band (their own
expose+swap), independent of this hook, so they always reflect current state.

*** Event loop

GLFW requires that window/input events be polled on the main thread, so lrg
does *not* use a separate input thread.  Instead ~lrg_term_init~ arms a
~timerfd~ (~16 ms ≈ 60 Hz) registered with ~add_keyboard_wait_descriptor~, so
Emacs's ~pselect~ wakes periodically and calls ~lrg_read_socket~, which polls
the window *once* (~grl_window_poll_events~ — the single poll point) and
translates the queued input into ~struct input_event~ s, then mouse
buttons/motion, focus and resize.  Presentation (~grl_window_swap_buffers~)
deliberately does *not* poll, so input is never double-consumed.

Keyboard translation drains raylib's key-press *queue*
(~grl_input_get_key_pressed~) in press order rather than scanning key state
per frame.  Each key becomes: a NON_ASCII keysym for mapped non-character
keys (ESC → ~escape~, arrows, Tab, …); a char-with-modifiers for a printable
key held with Ctrl/Meta; or, for a printable key with no modifier, the next
Unicode char from the char queue (which encodes layout + shift), pulled at
the key's position so it stays interleaved with function keys pressed in the
same poll.  The queue guarantees every keystroke is delivered exactly once,
in order — no missed fast taps and no 60 Hz auto-repeat storm — which a
per-frame state scan could not, and which is why Evil/Doom keybinds (ESC to
normal mode, ~hjkl~, chords) behave as they do under pgtk.

The OS window is user-resizable: ~lrg_window_create~ sets
~GRL_FLAG_WINDOW_RESIZABLE~ on the raylib window (which otherwise opens
fixed-size — no corner-drag, no maximize button), and ~lrg_read_socket~
re-fits the Emacs frame to the new pixel size on every
~grl_window_is_resized~ via ~change_frame_size~.

*** libregnum 3D buffers under --lrg

The *cmacs-libregnum* subsystem (the libregnum editor, ~gnuseye~, the
CAD/STL model viewer) renders its 3D scenes through libregnum too.  raylib
allows only one window per process, so under ~--lrg~ these features do *not*
open a second window (which would deadlock); instead they BORROW the lrg
backend's window + GL context.  ~cmacs_libregnum_render_window_acquire~
detects an active lrg frame (~cmacs_lrgterm_active_p~, linked weakly) and
sets up a windowless renderer; each view renders its scene into its own FBO
(the lrg GL context is current on the main thread), and the lrg present
(~lrg_paint_libregnum_views~) blits each view's FBO colour texture into its
buffer's window rect via ~lrg_frame_surface_draw_texture_region~ — the
analogue of pgtk's cairo overlay (~cmacs_libregnum_overlay_paint~).  So
~M-x gnuseye~, ~M-x cmacs-libregnum-editor~ and opening an STL all render
inside the lrg frame.

Mouse navigation into these views works too: ~lrg_read_socket~ routes pointer
motion, button presses/releases and the wheel into the same input router pgtk
uses (~cmacs_libregnum_handle_motion~/~_button~/~_scroll~), so left/right-drag
orbits, middle-drag pans, the wheel zoom-s the viewport under the pointer, a
click picks a node, and right-click pops the context menu.  Because the
libregnum router expects X11/GDK button numbers, lrg maps raylib L/R/M
(0/1/2) → 1/3/2, and negates the raylib wheel sign to match pgtk's zoom
direction.  A wheel event that *isn't* over a view becomes a normal Emacs
~WHEEL_EVENT~, so buffers scroll with the wheel under ~--lrg~ as well.  (In-scene
text labels are still a follow-up; everything else interacts now.)

Because lrg has no native (GTK) popup menus (~menu_show_hook~ returns nil), the
libregnum/gnuseye right-click context menus are drawn *in-engine*, with
cascading fly-out submenus: the ~lrg-popup-menu~ primitive renders a GTK-like
popup with libregnum (a panel + hovered/disabled rows + separators + a ~›~
arrow on submenu rows, label text via the glyph atlas) and runs a modal loop
over a *stack* of open panels (hover opens a submenu to the right — flipping
left at the screen edge; left-click chooses a leaf; right-click/ESC/click-
outside dismiss; up/down move, right/RET open a submenu or choose, left closes
one), exactly like ~x-popup-menu~'s own modal loop.  ~cmacs-libregnum-popup-menu~
flattens an Emacs menu (alist *or* keymap form, submenus kept as real nested
nodes) into the item tree it takes, then maps the chosen leaf index back to its
value; on graphical frames it still pops the native menu.  Runs of separators
(common once kind-filtering drops the items between them) collapse to a single
thin divider, and a separator row is half height, so the menu stays compact.  And since those 3D
buffers sit in Evil *emacs state*
for their single-key navigation, ~<escape>~ is bound to drop them to Evil
*normal* state (gnuseye's ~<escape>~ first deselects a selected entity, then
escapes); re-enter navigation with ~C-z~ (~evil-emacs-state~).

*** gsurf web buffers under --lrg

The *cmacs-gsurf* web browser composites the same way when built with
=--with-cmacs-gsurf-lrg=.  A gsurf buffer's page is rendered to a libregnum
=GrlTexture= by gsurf's libregnum backend (offscreen WebKitGTK → texture) and
=lrg_paint_libregnum_window= blits it into the buffer's window rect alongside
the libregnum 3D buffers (gsurf's readback is top-down, so unlike the FBO
views it is *not* Y-flipped).  =lrg_read_socket= offers pointer motion /
buttons / wheel to =cmacs_gsurf_lrg_handle_*= right after the libregnum
handlers, and — while a page holds focus
(=cmacs_gsurf_lrg_page_focused_p=) — routes the keyboard to it via
=lrg_route_keys_to_gsurf= instead of =lrg_drain_keys= (Escape releases focus
back to Emacs).  See *CMacs Gsurf* → *Render backends* for the full model.

* Render modes (2D + 3D; VR reserved)

The abstract ~LrgFrameSurface~ + ~LrgRenderMode~ + ~pick~ seam makes each mode
additive: Layer 3 (the Emacs glue) only ever calls the base surface vtable, the
glyph atlas / ~LrgTextRenderer~ are projection-free, and input routes through
~pick~ (identity in 2D, a ray-cast in 3D/VR).

- ~2d~ (default) — ~Lrg2DSurface~: flat, pixel-exact.  Plain ~emacs --lrg~.
- ~3d~ — ~Lrg3DSurface~: the Emacs frame is rasterised flat and captured to a
  texture each redisplay, then drawn as one or more textured *panels* in a
  real-time 3D scene viewed through a perspective camera.  (Internally the 3D
  surface owns an ~Lrg2DSurface~ and delegates the flat rasterisation to it,
  then composites the captured texture onto panels — no renderer duplication.)
  The default camera is a gentle (~14°) elevated 3/4 view, so the panels show
  real perspective and the environment floor recedes into the distance on launch
  rather than looking head-on/flat; orbit/zoom it with =C-c 3= (arrows / =+= /
  =-=, =0= to reset).
- ~3dvr~ — reserved; today it builds the 3D surface (mono).  A future
  ~LrgVRSurface~ renders the same scene per-eye.

** 3D mode

Launch with a colon-/comma-separated SPEC after the mode token
(~MODE[:ARRANGEMENT][:ENVIRONMENT]~):

#+begin_src sh
emacs --lrg=3d                       # one floating panel, void backdrop
emacs --lrg=3d:per-window            # one panel per Emacs window
emacs --lrg=3d:per-window:workshop   # ... on a grid-floor workbench
emacs --lrg=3d:cockpit               # enclosed grid "cockpit" room
#+end_src

Two orthogonal axes, each also switchable at runtime:

*Arrangement* (panel layout):
- ~single-panel~ — the whole frame on one panel.
- ~per-window~ — each Emacs window on its own panel, mirroring the window tree
  (the minibuffer becomes its own panel).
- ~free~ — per-window panels with independent transforms (spatial WM; basic).

*Environment* (ambient scene):
- ~void~ — plain dark backdrop.
- ~workshop~ — a grid floor beneath the panels.
- ~cockpit~ — an enclosed grid room (floor + back + side walls).

New arrangements / environments are added by implementing the
~LrgSceneArrangement~ / ~LrgPanelEnvironment~ GInterfaces and registering an id
with ~LrgModeRegistry~ — no surface or glue changes.

*Depth-of-field*: the selected window's panel is focused (bright/forward) and the
others recede/dim; with the global ~cmacs-lrg-3d-mode~ on, focus follows the
selected window.

*Runtime control* — ~cmacs-lrg-3d-mode~ (auto-enabled for lrg frames) binds the
commands under the ~C-c 3~ prefix:

| Command | Key | Description |
|---------+-----+-------------|
| ~cmacs-lrg-set-arrangement~ | =C-c 3 a= | switch arrangement (completing-read) |
| ~cmacs-lrg-set-environment~ | =C-c 3 e= | switch environment |
| ~cmacs-lrg-3d-describe~ | =C-c 3 ?= | echo mode / arrangement / environment |
| ~cmacs-lrg-camera-reset~ | =C-c 3 0= | reset the camera |
| ~cmacs-lrg-camera-zoom-in~ / ~-out~ | =C-c 3 += / =-= | dolly toward / away |
| ~cmacs-lrg-camera-orbit-{left,right,up,down}~ | =C-c 3 <arrows>= | orbit |
| ~cmacs-lrg-focus-window~ | =C-c 3 f= | bring the selected window's panel front-and-centre (fly the camera) |
| ~cmacs-lrg-maximize-window~ | =C-c 3 2= | flat *2D view*: maximize the selected window's panel head-on, level, filling the viewport (like the 2D backend / PGTK).  =C-c 3 0= returns to 3D |
| ~cmacs-lrg-pin-window~ / ~cmacs-lrg-unpin-window~ | =C-c 3 p= / =u= | pin the selected panel in place / release it to auto-layout |
| ~cmacs-lrg-unpin-all~ | =C-c 3 U= | release every panel to auto-layout |
| ~cmacs-lrg-place-wall~ / ~cmacs-lrg-clear-wall~ | =C-c 3 w= / =W= | show a 3D-view buffer (gnuseye globe, gobject graph, …) on the cockpit back wall / clear it |

~emacsclient --lrg=3d:per-window:workshop~ spawns a matching frame.

** Spatial interaction

The interaction model is *hybrid*: by default the room responds to your attention
(/command-the-room/) and you can also take manual control when you want.

- *Command* (default): focus a panel and the camera flies it front-and-centre
  while the others recede/dim — by *Ctrl+double-left-click*, by =C-c 3 f=, or by
  voice/AI via MCP.  Selecting a window moves the depth-of-field focus to it
  (and, with ~cmacs-lrg-3d-focus-follow-flies-camera~ set, flies the camera too).
- *Manual override*: orbit the view and drag panels into your own arrangement;
  *pin* a panel (=C-c 3 p=) so it keeps its place across re-layouts, resizes and
  arrangement switches; =C-c 3 u= / =U= release it / all back to auto-layout.

Default *mouse* bindings (all rebindable — see /Device-agnostic intent layer/):

| Gesture | Action |
|---------+--------|
| plain left-click / drag | place point / select region (normal Emacs) |
| *Ctrl + left-click* | peek-focus the panel (depth-of-field only) |
| *Ctrl + double-left-click* | focus the panel *front-and-centre* (fly the camera); on a *workspace* panel, *switch* to that workspace |
| *Ctrl + left-drag* | first-person *look*: turn the camera in place about its own position (the view swings around the eye) |
| *middle-drag* | orbit the camera around the *room* (the whole scene), not just a focused panel |
| *Ctrl/Super + middle-drag* | grab and move the panel under the pointer (it pins) |
| middle-click (no drag) | normal Emacs ~mouse-2~ (yank) |
| *Ctrl + wheel* | dolly the camera in / out (zoom) |
| *Super + drag* | trackpad alias for middle-drag (orbit / move) |
| wheel | scroll the buffer |

When the pointer is over a window hosting a *libregnum view* (gnuseye, the
libregnum editor, a CAD/STL viewer), the 3D spatial gestures *defer to that app*
— middle-drag, Ctrl+wheel and clicks go to the view's own camera/controls
(routed at the picked frame pixel), so the workspace navigation never fights an
embedded app's navigation.

Mouse motion / plain clicks still ray-cast onto the panel under the pointer
(~cmacs-lrg-3d-pick~ / ~cmacs-lrg-3d-pick-panel~ expose the mapping), so editing
in 3D lands on the right buffer cell.

*** Device-agnostic intent layer

The spatial controls are *intents*, not raw buttons: every gesture maps to a C
method that is also a DEFUN and an MCP tool, so the mouse is just the first input
device.  The high-rate drag math runs in C (no Lisp round-trip), mirroring
~cmacs-libregnum-input.c~.

| Intent | DEFUN | MCP tool |
|--------+-------+----------|
| focus a panel front-and-centre | ~cmacs-lrg-3d-focus-panel~ | ~lrgterm_3d_focus_selected~ |
| maximize a panel head-on (flat 2D view) | ~cmacs-lrg-3d-maximize-window~ | — |
| orbit / dolly the camera | ~cmacs-lrg-3d-orbit~ / ~-dolly~ / ~-camera~ | ~lrgterm_3d_camera_orbit~ |
| move a panel by a world delta | ~cmacs-lrg-3d-move-panel~ | — |
| pin / unpin a panel | ~cmacs-lrg-3d-pin-panel~ / ~-unpin-panel~ | ~lrgterm_3d_pin_selected~ / ~lrgterm_3d_unpin_all~ |
| ray-cast a pixel to a panel | ~cmacs-lrg-3d-pick-panel~ | — |
| switch to a workspace panel | ~+workspace-switch~ (via ~cmacs-lrg-3d-take-pending-workspace~) | — |
| place / rotate a workspace panel | ~cmacs-lrg-3d-place-workspace-panel~ / ~-place-workspace-panel-eased~ / ~-rotate-workspace-panel~ | — |
| render a workspace off screen | ~cmacs-lrg-3d-render-into-panel~ (between ~-begin-offscreen~ / ~-end-offscreen~) | — |

Because the binding layer is data-driven, future devices — a SpaceMouse/6DOF
(gamepad-axis bindings), Wayland gestures, or VR controllers — bind to the *same*
intents with no rendering or glue changes, and voice/AI ("Jarvis, bring the diff
front and centre") drive them through MCP.  This is the path toward the
/stark-mode/ workshop without re-architecting.

*Gamepad / 6DOF* (the first non-mouse device on this seam): a connected gamepad
drives the camera through a libregnum ~LrgInputMap~ — right stick orbits the
room, left stick pans, triggers dolly — reading each axis as a *signed* analog
value (~lrg_input_map_get_axis~) and calling the same orbit/pan/dolly intents.
It is polled ~60 Hz and is a no-op when no gamepad is present.  The map is data:
~cmacs-lrg-3d-load-gamepad-bindings~ FILE loads a YAML remap, so a SpaceMouse or
other 6DOF device exposed as a joystick is rebound without code (a native
SpaceMouse via ~libspnav~ remains a roadmap item).

** Spatial workspaces (the workspace carousel)

With Doom / persp-mode workspaces, the *workspace carousel* shows *every
workspace* as a live panel in 3D: the current workspace is the live centre (the
real window panels), and each other workspace renders its *real contents* into a
panel arranged on a curved arc ("carousel") that curves away from you.  You see
all your workspaces at once, move/rotate them, and switch between them in 3D.

It turns on *automatically* on a 3D lrg frame once persp-mode is active (the
=cmacs-lrg-3d-workspaces-auto= defcustom; set it to nil, or toggle by hand with
=cmacs-lrg-3d-workspaces-mode= / =C-c 3 m=).  The immediate neighbours sit in view
at the default camera; pull back with =C-c 3 o= (overview) — or orbit
(middle-drag) — to see the rest of the ring.

The other workspaces are *not snapshots* — each one keeps rendering its actual
buffers off screen, so a compile running in another workspace updates on its panel
while you work.  This rides a deferred primitive: a non-current workspace's saved
window layout is installed in the frame off screen, redisplayed (so its buffers'
current contents draw), captured to that workspace's own panel texture, and the
live layout restored — all without disturbing what you see
(~cmacs-lrg-3d-begin-offscreen~ / ~-render-into-panel~ / ~-end-offscreen~).

A repeating timer keeps them live: each tick re-renders at most *one* off-screen
workspace whose content changed since it was last drawn (round-robin, with
dirty-tracking via buffer modification ticks), so idle workspaces cost nothing and
a changing one updates roughly every (interval × workspace-count) seconds.  The
current workspace is always full-rate (it is the real frame).  This is the
performance trade-off of live (not snapshot) workspaces; tune it below or set
~cmacs-lrg-3d-workspaces-live~ to nil to update panels only on switch / refresh.

Layout follows ~+workspace-list-names~ order: a workspace's slot is its position
*relative to the current one*, so the current workspace is always centred and
switching shifts the carousel.  Switching (via ~SPC TAB <n>~, ~+workspace-switch~,
or a click — see below) eases the carousel smoothly to the new arrangement.  A
workspace you move (Ctrl/Super + middle-drag its panel) or rotate keeps its place
— the transform is remembered per workspace (a ~lrg-3d-xform~ persp-parameter).

*Switch by clicking*: *Ctrl+double-left-click* a workspace panel to switch to it.
(The same chord focuses a window panel front-and-centre; on a workspace panel it
switches.)  The click is handled in the command loop, so the persp hooks and the
eased transition fire exactly as for ~SPC TAB <n>~.

Commands (all under the =C-c 3= prefix of `cmacs-lrg-3d-mode', and via =M-x=):

| Command | Key | Action |
|---------+-----+--------|
| ~cmacs-lrg-3d-workspaces-mode~ | =C-c 3 m= | toggle the carousel (global mode) |
| ~cmacs-lrg-3d-workspaces-toggle~ | =C-c 3 SPC= | hide / show the ring (centre unaffected) |
| ~cmacs-lrg-3d-workspaces-overview~ | =C-c 3 o= | pull the camera back to see all workspaces |
| ~cmacs-lrg-3d-workspaces-rotate~ | =C-c 3 r= | rotate a chosen workspace panel (remembered) |
| ~cmacs-lrg-3d-workspaces-refresh~ | =C-c 3 g= | relayout + re-render every panel now |

No-op without persp-mode or off a 3D lrg frame.

* Clipboard, fonts, faces

- *Clipboard*: the system clipboard maps to Emacs's ~CLIPBOARD~ selection
  (~grl_window_get/set_clipboard_text~); kill/yank interoperate with other
  applications.  ~PRIMARY~ and non-text targets are not supported by the
  windowing layer.
- *Colours*: colour names are resolved through pango's X11 ~rgb.txt~ table, so
  the full Emacs default-face palette (~Firebrick~, ~Blue1~, ~grey75~, …)
  renders correctly.
- *Faces*: foreground/background, font-lock colours, the region, the modeline
  (with its 3D box), and text decorations (underline single/double, overline,
  strike-through, box) are all drawn.
- *Fringes*: the standard 8 px graphical fringes are on; continuation /
  truncation / overlay-arrow bitmaps are drawn (not the no-fringe ~\~/~$~ text
  indicators).  The cursor blinks (~blink-cursor-mode~).
- *Transparency* (~alpha-background~): the OS window is created with a
  transparent (32-bit ARGB) framebuffer, and the ~alpha-background~ frame
  parameter (Emacs 29's translucent-background feature) is honored — the frame
  is cleared and every face background is filled at that alpha (using a
  source/replace blend so non-default backgrounds composite over the desktop,
  mirroring pgtk's ~CAIRO_OPERATOR_SOURCE~), while text and other foreground
  stay opaque.  So ~(set-frame-parameter nil 'alpha-background 85)~ (or
  ~(add-to-list 'default-frame-alist '(alpha-background . 85))~) lets the
  wallpaper show through, exactly as under pgtk.  Requires a compositing
  display server (any modern Wayland/X11 desktop).
- *Inline images*: image glyphs (PNG, XPM, JPEG, …) are drawn.  In this
  Cairo build the loaded pixels live in the image's ~cr_data~ Cairo pattern;
  the backend converts that surface to a straight-RGBA ~GrlTexture~ (caching it
  as Cairo user-data so it is freed with the image) and blits it with
  ~lrg_frame_surface_draw_texture_region~, honouring ~:scale~ / ~:width~ /
  slices.  This covers the Doom dashboard banner, ~README.org~ image links, etc.

* Known v1 limitations

These are genuine, acceptable and documented; most match the phased plan:

- *One OS window per terminal, but child frames work as in-window overlays.*
  raylib's process-global state makes true multi-window a graylib engine change,
  so a second *top-level* frame is still refused (~lrg-create-frame~ signals an
  error rather than open a stray second OS window).  A *child frame*, however
  (~parent-frame~ set) — corfu/company popups, ~posframe~, tooltips — is created
  WITHOUT its own OS window and *composited as an overlay inside the parent's
  single window*: the parent's present pass draws each visible child at its
  =(left, top)= via a per-surface draw offset and ~expose_frame~
  (~lrg_composite_child_frames~).  So corfu's popup shows at point (in 2D and, in
  3D, captured onto the panel).  Limits: the child takes no keyboard input
  (corfu redirects focus to the parent, so this is fine); *mouse-clicking* a
  popup candidate is not yet routed to the child (keyboard selection works) —
  a follow-up.
- *Menus / dialogs*: the Emacs *menu bar* is not drawn — keyboard menu access
  is via ~M-x tmm-menubar~ / =F10=; dialogs route to the minibuffer
  (~use-dialog-box~ is ~nil~).  The libregnum/gnuseye right-click *context*
  menus, however, ARE drawn in-engine (~lrg-popup-menu~; see /libregnum 3D
  buffers under --lrg/).
- *Scroll bars*: not drawn (off by default).
- *Tool bar*: not drawn.  (Child frames / popups *are* composited as in-window
  overlays — see the one-OS-window item above; inline images *are* drawn — see
  /Clipboard, fonts, faces/.)
- *Mouse-pointer shapes*: the pointer does not change to an I-beam etc. yet.
- *IME*: direct/Quail input only (real CJK *input* — not display — is a gap).
- ~--lrg~ and ~--gowl~ are mutually exclusive at startup.
- *3D mode resize*: panels re-fit on a window resize — the surface reconciles
  its geometry to the live window each frame, re-runs the arrangement layout, and
  eases the panels to the new size (driven by the 60 Hz recompose tick).  Sizing
  is *always-fit*: the frame fills the camera view at a fixed world height with
  the width following the frame aspect, so the whole frame stays visible and
  consistently framed at every window size (text reflows with the frame, as in
  any Emacs frame).
- *3D mode v1*: camera / focus / resize animate smoothly and the mouse ray-casts
  onto the panel under it, but an ARRANGEMENT switch snaps (no cross-fade), and the
  heavier signature features — live dashboards as ~cockpit~ walls (the gnuseye
  globe), the Rolodex buffer switcher and git-history-as-depth — are designed but
  deferred.  See [[file:cmacs-lrgterm-3d-roadmap.org]].

* Troubleshooting

- *Window does not appear / "No lrg display"*: ensure the graylib shared
  library is on ~LD_LIBRARY_PATH~ (~just run~ handles this), and that you
  passed ~--lrg~ (plain ~emacs~ starts pgtk).
- *Everything renders black / no colours*: this was a face-realisation bug
  (lrg not recognised as a colour display) — fixed; if it recurs after a
  merge, re-check that ~lrg~ is present in the ~display-graphic-p~ /
  ~display-color-cells~ / ~face-spec-set-match-display~ lists (see the
  upstream-changes catalogue).
- *Typed text does not appear until you click / cursor never blinks*: the
  on-screen present is not running.  lrg presents only from
  ~terminal->buffer_flipping_unblocked_hook~ (the screen is otherwise frozen
  because ~frame_up_to_date~ and the RIF hooks all run while buffer flips are
  blocked).  Verify that hook is wired in ~lrg_create_terminal~ (see §Rendering
  / presentation model).  Capturing with ~lrg-capture-screen~ will still look
  correct in this state because it presents out-of-band.
- *A stray, blurry second desktop window appears (often on completion / a
  prompt)*: historically lrg spawned a broken second OS window for a *child
  frame* (~posframe~, ~corfu~/~company~ popup, ~which-key-posframe~, a GUI
  tooltip).  lrg now composites child frames as *in-window overlays* (see
  /Child-frame UIs/), so this should no longer happen; if a stray window still
  appears it is a second *top-level* frame, which lrg refuses (one OS window per
  process).  Run ~emacs -Q --lrg=3d~ to rule out config.
- *A PGTK frame freezes right after a popup (LSP/~corfu~/~company~ autocomplete,
  a tooltip); GNOME says "Force quit or Wait"; a ~--fg-daemon~ then dies*: this
  is a *pgtk-on-Wayland* limitation, *not* an lrg bug — it hits ordinary
  ~emacs~/~emacsclient~ pgtk frames, and the lrg backend is one of the fixes
  (below).  Emacs built with PGTK *cannot survive a Wayland display-connection
  disconnect* (a GTK 3 limitation; the daemon prints exactly this warning at
  startup), and *child-frame popups* (~corfu~/~company~, ~posframe~,
  ~which-key-posframe~, GUI tooltips) are the usual trigger: a Wayland
  popup-protocol hiccup wedges or drops the compositor connection, the frame
  freezes, and the PGTK process can no longer recover (a ~--fg-daemon~ then
  exits, often via ~kill-emacs-hook~, with no crash or coredump).
  *Confirm it is this and not a wedge in cmacs*: the process sits at ≈0% CPU in
  the plain idle command loop — a thread dump shows ~command_loop_1 →
  read_key_sequence → read_char → wait_reading_process_output → pselect~ with an
  *empty Lisp backtrace* (no ~lrg_*~ / ~cmacs_glib_*~ / LSP-process frames), and
  there is no SIGSEGV/SIGABRT/coredump — it is a lost display, not a deadlock.
  *Fixes*: (1) run the daemon under *XWayland* — add
  ~Environment=GDK_BACKEND=x11~ to ~emacs.service~ (or launch
  ~GDK_BACKEND=x11 emacs~); pgtk-on-X11 child frames are robust and survive
  display hiccups; (2) or use the *lrg backend* (~emacs --lrg~ /
  ~emacsclient --lrg~), where child frames are in-window overlays so there is no
  Wayland popup protocol to break and lrg owns its own window.
- *Verifying rendering*: use ~(lrg-capture-screen "/tmp/x.png")~ — it reads
  the backend's own framebuffer in-process (no screen-capture portal needed).
