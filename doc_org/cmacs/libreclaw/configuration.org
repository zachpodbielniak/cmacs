#+TITLE: LibreClaw Configuration
#+AUTHOR: Zach Podbielniak

* Where configuration lives

LibreClaw reads a single YAML file at startup.  There are three
ways to tell cmacs-libreclaw which file to use:

** Option A — declarative, in your init file

#+begin_src elisp
(setq cmacs-libreclaw-config-file "~/.libreclaw/work.yaml")
#+end_src

Clean and idiomatic.  The path is expanded and checked the
first time =cmacs-libreclaw-start= (or =cmacs-libreclaw-open=)
runs — if the file is missing or unreadable the start errors
out with a pointer at the exact path.

** Option B — imperative, one-shot

#+begin_src elisp
(cmacs-libreclaw-load-config "~/.libreclaw/work.yaml")
#+end_src

Does the same thing, but also handles the "libreclaw is already
running" case: pass a non-nil second argument or answer the
=y-or-n-p= prompt and it cleanly stops the subsystem and
restarts it against the new config.  Useful when you need to
switch configs mid-session (e.g. jumping between a work bot and
a personal one).

Interactive: =M-x cmacs-libreclaw-load-config= prompts with
completion for the YAML path.

** Option C — let the default-config generator take over

If you never set =cmacs-libreclaw-config-file= at all,
=cmacs-libreclaw-start= calls =cmacs-libreclaw-ensure-config=,
which prompts to auto-generate a minimal default at
=cmacs-libreclaw-default-workspace= (=~/.libreclaw=) on first
run.  See [[#first-run-auto-generated-config][First-run
auto-generated config]] below.

** Switching vs. reloading

- =cmacs-libreclaw-load-config= switches to a *different* file
  and restarts the subsystem (if requested).  Session state in
  the old config is flushed.
- =cmacs-libreclaw-reload-config= re-reads the *same* file and
  fires libreclaw's =config-reloaded= signal, so live edits to
  your YAML take effect without a full restart.  Use this for
  tweaking things like the AI model, podomation DSL, or
  =identity_files= list while the subsystem is running.

The YAML schema is owned by libreclaw (not cmacs) so that upgrading
libreclaw automatically expands the set of supported keys.  See the
libreclaw documentation at =deps/libreclaw/docs/configuration.md=
for the canonical reference.

* First-run auto-generated config

You don't have to hand-author a YAML to get started.  On first use
=cmacs-libreclaw-start= calls =cmacs-libreclaw-ensure-config=, which:

1. adopts an existing =config.yaml= at
   =cmacs-libreclaw-default-workspace= if one is already there, or
2. prompts you (=yes-or-no=) to auto-generate a minimal default at
   that path — a single Local stdin/stdout channel, your choice of
   AI provider, no podomation, no audit log.  The raw
   =cmacs-libreclaw-generate-default-config= DEFUN does the work
   through libreclaw's =lc_hatch_*= library API, so the schema is
   always in sync with the libreclaw version you linked against.

To trigger it manually (without starting libreclaw):

#+begin_src elisp
M-x cmacs-libreclaw-generate-default-config
#+end_src

Customization knobs:

- =cmacs-libreclaw-default-workspace= — target directory (default
  =~/.libreclaw=)
- =cmacs-libreclaw-default-ai-provider= — symbol: =claude=,
  =openai=, or =both=
- =cmacs-libreclaw-default-prompt= — prompt for the generated
  Local channel
- =cmacs-libreclaw-auto-generate-config= — set to =nil= to disable
  the auto-prompt and force users to run the generator explicitly

For a richer wizard (Matrix credentials, email channels, podomation
DSL, audit log) use =M-x cmacs-libreclaw-hatch= instead —
[[file:hatch.org][hatch.org]] walks through it.

* Minimal example

#+begin_src yaml
agent:
  name: "my-bot"
  workspace: "/home/me/.libreclaw"

providers:
  - name: claude
    kind: claude-code
    command: "claude -p"
    model: claude-opus-4-5

channels:
  - id: local
    kind: local
    prompt: "libreclaw> "

podomation:
  enabled: true
#+end_src

* Ollama as the Claude Code transport

The =claude-code= and =claude-code-tmux= (a.k.a. =claude-tmux=) provider
kinds understand a special model form: when =model:= begins with =ollama/=,
the provider does *not* spawn =claude= directly --- it routes the turn
through Ollama as the transport:

#+begin_src yaml
providers:
  - name: glm
    kind: claude-code              # or claude-code-tmux
    model: "ollama/glm-5.2:cloud"  # => ollama launch claude --model glm-5.2:cloud -- ...
#+end_src

So =model: ollama/glm-5.2:cloud= makes libreclaw run

#+begin_example
ollama launch claude --model glm-5.2:cloud -- <the usual claude args>
#+end_example

Requirements and behaviour:

- Both =ollama= and =claude= must be installed and on =$PATH= (=ollama
  launch claude= execs the real =claude= binary; override the launcher path
  with the =OLLAMA_PATH= environment variable).
- claude's own =--model= flag is omitted --- the model is carried by =ollama
  launch --model=.
- A =model:= *without* the =ollama/= prefix is unchanged: plain =claude= is
  spawned as before.

This is implemented entirely in the underlying =ai-glib= CLI providers, so it
applies to any libreclaw provider of kind =claude-code= / =claude-code-tmux=
with no further configuration.  To preview the exact command outside
libreclaw, use ai-glib's =ai= CLI: =ai -p claude-code -m ollama/glm-5.2:cloud
--dry-run "hi"=.

* auth-source for secrets

LibreClaw's YAML supports =${auth-source:host:user}= indirection in
any string field.  At load time it calls out to Emacs's
=auth-source= to fetch the actual value.  The recommended pattern:

1. Store your Matrix token, email password, or API key via
   =auth-source-secrets-create= (or =authinfo.gpg=).
2. Reference it in YAML by host and user.
3. The raw secret never touches the YAML file or the hatch buffer.

#+begin_src yaml
channels:
  - id: matrix
    kind: matrix
    homeserver: "https://matrix.example.com"
    user_id: "@bot:example.com"
    access_token: "${auth-source:matrix:@bot:example.com}"
#+end_src

The hatch wizard (=M-x cmacs-libreclaw-hatch=) automatically writes
YAML with this pattern when you enter secrets at the =read-passwd=
prompt — the raw value is stored via auth-source and the YAML keeps
only the indirection.

* Hot reload

Once started, you can re-read the config file without restarting:

#+begin_src elisp
M-x cmacs-libreclaw-reload-config
#+end_src

This re-parses the file and fires libreclaw's =config-reloaded=
signal, which the podomation bridge translates into
=on_cm_lc_config_reloaded= for DSL rules.  Channel creation /
destruction on reload is subject to libreclaw's own rules — see its
docs for which fields can change at runtime.

* Customization (core)

- =cmacs-libreclaw-config-file= — the YAML path
- =cmacs-libreclaw-auto-start= — if non-nil, start on after-init-hook
- =cmacs-libreclaw-buffer-name-format= — printf format for generic
  room buffer names; defaults to =*libreclaw:%s:%s*= (channel /
  room-id).  Not used by the cmacs channel, which has its own
  formatter.
- =cmacs-libreclaw-my-name= — the label used for locally-echoed
  outbound messages (defaults to ="you"=)
- =cmacs-libreclaw-timestamp-format= — strftime format for message
  heading timestamps
- =cmacs-libreclaw-message-hook= — run on every inbound message
- =cmacs-libreclaw-room-added-hook= — run when a new room buffer is
  created
- =cmacs-libreclaw-save-conversations-dir= — directory to archive
  embedded-mode conversations into; =nil= (default) disables it.
  See [[*Archiving conversations to disk][Archiving conversations to disk]].
- =cmacs-libreclaw-save-conversations-name-format= — file-name
  format for those archives; default
  ="%y%m%d-%H%M%S-<agent-name>.org"=

* Customization (cmacs channel)

- =cmacs-libreclaw-default-workspace= — where the first-run default
  config lives (default =~/.libreclaw=)
- =cmacs-libreclaw-default-ai-provider= — symbol =claude=, =openai=,
  or =both=; baked into the generated YAML as =ai.model=
- =cmacs-libreclaw-auto-generate-config= — prompt to create a
  default on first run (default =t=)
- =cmacs-libreclaw-cmacs-channel-history-dir= — where per-project
  buffer history is persisted; default
  =~/.libreclaw/cmacs-sessions=
- =cmacs-libreclaw-cmacs-channel-sender= — identifier used as the
  sender component in the session key
  =cmacs:<project-root>:<sender>=; defaults to =$USER=
- =cmacs-libreclaw-cmacs-channel-buffer-name-format= — printf
  format for chat buffer names; =%s= is the project basename
- =cmacs-libreclaw-cmacs-channel-autosave-history= — if non-nil,
  persist on kill/save (default =t=)

Set these via =M-x customize-group cmacs-libreclaw RET= /
=cmacs-libreclaw-cmacs-channel RET= or with =setq= in your init
file.

* Customization (remote mode)

These apply only to "remote" mode (see [[file:remote.org][LibreClaw Remote Mode]]).
~M-x customize-group cmacs-libreclaw-remote~ for the full list; the
load-bearing ones for chat/command behaviour are:

- =cmacs-libreclaw-remote-mcp-servers= (default =(cmacs)=) — list of
  MCP endpoint specs to expose to the remote libreclaw.
- =cmacs-libreclaw-remote-display-name= (default ~nil~) — display
  name advertised to the remote server.
- =cmacs-libreclaw-remote-user-id= (default ~nil~) — stable
  =sender_id= for outbound chat.  When nil, resolved at connect
  time to =$USER=, then ~(user-login-name)~, then to nil (server
  falls back to the unstable bridge id).  This is what libreclaw's
  =session.command_allowed_users= / =messages.command_allowed_users=
  match against to enable session/message bot commands like
  =!close_session=, =!swap_model=, =!stop=, =!sessions=.  See
  [[file:remote.org::*Enabling bot commands on the bridge][Enabling bot commands on the bridge]] for the
  full recipe.
- =cmacs-libreclaw-remote-local-room-id= (default ="local"=) — room
  id used by =cmacs-libreclaw-remote-chat=.
- =cmacs-libreclaw-remote-local-room-name= (default ="Bridge"=) —
  display label for the local-style chat buffer.
- =cmacs-libreclaw-remote-save-conversations-dir= (default ~nil~) —
  directory to archive remote-bridge conversations into.
  Independent of the embedded-mode
  =cmacs-libreclaw-save-conversations-dir=.  See
  [[*Archiving conversations to disk][Archiving conversations to disk]].
- =cmacs-libreclaw-remote-save-conversations-name-format= (default
  ="%y%m%d-%H%M%S-<agent-name>.org"=) — file-name format for those
  archives.

* Archiving conversations to disk

By default libreclaw conversations are ephemeral — they live only
in their room buffers (the cmacs channel is the exception; see
[[*Per-project session persistence][Per-project session persistence]]).  Setting an archive directory
turns on a readable, opt-in on-disk archive: every conversation is
mirrored to a standalone =.org= file that is rewritten as messages
arrive and again when the room buffer is killed.

Embedded mode and remote mode keep *separate* settings, so you can
archive them to different directories — or only one of them:

- =cmacs-libreclaw-save-conversations-dir= — archive directory for
  embedded-mode conversations (Matrix, email, webhook, the Local
  channel, and the native cmacs channel).
- =cmacs-libreclaw-remote-save-conversations-dir= — archive
  directory for remote-bridge conversations.

Both default to =nil=, which disables archiving.  Enable it from
your init file, for example:

#+begin_src emacs-lisp
(setq cmacs-libreclaw-save-conversations-dir
      "~/Documents/notes/libreclaw")
(setq cmacs-libreclaw-remote-save-conversations-dir
      "~/Documents/notes/libreclaw-remote")
#+end_src

The file name comes from a customizable format —
=cmacs-libreclaw-save-conversations-name-format= for embedded mode
and =cmacs-libreclaw-remote-save-conversations-name-format= for
remote mode.  Both default to ="%y%m%d-%H%M%S-<agent-name>.org"=.
The string is first run through =format-time-string= with the
conversation's start time (so =%y=, =%m=, =%d=, =%H=, =%M=, =%S=
all work), then the literal token =<agent-name>= is replaced with
the agent name.  For embedded mode that name is =agent.name= from
the loaded =config.yaml= (via =cmacs-libreclaw-agent-name=); for
remote mode it is the remote server's =agent.name=, queried over
the bridge API (via =cmacs-libreclaw-remote-agent-name=).  The
default produces names such as =260522-143015-claude.org=.

The archived file excludes the editable =* Compose= region, so it
is a self-contained org document.  Archiving is additive: the
cmacs channel keeps its own per-project session persistence
(below) regardless of this setting.

* Per-project session persistence

The cmacs channel writes two kinds of state to disk, keyed off
the absolute path of each project root:

1. *Buffer history* — the visible conversation (all the
   =** timestamp sender= org headings above =* Compose=) is
   written to
   =~/.libreclaw/cmacs-sessions/<sha>.org=
   where =<sha>= is =secure-hash 'sha1 <project-root>=.  Written
   on buffer kill and after manual =C-c C-s=
   (=cmacs-libreclaw-cmacs-channel-save-history=), restored on
   next =cmacs-libreclaw-open= for the same project.
2. *AI session context* — libreclaw's own session manager
   persists the model's rolling context under the session key
   =cmacs:<project-root>:<user>=, in
   =~/.libreclaw/sessions/=.  This is independent of the buffer
   history and is managed entirely by libreclaw.

Because both stores key off the absolute project path, opening
the same project twice (even across Emacs restarts) picks up
where you left off, and opening a different project gives you
a clean slate with its own separate memory.

To reset one project without affecting others, delete the
matching =<sha>.org= file and the corresponding entry under
=~/.libreclaw/sessions/=.  To reset everything, wipe the two
directories entirely.
