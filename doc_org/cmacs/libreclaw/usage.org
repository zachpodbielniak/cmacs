#+TITLE: LibreClaw Usage
#+AUTHOR: Zach Podbielniak

* One-command entry point

If you just want to start chatting, this is it:

#+begin_src elisp
M-x cmacs-libreclaw-open
#+end_src

On first run this will:

1. Ensure libreclaw is running — auto-generating a default config
   at =cmacs-libreclaw-default-workspace= if one is not already
   configured (see [[file:configuration.org][configuration.org]]).
2. Detect the current *project directory* via =project-current=,
   =vc-root-dir=, or =locate-dominating-file= for common markers
   (=.git=, =Cargo.toml=, =pyproject.toml=, etc.).  Falls back to
   the current =default-directory= when no project is detected.
3. Open a dedicated org-mode buffer named =*libreclaw: <project>*=
   bound to that project root.  The first time you open a
   project, libreclaw starts a fresh AI session for it.  Subsequent
   opens restore the conversation from disk
   (=~/.libreclaw/cmacs-sessions/<sha>.org=) and continue the same
   session.

Two different projects, two different buffers, two independent
conversations — the cmacs channel gives each project root its
own room key, so libreclaw's session manager keeps their memory
separated automatically:

#+begin_example
M-x find-file ~/Documents/notes
M-x cmacs-libreclaw-open
  → *libreclaw: notes*     (fresh session for the notes project)

M-x find-file ~/source/projects/cmacs
M-x cmacs-libreclaw-open
  → *libreclaw: cmacs*     (completely separate session)
#+end_example

Both buffers persist across Emacs restarts.

* Starting and stopping manually

=cmacs-libreclaw-open= handles the lifecycle for you, but you can
drive it directly:

#+begin_src elisp
(setq cmacs-libreclaw-config-file "~/.libreclaw/config.yaml")
M-x cmacs-libreclaw-start
#+end_src

Calling =cmacs-libreclaw-start= when it is already running signals
=cmacs-libreclaw-error=.  Use =cmacs-libreclaw-running-p= to check
first.

Stop with =M-x cmacs-libreclaw-stop=.  Room buffers are left in
place with their history preserved; killing them removes them from
=cmacs-libreclaw-rooms-alist= and persists their history to disk.

* Room buffers

Each room surfaces as its own buffer named
=*libreclaw:CHANNEL-ID:ROOM-ID*=.  The buffer uses
=cmacs-libreclaw-room-mode=, derived from =org-mode=, with a fixed
structure:

#+begin_src
#+TITLE: LibreClaw — <room-name>
#+STARTUP: showall indent
#+OPTIONS: toc:nil num:nil
#+PROPERTY: channel <channel-id>
#+PROPERTY: room-id <room-id>

* Messages

** 2026-04-15 14:30:12  bob
Hey, just checking in.

** 2026-04-15 14:31:05  you
All good — working on the libreclaw integration.
#+begin_src c
void hello(void) { puts("world"); }
#+end_src

* Compose                                             :compose:
<cursor parks here; type, then C-c C-c sends>
#+end_src

Everything above the =* Compose= sentinel is read-only — attempting
to edit it signals =text-read-only=.  The region below is a normal
org buffer, so all your usual org muscle memory works: source
blocks, tables, links, lists, footnotes, =M-RET= to insert a new
list item, =TAB= to cycle visibility, etc.

* Sending a message

Type below the =* Compose= heading and press =C-c C-c=.  The compose
region is read, cleared, sent async through the libreclaw channel,
and inserted as a new =** TIMESTAMP you= heading above the sentinel
as a local echo.

Useful bindings (all buffer-local to =cmacs-libreclaw-room-mode=):

| Binding       | Command                          | Purpose                          |
|---------------|----------------------------------|----------------------------------|
| =C-c C-c=     | =cmacs-libreclaw-send-compose=    | send & clear                     |
| =C-c C-k=     | =cmacs-libreclaw-clear-compose=   | drop the draft                   |
| =C-c C-x C-f= | =cmacs-libreclaw-attach-file=     | insert an org file: link         |
| =C-c C-a=     | =cmacs-ai-view-attach=            | attach what you have on screen   |

=RET=, =TAB=, =C-c C-l=, etc. are the standard org-mode keys and
behave as usual for multi-line editing.

* Why the transcript cannot be edited, and why that took two goes

A read-only region in Emacs has two ways to fail /open/ -- protecting
nothing while looking protected -- and cmacs hit both:

1. *Emacs clears =before-change-functions= when a function on it
   signals.*  A guard that signals =text-read-only= therefore protects a
   buffer *exactly once*: after the first stray keypress the hook is
   gone and every edit after it lands.  That is what the transcript
   guard used to be on its own.
2. *=(read-only t rear-nonsticky t)= -- the comint idiom -- permits
   insertion in the MIDDLE of the run.*  With =rear-nonsticky= Emacs
   decides inserted text would join neither neighbouring interval and
   allows the insert, so only the run's edges were protected.

So finished text carries =(read-only t front-sticky t)=, applied at turn
boundaries; the property is enforced in C and cannot be disarmed.  The
change guard is kept for anything not yet sealed, and is
re-armed every time the transcript is sealed, so a clearing heals itself
at the next message rather than lasting the session.

Both are covered by tests that try the same edit three times and once in
the middle -- a single attempt at the edge passes against either bug.

* What the agent is told about your screen

An agent room is a chat with something that can drive your editor, so
"summarize this" has to mean the buffer you are looking at rather than
the room you typed it in.  Each outgoing message therefore carries an
invisible prelude: a listing of the buffers currently on your screen --
name, file, mode, where point is, which lines are visible -- and, on the
first message of a room, a standing explanation of what that listing is
for.

*The room shows exactly what you typed.*  The prelude rides the wire and
nothing else; the local echo and the send are separate statements in
=cmacs-libreclaw-send-compose= for that reason, and there is a test
holding them apart.  A transcript of an agent conversation is still
readable a week later.

The listing carries no buffer text.  The agent has cmacs's whole MCP
surface tunnelled to it, so it reads what it needs with
=get_buffer_content=, =search_buffer= or =current_view=.  See
[[file:../cmacs-ai.org][What the model can see]] for the full model, the
exclusion rules, and the =inline= fallback for an agent with no tools.

*Only cmacs's own agent rooms.*  A matrix room, a mailing list or a
webhook channel is other people, and what is on your screen is none of
their business -- the branch in =cmacs-libreclaw-send-compose= is what
enforces that.

Two knobs:

| Variable                           | Default                          | What                                  |
|------------------------------------+----------------------------------+---------------------------------------|
| =cmacs-libreclaw-view-mode=        | =tools=                          | =tools= (agent has MCP) or =inline=   |
| =cmacs-libreclaw-context-function= | =cmacs-libreclaw-default-context= | build the prelude yourself, or nil to send nothing |

Set =cmacs-libreclaw-view-mode= to =inline= if the agent keeps saying it
cannot see your screen -- that means its MCP config does not include the
cmacs server.  =cmacs-ai-view-attach-mode= set to =off= disables the
whole thing here too.

=C-c C-a= forces the payload: the visible buffers' actual text, dropped
into the compose region where you can trim it before sending.

* Switching between rooms

=M-x cmacs-libreclaw-show-room= prompts with a completion list of
=CHANNEL/ROOM-ID= strings and pops the selected buffer to the
current window.

* Sending programmatically

The send path is available as a DEFUN:

#+begin_src elisp
(cmacs-libreclaw-send-message
 "matrix" "!roomid:example.com"
 "Hello from Elisp!")
#+end_src

Optional =HTML-BODY= and =THREAD-ID= arguments cover Matrix reply
threads.
