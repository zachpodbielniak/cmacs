#+TITLE: Org-Ex: Interactive Widget Embedding
#+STARTUP: showall
#+OPTIONS: toc:2 num:t

* Overview

Org-Ex embeds interactive widgets directly inside Org mode buffers.
Instead of static screenshots or code output, an Org document can
contain live GTK controls, WebKit web views, embedded file buffers,
and evaluated code blocks --- all rendered inline as overlays.

The subsystem has three layers:

| Layer              | Location                     | Role                                    |
|--------------------+------------------------------+-----------------------------------------|
| liborgex (C)       | =cmacs/org-ex/lib/=          | GObject types: widgets, bindings, channels |
| C DEFUN bridge     | =cmacs/org-ex/cmacs-org-ex.c= | Wraps liborgex as Emacs primitives       |
| Elisp layer        | =lisp/cmacs/cmacs-org-ex*.el= | Minor mode, dispatch, export, state     |

** Rendering Architecture

Under pgtk, Org-Ex embeds native GTK3 widgets directly in the Emacs
frame using the =gtk-embed= xwidget type.  This is a CMacs extension
to the Emacs xwidget system (=src/xwidget.c=) that adds the actual
=GtkWidget= to the frame's =GtkFixed= container --- no offscreen
rendering or draw callbacks needed, the widget draws itself natively.

The rendering path for GTK widget types (=slider=, =web=, =elisp=):

1. Widget creation function produces a =GtkWidget= via GObject
   Introspection (e.g. =gobject-new "GtkScale"= or
   =gobject-new "WebKitWebView"=).
2. The widget is wrapped as an =OrgExWidgetGtk= via
   =org-ex-widget-gtk-new=.
3. A =gtk-embed= xwidget is created and the underlying =GtkWidget= is
   extracted via =org-ex-widget-gtk-get-widget= and set with
   =xwidget-gtk-embed-set-widget=.
4. The xwidget is displayed via an Org buffer overlay.
5. On redisplay, Emacs adds the widget to the frame and positions it
   with =gtk_fixed_move=.

*Note:* pgtk uses GTK3 (=libgtk-3=), not GTK4.  All GI widget
creation uses =gi-require "Gtk" "3.0"=.

** Activating Org-Ex

#+begin_example
;; Automatic: add this keyword to the org file header:
#+ORGEX: t

;; Manual:
M-x cmacs-org-ex-mode
#+end_example

When the mode activates it creates an =OrgExDocument=, scans the
buffer for =#+BEGIN_WIDGET= blocks, instantiates each widget, and
displays them as overlays.

* Widget Block Syntax

Widgets are declared using Org special blocks with the type =WIDGET=.
The word after =WIDGET= on the =#+BEGIN_WIDGET= line specifies the
widget subtype.

** Basic Structure

#+begin_example
#+BEGIN_WIDGET slider
:min 0
:max 100
:value 50
:step 1
:width 400
:height 60
#+END_WIDGET
#+end_example

The general form is:

#+begin_example
#+BEGIN_WIDGET <subtype>
:<key1> <value1>
:<key2> <value2>
...
#+END_WIDGET
#+end_example

=<subtype>= is a registered widget type name string (e.g. =slider=,
=web=, =buffer=).  Properties are lines beginning with =:key=
followed by whitespace and a value.

** Common Properties

All widget types accept these properties:

| Property     | Description                                      | Default |
|--------------+--------------------------------------------------+---------|
| =:width=     | Width in pixels or percentage (e.g. =50%=)       |     400 |
| =:height=    | Height in pixels or =auto=                       |     200 |
| =:bind=      | Bind to a document =#+PROPERTY:= line            |         |
| =:publish=   | Publish value changes to a named channel         |         |
| =:subscribe= | Subscribe to a named channel                     |         |
| =:direction= | Binding direction: =both=, =to-widget=, =from-widget= | =both= |
| =:reactive=  | If =t=, re-evaluate the widget when bindings change |     =nil= |
| =:interval=  | Re-evaluate every N seconds (polling mode)       |         |
| =:bridge=    | If =t=, enable JS bridge for =web= widgets       |     =nil= |

** Responsive Sizing

Widget dimensions support responsive values in addition to fixed
pixel sizes:

| Value      | Behavior                                               |
|------------+--------------------------------------------------------|
| =400=      | Fixed size: 400 pixels                                 |
| =50%=      | Percentage of the Emacs window body width              |
| =auto=     | Compute from content (images: intrinsic size; web: fit) |

#+begin_example
#+BEGIN_WIDGET web
:url https://example.com
:width 80%
:height auto
#+END_WIDGET
#+end_example

Percentage widths are recalculated when the Emacs window is resized
via =window-configuration-change-hook=.  The =auto= height is
currently supported by =image= and =web= widget types.

** Widget IDs

Each widget is assigned a unique ID of the form =<subtype>-<position>=
where =<position>= is the buffer byte offset of the =#+BEGIN_WIDGET=
line.  This ID is used for document registration, state persistence,
and export.

* Built-in Widget Types

Org-Ex ships with six built-in widget types, registered at load time
by =cmacs-org-ex-widgets.el=.

** slider

A GTK3 =GtkScale= control created via GObject Introspection
(=gi-require "Gtk" "3.0"=).  The slider is embedded natively in the
Emacs frame using the =gtk-embed= xwidget type.

| Property | Description         | Default |
|----------+---------------------+---------|
| =:min=   | Minimum value       |       0 |
| =:max=   | Maximum value       |     100 |
| =:value= | Initial value       |      50 |
| =:step=  | Step increment      |       1 |

#+begin_example
#+BEGIN_WIDGET slider
:min 0
:max 255
:value 128
:step 1
:width 400
:height 60
:bind brightness
#+END_WIDGET
#+end_example

The slider emits a =value-changed= GObject signal when the user
drags it.  When bound to a property, the corresponding =#+PROPERTY:=
line updates automatically.

** web

A WebKit2GTK web view created via GObject Introspection
(=gi-require "WebKit2" "4.1"=).  The =WebKitWebView= is a GTK3
widget, so it embeds natively through the =gtk-embed= path just like
slider and elisp widgets.  Specify either a URL or inline HTML.

| Property | Description                          |
|----------+--------------------------------------|
| =:url=   | URL to load                          |
| =:html=  | Inline HTML (used if =:url= absent)  |

#+begin_example
#+BEGIN_WIDGET web
:url https://example.com
:width 600
:height 400
#+END_WIDGET
#+end_example

#+begin_example
#+BEGIN_WIDGET web
:html <h1>Hello</h1><p>Inline HTML content.</p>
:width 400
:height 200
#+END_WIDGET
#+end_example

** buffer

Embeds another file as an Emacs buffer view inside the Org document.

| Property    | Description                             | Default    |
|-------------+-----------------------------------------+------------|
| =:file=     | Path to the file to embed (required)    |            |
| =:editable= | If =t=, the embedded buffer is editable | view-only  |

#+begin_example
#+BEGIN_WIDGET buffer
:file ~/code/hello.py
:editable t
:width 500
:height 300
#+END_WIDGET
#+end_example

** elisp

Evaluates Elisp code.  The result must be a =GtkWidget= (wrapped
via =org-ex-widget-gtk-new=) or a value coerced to an HTML string.

| Property | Description                        |
|----------+------------------------------------|
| =:code=  | Elisp expression to evaluate       |

#+begin_src emacs-lisp :eval no
;; Example: create a GTK button
#+BEGIN_WIDGET elisp
:code (let ((btn (gi-call "Gtk" "button_new_with_label" "Click Me"))) btn)
:width 200
:height 50
#+END_WIDGET
#+end_src

** crispy

Evaluates a C code string via the Crispy subsystem.  Code and stdout
output are displayed as a code widget.

| Property | Description                        |
|----------+------------------------------------|
| =:code=  | C code to evaluate                 |

#+begin_example
#+BEGIN_WIDGET crispy
:code printf("result: %d\n", 6 * 7);
:width 400
:height 150
#+END_WIDGET
#+end_example

** bacon

Evaluates a shell command via the Bacon subsystem.  Command and output
are displayed as a code widget.

| Property | Description                        |
|----------+------------------------------------|
| =:code=  | Shell command to evaluate          |

#+begin_example
#+BEGIN_WIDGET bacon
:code echo "Files:" && ls -1 ~/Documents | head -5
:width 400
:height 150
#+END_WIDGET
#+end_example

** wayland

Embeds a live Wayland client window inside the Org document.  The
client's surface is composited directly into the widget area via the
Gowl compositor --- no pixel copying or offscreen rendering.

| Property    | Description                                    | Default |
|-------------+------------------------------------------------+---------|
| =:command=  | Command to launch the Wayland client (required) |         |
| =:app-id=   | Match an existing client by app-id instead      |         |

#+begin_example
#+BEGIN_WIDGET wayland
:command foot
:width 600
:height 400
#+END_WIDGET
#+end_example

#+begin_example
#+BEGIN_WIDGET wayland
:app-id org.gnome.Calculator
:width 300
:height 400
#+END_WIDGET
#+end_example

The widget spawns the command (or finds an existing client by
=app-id=), then embeds it using the same scene-reparenting mechanism
as =gowl-embed-into=.  Keyboard focus follows the same ESC
escape-hatch described in the Gowl manual.

** image

Displays an image file inline in the Org document.  The image is
rendered natively via GdkPixbuf and displayed as a GTK =GtkImage=
widget.

| Property   | Description                                    | Default |
|------------+------------------------------------------------+---------|
| =:file=    | Path to the image file (required)              |         |
| =:scale=   | Scale factor for the image                     |     1.0 |

#+begin_example
#+BEGIN_WIDGET image
:file ~/photos/diagram.png
:width 500
:height auto
#+END_WIDGET
#+end_example

Supported formats: PNG, JPEG, GIF, SVG, WebP, TIFF (anything
supported by GdkPixbuf).  Paths are resolved relative to the Org
file's directory, just like =buffer= widgets.

* Reactive Binding

Org-Ex provides reactive data binding between widgets and Org
document properties.

** The :bind Directive

Add =:bind <property-name>= to a widget block to create a reactive
link with a =#+PROPERTY:= line:

#+begin_example
#+PROPERTY: temperature 50

#+BEGIN_WIDGET slider
:min 0
:max 100
:value 50
:bind temperature
#+END_WIDGET
#+end_example

When the user drags the slider, the =#+PROPERTY: temperature= line
updates.  When the property line is edited manually, the slider
position updates.

** Binding Direction

| Direction      | Behavior                                          |
|----------------+---------------------------------------------------|
| =both=         | Bidirectional (default).  Widget and property sync |
| =to-widget=    | Property changes update widget only                |
| =from-widget=  | Widget changes update property only                |

#+begin_example
#+BEGIN_WIDGET slider
:min 0
:max 100
:bind temperature
:direction from-widget
#+END_WIDGET
#+end_example

** How It Works

Under the hood, =cmacs-org-ex-setup-bindings= calls
=org-ex-binding-create= to create an =OrgExBinding= GObject that
connects the widget to the document.  The document monitors
=#+PROPERTY:= changes via =after-change-functions= and calls
=org-ex-document-notify-property-changed= to propagate.  A
re-entrancy guard (=cmacs-org-ex--inhibit-notify=) prevents infinite
update loops.

* Channels

Channels provide decoupled communication between widgets that are not
bound to the same property.  A channel is a named message bus:
publishers emit values, subscribers receive them.

** Declaring Channels

Use =:publish= and =:subscribe= in widget blocks:

#+begin_example
#+BEGIN_WIDGET slider
:min 0
:max 100
:value 50
:publish data-feed
#+END_WIDGET

#+BEGIN_WIDGET web
:html <div id="display">Waiting...</div>
:subscribe data-feed
:width 400
:height 100
#+END_WIDGET
#+end_example

** Programmatic Use

#+begin_src emacs-lisp :eval no
(let ((channel (org-ex-channel-create "my-channel")))
  ;; Subscribe:
  (gobject-connect channel "message"
    (lambda (value)
      (message "Received: %s" value)))
  ;; Publish:
  (org-ex-channel-publish channel "hello"))
#+end_src

** Channel Lifecycle

Channels are created lazily on first reference (either =:publish= or
=:subscribe=).  They are stored in a buffer-local alist
(=cmacs-org-ex--channels=) and cleaned up when the mode is disabled.

* Inline Widgets

For small widgets that belong inside paragraph text, Org-Ex provides
a custom Org link type:

#+begin_example
See the current value: [[widget:slider:min=0,max=100,value=50]]

With a description: [[widget:slider:min=0,max=100][Temperature]]
#+end_example

The link format is =[[widget:<type>:<params>]]= where =<params>= is
a comma-separated list of =key=value= pairs.

On export, the link produces:

| Backend | Output                                                |
|---------+-------------------------------------------------------|
| HTML    | =<span class="org-ex-widget" data-type="...">...=    |
| LaTeX   | =\texttt{...}=                                        |
| Text    | The description or path string                        |

* State Persistence

Widget state (slider positions, text entry values, toggle states) is
ephemeral --- it lives only in GObject properties.  Org-Ex persists
state to a sidecar file so values survive buffer kills and Emacs
restarts.

** Sidecar File

For a file =notes.org=, the state file is =notes.org.org-ex-state=.
The format is a Lisp alist written with =prin1=:

#+begin_example
;; org-ex state file --- auto-generated
;; Do not edit manually.

(("slider-42" ("value" . "73") ("active" . "t"))
 ("web-200" ("text" . "hello"))
 (channel "data-feed"))
#+end_example

** Save and Restore

State is saved automatically when:

- The buffer is killed (=kill-buffer-hook=).
- =cmacs-org-ex-mode= is disabled.

State is restored when =cmacs-org-ex-mode= enables: the sidecar is
read and values are applied via =gobject-set= after a 100ms timer
delay to ensure widgets have finished initialization.

** Configuration

| Variable                       | Description                    | Default           |
|--------------------------------+--------------------------------+-------------------|
| =cmacs-org-ex-state-enabled=   | Enable state persistence       | =t=               |
| =cmacs-org-ex-state-suffix=    | Suffix for state file path     | =.org-ex-state=   |

** Cleanup

=M-x cmacs-org-ex-state-delete= removes the sidecar state file for
the current buffer.

* Export Behavior

Org-Ex defines derived export backends so that widget blocks produce
meaningful output.

** HTML Export

=C-c C-e w h= exports using the =org-ex-html= backend.  For each
=#+BEGIN_WIDGET= block:

1. If the widget is live, =org-ex-widget-export-html= is called.
   Web widgets export their HTML directly; GTK widgets produce a
   screenshot; code widgets export a =<pre>= block with output.
2. If the widget is not live, a placeholder =<div>= with the widget
   type and properties is emitted.

** Text Export

=C-c C-e w t= exports using the =org-ex-text= backend.  Widgets
produce a plain text description, e.g. =[slider widget: min=0,
max=100, value=73]=.

** PDF Export

PDF export (via LaTeX) uses text fallback descriptions.  For richer
PDF output, export to HTML first, then print to PDF.

** Export Commands

| Keybinding      | Function                          | Output         |
|-----------------+-----------------------------------+----------------|
| =C-c C-e w h=   | =cmacs-org-ex-export-to-html=     | HTML file      |
| =C-c C-e w H=   | =cmacs-org-ex-export-as-html=     | HTML buffer    |
| =C-c C-e w t=   | =cmacs-org-ex-export-to-text=     | Text file      |
| =C-c C-e w T=   | =cmacs-org-ex-export-as-text=     | Text buffer    |

* Custom Widget Types

Org-Ex is extensible: you can define new widget types that integrate
with the block syntax, binding system, and export pipeline.

** Registering a Type in Elisp

#+begin_src emacs-lisp :eval no
(cmacs-org-ex-register-widget-type "my-gauge"
  (lambda (props width height)
    ;; PROPS is an alist of ("key" . "value") strings.
    ;; Must return an OrgExWidget GObject.
    (let* ((label (or (cdr (assoc "label" props)) "Gauge"))
           (gtk-widget (gi-call "Gtk" "label_new" label))
           (widget (org-ex-widget-gtk-new gtk-widget)))
      (org-ex-widget-set-size widget width height)
      widget)))
#+end_src

After registration:

#+begin_example
#+BEGIN_WIDGET my-gauge
:label CPU Temperature
:width 200
:height 50
#+END_WIDGET
#+end_example

** GObject Subclassing (C)

For full control, subclass =OrgExWidget= in C:

1. Use =G_DECLARE_FINAL_TYPE= to declare your widget type.
2. Override the virtual methods in =OrgExWidgetClass=:

| Method          | Purpose                                          |
|-----------------+--------------------------------------------------|
| =render=        | Render the widget to a display target            |
| =update=        | Update widget state from properties              |
| =teardown=      | Release display resources                        |
| =save_state=    | Serialize ephemeral state for persistence        |
| =restore_state= | Restore state from saved =OrgExWidgetState=     |

3. Implement =OrgExExportable= for export support (=export_html=,
   =export_text=).
4. Register the type from Elisp using
   =cmacs-org-ex-register-widget-type=.

** GObject Interfaces

| Interface          | Purpose                                     |
|--------------------+---------------------------------------------|
| =OrgExRenderable=  | For widgets that render to a display context |
| =OrgExExportable=  | For widgets that produce export output       |

* JS Bridge

Web widgets with =:bridge t= gain a bidirectional JavaScript bridge
that allows JavaScript code in the WebKit view to call Elisp functions
and vice versa.  The bridge is implemented via WebKit user content
manager messages.

** Enabling the Bridge

#+begin_example
#+BEGIN_WIDGET web
:html <button onclick="cmacs.call('greet', 'world')">Say Hello</button>
:bridge t
:width 400
:height 100
#+END_WIDGET
#+end_example

** Registering Bridge Functions

Use =cmacs-org-ex-bridge-register= to expose Elisp functions to
JavaScript:

#+begin_src emacs-lisp
(cmacs-org-ex-bridge-register "greet"
  (lambda (name)
    (message "Hello, %s!" name)))
#+end_src

From JavaScript, call registered functions via the =cmacs= object:

#+begin_src javascript
// Call Elisp from JS:
cmacs.call("greet", "world");

// Call with callback:
cmacs.call("get-value", "key", function(result) {
  document.getElementById("output").textContent = result;
});
#+end_src

** Bridge API

| Function                                       | Description                          |
|------------------------------------------------+--------------------------------------|
| =(cmacs-org-ex-bridge-register NAME FN)=       | Register FN as callable from JS      |
| =cmacs.call(name, ...args)=                    | (JS) Call a registered Elisp function |
| =cmacs.call(name, ...args, callback)=          | (JS) Call with result callback       |

* Ink Canvas

The ink canvas is a tablet-driven drawing surface embedded inside Org
buffers via =#+BEGIN_INK= blocks.  Strokes live inline in the block
body as one-stroke-per-line S-expressions, so a single =.org= file is
self-contained, hand-editable, and produces minimal git diffs as
drawings evolve.

A modal capture window --- pure GTK3 with Cairo rendering --- reads
pen, eraser, and pressure straight from =GdkDeviceTool= and the
=GDK_AXIS_PRESSURE= axis.  Under standalone pgtk Emacs on Wayland, the
host compositor's =wp_tablet_v2= events flow through GDK unchanged,
so a Wacom tablet works without any extra configuration.

** Requirements

- *SVG image support is mandatory.*  The rendered canvas is an inline
  =(image :type svg)= overlay.  Configure with =--with-rsvg=.  Install
  =librsvg2-devel= (Fedora / RHEL), =librsvg2-dev= (Debian / Ubuntu),
  or the equivalent =librsvg= package on Arch / macOS / FreeBSD.  The
  =install-deps= helper at the repo root handles every supported OS.
- GTK3 (already required by pgtk Emacs).
- Cairo (already required by pgtk Emacs).

** Block Syntax

Ink blocks are a parallel block kind to =#+BEGIN_WIDGET= --- they have
their own header keyword vocabulary and their body is parsed by a
hand-rolled S-expression reader.

#+begin_example
#+BEGIN_INK :id 7e3a-9b21 :w 800 :h 400 :v 1
;; cmacs-ink v1; one stroke per line for git-friendly diffs
(s :t pen :c "#222" :w 2 :p ((123 245 850) (130 250 860) (138 255 870)))
(s :t pen :c "#cc2a2a" :w 2.5 :p ((220 100 700) (228 115 750)))
#+END_INK
#+end_example

| Header keyword | Description                                                            | Default |
|----------------+------------------------------------------------------------------------+---------|
| =:id=          | Unique block id; used by the write path to re-resolve at commit time.  |         |
| =:w=           | Canvas width in pixels.                                                |     800 |
| =:h=           | Canvas height in pixels.                                               |     400 |
| =:v=           | Body-format version.                                                   |       1 |

Each stroke line:

#+begin_example
(s :t TOOL :c "#hex" :w WIDTH :p ((X Y P) (X Y P) ...))
#+end_example

| Stroke key | Description                                                                                  |
|------------+----------------------------------------------------------------------------------------------|
| =:t=       | Tool symbol: =pen=, =eraser= (transient -- never persisted), =highlighter= (reserved v2).    |
| =:c=       | Hex colour string for the stroke.                                                            |
| =:w=       | Base width in pixels; pressure scales it per-segment.                                        |
| =:p=       | Points list.  Each point =(X Y P)= with X,Y integer pixels and P pressure scaled to 0..1000. |

=;;= comment lines inside the body are ignored on parse and preserved
on round-trip --- this is how the canonical version marker line lives
at the top of every block.

** Rendering

When =cmacs-org-ex-ink-auto-render= is non-nil (default), every block
body is replaced visually with an SVG image overlay.  The renderer
(=org_ex_ink_render_to_svg= in
=cmacs/org-ex/lib/core/org-ex-ink-render.c=) emits:

- A white background rect, so strokes are visible against any theme.
- A 1px =#cccccc= border so the canvas extent is visible.
- One =<path>= per stroke segment, split at pressure-change boundaries
  (=Δwidth > 0.3px=).  Single-pressure strokes collapse to a single
  path.
- Single-point strokes as =<circle>= so taps remain visible.
- Eraser strokes are skipped --- they are hit-test trails, never
  persisted into the rendered SVG.

The underlying buffer text is unchanged.  =save-buffer= writes the
canonical S-expression form to disk; the SVG is purely a display
overlay.

** Capture Window

The capture window is a transient GTK3 toplevel
(=cmacs/org-ex/cmacs-org-ex-ink-capture.c=).  It runs a nested
=GMainLoop= so the call returns synchronously to Elisp.

| Key       | Action                                  |
|-----------+-----------------------------------------|
| =C-RET=   | Commit and return strokes.              |
| =Esc=     | Cancel and discard.                     |
| =C-z=     | Undo last committed stroke.             |

Tablet input model:

1. *Pen tip* (=GDK_DEVICE_TOOL_TYPE_PEN=) -- =:t pen= strokes.
2. *Eraser end* (=GDK_DEVICE_TOOL_TYPE_ERASER=) -- each stroke is a
   hit-test path; on release every existing pen stroke whose points
   lie within =max(stroke_width, 6)= pixels is removed wholesale.
   Whole strokes only --- never partial pixels.
3. *Side-button-as-eraser fallback* -- when
   =cmacs-org-ex-ink-side-button-erases= is non-nil (default), holding
   button 2 mid-stroke routes through the same erase path.

While the modal is up Emacs's =SIGALRM=-driven atimer chain is blocked
via =pthread_sigmask=.  Without that guard the hourglass timer firing
during a Wacom =tablet-tool-added/done= dispatch can re-enter GTK
widget realisation in an inconsistent device state and trigger a GDK
assertion.

** Marginalia

Marginalia are per-line ink notes anchored to source code or
prose lines.  See *Storage* below for where annotations are
persisted (org files use an inline section by default; everything
else uses a sidecar).

Anchors carry both a line number and a SHA1 of the line plus two
neighbours.  On load, anchors are reconciled:

1. Match by =:line=; if =:line-hash= matches the current line's hash,
   bind to that marker.
2. Otherwise search =cmacs-ink-marginalia-search-radius= (10) lines
   around for a hash match and relocate.
3. Otherwise mark the anchor as orphan and float it to the top of the
   buffer with an =[orphan annotation]= badge.

** Storage

cmacs-ink persists per-line marginalia and region overlay
annotations in one of two places, chosen automatically per
buffer:

- *Inline section* (default for org buffers).  A folded =* cmacs-ink :noexport:= heading is appended to the org file with one block per anchor.  Annotations travel with the file on copy/move; =git status= captures source + annotation in a single commit; the section is excluded from HTML/PDF exports.
- *Sidecar file* (default for non-org buffers).  A =<source>.cmacs-ink= file next to the source.  Source formats like C / Python / Markdown can't host arbitrary blocks without breaking the parser, so the sidecar is the only option.  The sidecar is /pretty-printed/ now (one anchor per indented form, one stroke per line) so it produces minimal =git diff= output as strokes change.

The choice is governed by =cmacs-ink-storage=:

| Value     | Behaviour                                                                  |
|-----------+----------------------------------------------------------------------------|
| ='auto=   | (default) org-mode → inline; everything else → sidecar.                    |
| ='inline= | force inline (errors when not org-mode).                                   |
| ='sidecar=| force sidecar regardless of mode.                                          |

May be set buffer-locally or via =.dir-locals.el=.

*** Inline Section Format

#+begin_example
* cmacs-ink                                                          :noexport:
:PROPERTIES:
:VISIBILITY: folded
:END:

#+BEGIN_INK_MARGINALIA :id "ann-..." :line 412 :hash "9af2c0..." :w 320 :h 120 :created 1745600000
;; cmacs-ink marginalia v1; one stroke per line for git-friendly diffs
(s :t pen :c "#cc2a2a" :w 2 :p ((50 30 850) (60 35 870)))
#+END_INK_MARGINALIA

#+BEGIN_INK_REGION :id "rgn-..." :start-line 412 :start-col 4 :end-line 415 :end-col 12 :hash "9af2c0..." :w 480 :h 60 :created 1745600000
;; cmacs-ink region v1; one stroke per line for git-friendly diffs
(s :t pen :c "#cc2a2a" :w 2 :p ((10 5 850) (24 12 875)))
#+END_INK_REGION
#+end_example

Block headers use the same flat =:key value= parser as
=#+BEGIN_INK= canvas blocks; bodies use the canonical stroke
S-expr grammar produced by =org_ex_ink_strokes_to_string=.
Adding a stroke is literally one new line in the diff.

*Warning:* the inline section is rewritten as a unit on every
save.  Any text you put inside =* cmacs-ink= that is /not/
inside a =#+BEGIN_INK_*=..=#+END_INK_*= block is deleted on the
next save.  Keep your own notes in a sibling heading.

*** Backward Compatibility

The loader tries the inline section first; if absent, falls
back to reading =<file>.cmacs-ink=.  Existing v1 single-line
sidecars (one giant =prin1=) load cleanly --- no flag day --- and
are upgraded to the pretty-printed form (or to inline when the
buffer is org-mode) on the next save.

*** Migration

=M-x cmacs-ink-migrate-to-inline=, run in an org buffer, reads
any existing sidecar and writes the equivalent inline section,
then prompts to delete the sidecar.  No reverse command: to
switch a buffer back to sidecar, set =(setq-local
cmacs-ink-storage 'sidecar)= and save --- the inline section is
removed and the sidecar regenerated.

** Region Overlay Ink

Marginalia attaches a single-line note as an SVG /image/ overlay
below the line.  *Region overlay ink* is a complementary mode:
select a multi-line range, draw on a screenshot of that text, and
the strokes are painted as a *transparent Cairo layer on top of
the live buffer text*.  The underlying glyphs remain editable;
strokes scroll with the text and re-anchor on each redisplay.

This is a cmacs-only feature: it depends on a small extension to
=src/pgtkterm.c=.  *Two* paint-commit sites are intercepted; the
hook needs to fire at /both/ for strokes to remain stable across
cursor moves and partial redisplays:

1. =pgtk_frame_up_to_date(f)= --- catches out-of-redisplay flushes
   (echo-area updates, cursor-blink via =gui_update_cursor=,
   post-=force-window-update= notifications).  The body is gated on
   =!buffer_flipping_blocked_p()=, so it is a no-op during
   =redisplay_internal=.
2. =pgtk_buffer_flipping_unblocked_hook(f)= --- the canonical
   "redisplay just finished" callback during the normal flow.
   =redisplay_internal= wraps its work in
   =block_buffer_flips=/=unblock_buffer_flips=; the /unblocked/
   hook is what actually performs the =flip_cr_context= during a
   normal cursor move or scroll.  Without painting here,
   partial-row repaints clear stroke pixels and the strokes never
   come back until something forces a full-frame update.

In both sites the hook calls =cmacs_ink_overlay_paint(f)=, which
walks every leaf window of the frame, reads the buffer-local
=cmacs-ink-region--annotations= list via =buffer_local_value=, and
paints stored strokes on the active Cairo context using
=org_ex_ink_paint_strokes_cairo=.  Strokes are positioned via
=pos_visible_p= so the overlay tracks scroll, edits, and resize.

The capture window is extended to accept a Cairo background
surface.  =cmacs-ink-region-annotate= takes a screenshot of the
selected region via the new =cmacs-frame-screenshot-rect= DEFUN
(which copies from the frame's back-buffer with
=cairo_set_source_surface= + =cairo_paint=) and threads it into the
capture as the canvas background --- the user is literally drawing
on top of the same pixels they will later see overlaid on the
buffer.

*** Workflow

1. =M-x cmacs-ink-overlay-mode= in the buffer.
2. Select a multi-line region.
3. =C-c i r= (=cmacs-ink-region-annotate=) opens the capture window
   with a screenshot of the selected text as background.
4. Draw across the text with pen / mouse.
5. =C-Return= commits.  Strokes paint on top of the real buffer
   text.

| Key       | Command                                    | Purpose                              |
|-----------+--------------------------------------------+--------------------------------------|
| =C-c i r= | =cmacs-ink-region-annotate=                | Annotate the active region.          |
| =C-c i R= | =cmacs-ink-region-edit-at-point=           | Re-edit annotation covering point.   |
| =C-c i D= | =cmacs-ink-region-delete-at-point=         | Remove the annotation.               |
| =C-c i L= | =cmacs-ink-region-list=                    | List all region annotations.         |
| =C-c i o= | =cmacs-ink-overlay-mode=                   | Toggle paint pass on/off.            |

*** Storage

Region annotations are persisted alongside per-line marginalia
through the same dispatcher --- inline =#+BEGIN_INK_REGION=
blocks in the =* cmacs-ink :noexport:= section for org buffers,
or under =:region-anchors= in the pretty-printed sidecar for
non-org buffers.  See the *Storage* section under *Marginalia*
above for the policy, format, and migration command.

Reconciliation on load tries the saved (=:start-line= ,
=:start-col= ); falls back to a hash search of
=cmacs-ink-region-search-radius= lines around it; orphans if no
match.

| =cmacs-ink-region-default-base-width=   |         2.0 | Default base pen width.                    |
| =cmacs-ink-region-default-alpha=        |        0.85 | Stroke layer opacity (read every redisplay). |

*** Limitations

- pgtk only.  X11/Lucid and tty frames don't have the post-glyph
  Cairo hook; the feature errors gracefully on non-pgtk frames.
- Heavy edits inside the annotated region don't reflow strokes;
  they stay anchored to the start-marker.  Use re-edit
  (=C-c i R= ) to redraw on top of the new layout.
- Pressure under =cmacs --gowl= is fixed at =1.0= until gowl
  advertises =wp_tablet_v2= (v2).

** Limitations and Roadmap

- Under =cmacs --gowl=, pressure is fixed at =1.0= (gowl does not yet
  advertise =wp_tablet_v2=; v2 lifts this).
- =highlighter=, replay scrubber, gestures (scribble-out, lasso), and
  OCR enrichment are reserved for v2.
- Voice-coupled ink --- time-linking strokes to libreclaw audio --- is
  a v3 target.
